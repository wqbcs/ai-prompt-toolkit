# 提示词设计原则

> **文档版本**：v1.0  
> **日期**：2026-05-28  
> **来源**：基于64次迭代（B1-B10）+ 4次调研（RSH-INIT-01/02/03 + RSH-B7-1）提炼

---

## 原则1：Context Engineering优先

**核心观点**：架构完整上下文(System/Instruction/User/Tools/RAG)比调优文本更重要。

**调研依据**：
- RSH-INIT-01中DAIR.AI Context Engineering Guide指出：上下文工程是提示词工程的自然演进
- 完整上下文包含5层：System(系统约束) → Instruction(任务指令) → User(用户输入) → Tools(可用工具) → RAG(检索增强)

**迭代验证**：
- B3(角色设定深化)为05/07/10补充工作方式后，角色设定维度从13.9提升至15.8(+1.9)
- 验证结论：角色定义从"身份+能力"扩展为"经验+领域+能力+工作方式"4要素后，LLM输出质量显著提升

**实践建议**：
- 角色定义必须包含：经验年限 + 专业领域 + 核心能力 + 工作方式
- 系统约束必须覆盖：技术 + 业务 + 安全 + 性能 四维度
- 工具声明必须包含：工具名 + 用途 + 使用时机 + 输出格式

## 原则2：结构化输出强制

**核心观点**：所有分析/审查类场景必须指定JSON/YAML输出格式。

**调研依据**：
- RSH-INIT-02设计模式中结构化输出模式是最稳定的设计模式
- 工业界实践：Copilot for PR Review、Snyk、SonarQbe均使用结构化输出

**迭代验证**：
- B4(输出格式精确化)为04/06/07/08/09补充JSON/YAML输出模板后，输出格式维度从15.9提升至17.0(+1.1)
- B8为11场景C补充复盘输出模板后，输出精确性持续提升

**实践建议**：
- 审查类输出：JSON `{summary, issues, score, recommendation}`
- 配置类输出：YAML (Pipeline/告警规则/部署配置)
- 文档类输出：Markdown模板 + 必含要素 + 禁止项
- 报告类输出：结构化字段 + 分级标准 + 修复建议

## 原则3：CoT是复杂分析必要条件

**核心观点**：推理深度>3的场景必须添加思维链(Chain-of-Thought)指令。

**调研依据**：
- RSH-INIT-01中DAIR.AI CoT详解：CoT使LLM在回答前先"思考"，显著提升复杂推理准确率
- Google研究表明：CoT对需要多步推理的任务有最显著效果

**迭代验证**：
- B6(推理模式)为04/08/09添加CoT指令后，推理模式维度从10.4提升至14.5(+4.1)
- B9为03/06/07/10补充CoT指令后，推理模式维度继续提升至15.2

**实践建议**：
- 审查分析场景：逐步分析(理解意图→识别问题→评估严重度→提供修复)
- 安全审计场景：攻击者思维(识别攻击面→STRIDE评估→构建攻击链→纵深防御)
- 性能优化场景：方法论驱动(建立基线→识别瓶颈→假设验证→优化实施→效果确认)
- 架构评审场景：自纠错检查(非功能需求/单点故障/扩展性/成本)

## 原则4：Few-shot格式>标签正确

**核心观点**：示例格式一致性比内容正确性更重要。Few-shot的格式模板作用大于知识传授作用。

**调研依据**：
- RSH-INIT-01中DAIR.AI Few-shot详解：格式一致性是Few-shot有效的关键
- 论文"Fantastically Ordered Prompts"证明：示例顺序和格式对性能影响巨大

**迭代验证**：
- B1为03场景A补充Few-shot示例(用户注册功能完整代码+3类测试)，推理模式维度+4
- B8为10场景D补充Few-shot示例(项目结构+常见问题TOP10)，结构完整性+3

**实践建议**：
- 每个Few-shot示例必须包含：输入格式 → 推理过程 → 输出格式
- 示例数量：3-5个最佳（1正例+1边界+1异常）
- 格式要求：所有示例使用相同的格式模板，即使领域不同

## 原则5：Self-Correction+外部工具

**核心观点**：纯LLM自纠错不够，必须结合lint/scan/test等外部工具验证。

**调研依据**：
- RSH-B7-1中Self-Correction模式强调：自纠错需要外部验证信号
- ReAct模式本质：LLM推理+工具执行循环

**迭代验证**：
- B7迭代41为05场景B添加Self-Correction+工具验证(覆盖率自检+边界补全+异常补全+P0验证+工具验证)
- B7迭代37为04场景A添加ReAct模式(Thought→Action→Observation→Fix循环)

**实践建议**：
- 自纠错指令模板：`完成后自检：[检查项1]/[检查项2]/... → 如发现问题则修正 → 使用[工具名]验证`
- 必须指定具体验证工具：lint(代码)/scan(安全)/test(功能)/bench(性能)
- 验证循环：生成→自检→修正→工具验证→确认

## 原则6：可衡量才可优化

**核心观点**：建立量化指标+基线+评估闭环，否则优化是盲目的。

**调研依据**：
- RSH-INIT-03工业框架强调评估闭环的重要性
- _evaluations/evaluation_framework.md定义4项核心指标

**迭代验证**：
- B9迭代57执行六维度二次全量评估，确认全体系均分85.3→92.8(+7.5)
- B10迭代58执行第三次全量评估，确认最终均分92.8→96.0(+3.2)

**实践建议**：
- 建立基线：修改前必须记录当前分数
- 量化指标：六维度评估(结构/约束/角色/输出/清单/推理)，0-20分制
- 评估闭环：评估→分析差距→针对性优化→再评估
- 收敛判定：连续3次达标+维度标准差≤1.5

## 原则7：Prompt Chaining>巨型Prompt

**核心观点**：复杂任务拆子任务链，单一职责+输入输出契约，优于单个巨型Prompt。

**调研依据**：
- RSH-INIT-01中Prompt Chaining详解：链式提示词提高可维护性和可调试性
- RSH-B7-1中Prompt Chaining最佳实践：子任务间通过输入输出契约连接

**迭代验证**：
- B7迭代39为09场景B添加Prompt Chaining(瓶颈定位→根因分析→优化方案→验证确认4子任务链)
- _workflows/定义4条链式工作流：review_fix_verify/requirement_design_coding/deploy_monitor_security/perf_optimize_verify

**实践建议**：
- 子任务粒度：每个子任务对应1个明确的输入→输出转换
- 契约定义：使用_interfaces/目录的YAML Schema定义输入输出接口
- 链式编排：使用_workflows/目录的YAML定义执行顺序和传递规则
- 错误处理：每个子任务必须定义失败时的回退策略

---

## 原则8：版本管理不可少

**核心观点**：语义化版本+CHANGELOG+迭代追溯，三者缺一不可。

**调研依据**：
- 工业界标准：SemVer + Keep a Changelog 是成熟项目的标配
- RSH-INIT-03工业框架强调可追溯性

**迭代验证**：
- v3.0.0建立语义化版本管理，v3.1.0-v3.7.0记录全部变更
- _iterations/traces/记录B1-B10共10批次64次迭代追溯

**实践建议**：
- 版本号：vX.Y.Z（X=体系架构变更/Y=场景模板变更/Z=格式修正）
- CHANGELOG：按Keep a Changelog格式记录Added/Changed/Fixed
- 迭代追溯：四元组(迭代ID, 目标文档, 变更内容, 分数变化)
- 版本联动：核心文档Major变更时评估受影响文档
