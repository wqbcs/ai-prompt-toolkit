## 一、调研-迭代-沉淀螺旋闭环

```
    ┌──────────────────────────────────┐
    │                                  │
    ▼                                  │
 调研 ──→ 迭代 ──→ 沉淀 ──→ 评估 ──┘
(R)      (I)      (S)      (E)
```

### 1.1 调研阶段(R)

**目标**：发现当前体系的短板和行业最佳实践

**输入**：
- 当前评估基线数据
- 行业权威源（DAIR.AI / LangChain / Learn Prompting / Anthropic / OpenAI）

**输出**：
- 调研报告（RSH-XX-XX_主题.md）
- 最佳实践清单
- 反模式清单

**执行标准**：
- 每个批次开始前至少完成1次调研
- 调研源≥3个
- 调研结论必须可操作（具体到可添加的指令/示例/约束）

### 1.2 迭代阶段(I)

**目标**：将调研发现转化为具体修改

**输入**：
- 调研报告
- 当前提示词文档
- 评估基线

**输出**：
- 修改后的提示词文档
- 迭代追溯记录（trace JSON）
- 分数变化记录

**执行标准**：
- 每次迭代修改1个文档1个场景的1个维度
- 迭代前记录input_snapshot，迭代后记录output_snapshot
- 每次迭代必须量化分数变化

### 1.3 沉淀阶段(S)

**目标**：从迭代中提炼可复用的设计原则和反模式

**输入**：
- 批次迭代追溯记录
- 分数变化趋势

**输出**：
- 设计原则（design_principles.md）
- 反模式清单（anti_patterns.md）
- 评估框架更新（evaluation_framework.md）

**执行标准**：
- 每个批次结束至少提炼1条设计原则
- 反模式必须附具体修复方案
- 设计原则必须附迭代验证数据

### 1.4 评估阶段(E)

**目标**：量化迭代效果，判定收敛

**输入**：
- 修改后的提示词文档
- 上次评估基线

**输出**：
- 评估报告
- 收敛状态更新

**执行标准**：
- 按六维度评估框架执行
- 与基线对比计算提升
- 更新convergence_status

## 二、迭代标准8步执行流程

每次迭代必须严格按以下8步执行：

```
Step 1: 确定目标 ──→ 选择待修改的文档+场景+维度
Step 2: 记录现状 ──→ 记录input_snapshot(当前内容摘要)
Step 3: 调研参考 ──→ 查阅调研报告和最佳实践
Step 4: 设计修改 ──→ 确定具体修改内容和预期效果
Step 5: 执行修改 ──→ 修改提示词文档
Step 6: 记录结果 ──→ 记录output_snapshot(修改后内容摘要)
Step 7: 评估分数 ──→ 估算维度分数变化
Step 8: 记录追溯 ──→ 写入trace JSON的四元组
```

### 追溯四元组规范

```json
{
  "id": "迭代编号(1-64)",
  "target": "目标文档.场景",
  "change": "具体修改内容描述",
  "delta": {"维度名": 分数变化值},
  "trace": ["关联文件路径"]
}
```

## 三、批次管理策略

### 3.1 批次划分原则

| 阶段 | 批次 | 策略 | 说明 |
|------|------|------|------|
| 专项优化 | B1-B6 | 单维度聚焦 | 每批次聚焦1个维度，逐文档逐场景优化 |
| 融合提升 | B7-B8 | 跨维度综合 | 融合多种推理模式，综合质量提升 |
| 收敛固化 | B9-B10 | 全量评估+修补 | 二次/三次全量评估，修补短板，固化成果 |

### 3.2 批次规模

- 专项优化阶段：6次迭代/批次（每个维度2轮×3文档）
- 融合提升阶段：7次迭代/批次（综合优化+评估）
- 收敛固化阶段：7次迭代/批次（评估+修补+固化）

### 3.3 批次内优先级

1. 最低分维度优先
2. 最低分文档优先
3. 最低分场景优先
4. 高影响修改优先（1处修改提升多个维度）

## 四、追溯四元组记录规范

### 4.1 四元组定义

```
T = (iteration_id, target, change, delta)
```

- **iteration_id**：整数1-64，全局唯一
- **target**：格式为"文档名:场景名"或"全体系"
- **change**：自然语言描述修改内容和原因
- **delta**：JSON对象，键为维度名，值为分数变化（正数表示提升）

### 4.2 存储规范

- 文件路径：`_iterations/traces/B{N}_trace.json`
- 文件格式：JSON，UTF-8编码
- 结构：`{batch, theme, dimension, iterations: [T1, T2, ...]}`
- 每个批次1个文件

### 4.3 全局状态维护

- 文件路径：`_iterations/iteration_state.json`
- 必须维护的字段：
  - `version`：当前体系版本号
  - `completed_iterations`：已完成迭代次数
  - `current_batch`：当前批次编号
  - `batches`：各批次完成状态
  - `convergence_status`：各维度收敛状态
  - `evaluation_summary`：评估摘要统计

### 4.4 CHANGELOG同步

- 每个批次完成后更新CHANGELOG.md
- 版本号遵循语义化版本：
  - Major(X)：体系架构级变更
  - Minor(Y)：场景模板新增/修改
  - Patch(Z)：格式修正/小修补
- 按Keep a Changelog格式记录Added/Changed/Fixed
