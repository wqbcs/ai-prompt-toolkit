# 提示词反模式清单

> **文档版本**：v1.0  
> **日期**：2026-05-28  
> **来源**：基于64次迭代中发现的常见问题提炼

---

## 反模式1：自由文本输出无格式约束

**问题描述**：场景模板仅指定"输出XXX"，未指定输出格式（JSON/YAML/Markdown模板）。

**危害**：
- LLM输出格式不可预测，难以自动化处理
- 不同模型输出格式差异大，无法对接下游工具
- 人工review效率低，需要逐段阅读

**迭代发现**：
- 基线评估中06_CI/CD、10_文档沉淀多场景存在此问题
- B4迭代19-24为04/06/07/08/09补充JSON/YAML输出模板后解决

**修复方案**：
- 审查类场景：指定JSON结构 `{summary, issues, score, recommendation}`
- 配置类场景：指定YAML格式
- 文档类场景：指定Markdown模板 + 必含要素 + 禁止项
- 添加输出格式示例（至少1个完整示例）

## 反模式2：角色定义过简

**问题描述**：角色仅包含身份和简单能力描述，缺少经验年限、专业领域、工作方式。

**典型反模式**：
```
你是一名代码审查专家。请审查以下代码...
```

**危害**：
- LLM无法准确定位专业深度，可能给出入门级建议
- 缺少工作方式描述，LLM无法模拟专家的工作流程
- 不同场景下同一角色表现不一致

**迭代发现**：
- 基线评估中所有12号文档均缺少"工作方式"描述
- 12_AI时代角色定义最简略(11分)，仅"AI安全专家"

**修复方案**：
- 角色定义4要素：经验年限 + 专业领域 + 核心能力 + 工作方式
- 示例：`你是一名拥有15年经验的代码审查专家，擅长Java/Python/Go多语言审查。你的工作方式：先理解架构上下文→逐模块审查→识别系统性问题→提供优先级排序的修复方案`

## 反模式3：约束条件隐含

**问题描述**：安全/性能/合规约束未显式声明，依赖LLM自行推断。

**危害**：
- LLM可能忽略安全约束，生成有漏洞的代码
- 性能约束缺失导致输出过于笼统，无法落地
- 合规约束缺失在金融/医疗等场景有法律风险

**迭代发现**：
- 基线评估中约束条件完备性维度均分仅13.6，排名倒数第二
- 04_代码审查缺少性能审查约束(如N+1/连接池/GC)
- 06_CI/CD缺少合规审查约束和回滚完整性约束

**修复方案**：
- 约束必须覆盖4维度：技术约束 + 业务约束 + 安全约束 + 性能约束
- 每个维度至少2条显式声明
- 使用表格或列表格式，避免隐含在段落中

## 反模式4：检查清单缺失或过简

**问题描述**：检查清单少于5项，或仅列出大类未细化具体检查点。

**危害**：
- 审查/验收流程形同虚设，关键风险点遗漏
- 不同人执行标准不一致
- 无法作为自动化检查的输入

**迭代发现**：
- 基线评估中03_编码规范检查清单缺"AI生成代码专项检查项"
- 06_CI/CD缺"流水线健康检查"和"合规检查项"
- 07_监控运维缺"混沌工程专项检查"

**修复方案**：
- 检查清单最少8项，理想12-20项
- 必须按维度分组（如：安全/正确性/性能/可维护性）
- 每项包含：检查点 + 检查方法 + 风险等级
- 复杂领域使用分层检查（L1快速/L2标准/L3深度/L4专家/L5合规）

## 反模式5：无推理模式适配

**问题描述**：复杂分析/审查场景缺少CoT/Few-shot/自纠错等推理模式标注。

**危害**：
- LLM直接输出结论，缺少推理过程，准确率低
- 复杂分析场景无法分解为可验证的步骤
- 无法利用推理模式提升特定场景性能

**迭代发现**：
- 基线评估中推理模式适配性维度均分仅10.4，为6维度最低
- 01/03/05/06/07/09/10/11均无任何推理模式标注

**修复方案**：
- 推理深度>3的场景必须添加CoT指令
- 有标准流程的场景添加Few-shot示例
- 有验证工具的场景添加Self-Correction+工具验证
- 使用HTML注释块统一标注：`<!-- CoT:描述 -->`

## 反模式6：场景模板缺5要素

**问题描述**：场景模板缺少描述/输入/输出/检查清单/验收标准5要素结构。

**危害**：
- 场景边界不清，输入输出模糊
- 无法自动化验证场景输出质量
- 新用户难以理解场景适用条件

**迭代发现**：
- 基线评估中结构完整性维度均分仅13.9
- 大部分场景仅有任务列表，缺显式5要素结构

**修复方案**：
- 每个场景必须包含5要素结构表：
  - 场景描述：1-2句话说明场景用途
  - 输入要素：必需输入 + 可选输入
  - 输出格式：结构化格式 + 示例
  - 检查清单：至少8项
  - 验收标准：可量化的通过条件

## 反模式7：无迭代追溯

**问题描述**：修改提示词后无记录——改了什么/为什么改/效果如何。

**危害**：
- 无法回溯变更历史，出问题时无法定位
- 重复犯相同错误
- 无法量化优化效果

**迭代发现**：
- v3.0.0之前无迭代追溯机制
- B1-B10批次建立追溯后，每次修改可追踪

**修复方案**：
- 追溯四元组：(迭代ID, 目标文档, 变更内容, 分数变化)
- 使用JSON格式存储在_iterations/traces/目录
- CHANGELOG同步记录面向用户的变更
- iteration_state.json维护全局迭代状态

---

## 反模式8：提示词过长无结构

**问题描述**：提示词超过2000字但无分节/标题/注释等结构化标记。

**危害**：
- LLM难以定位关键指令，注意力稀释
- 维护困难，修改一处可能影响多处
- 不同部分优先级不清

**迭代发现**：
- 04_代码审查、08_安全审计文档较长，但已有分节结构
- 12_AI时代在B8深化后内容增加，但通过表格化保持结构

**修复方案**：
- 超过2000字的提示词必须分节：## 一级标题 / ### 二级标题
- 使用Markdown表格替代长段落
- 关键指令使用`**加粗**`或`> 引用块`高亮
- 场景模板使用5要素结构表组织
- 约束条件使用编号列表或表格
