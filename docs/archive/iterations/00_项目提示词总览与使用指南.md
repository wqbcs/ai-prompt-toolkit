## 四、通用规范（所有文档通用约定）

1. **占位符格式**：`[占位符名称]` — 使用前替换为实际内容
2. **可选项标记**：`(可选)` 标注的章节可根据需要裁剪
3. **技术栈无关**：文档尽量保持技术栈中立，特定技术栈建议放在 `项目上下文` 中提供
4. **分级输出**：所有建议/问题按 P0（致命）→ P1（严重）→ P2（一般）→ P3（轻微）排序
5. **项目上下文文件**：建议将项目基本信息写入 `_project_context.md`，供所有文档引用
6. **术语统一**：术语定义以 `_glossary.md` 为准，所有文档引用的术语含义与该文件保持一致
7. **输出级别标注**：所有场景模板均已标注输出级别（L1/L2/L3），详见下方"输出规范总览"

## 4.5 输出规范总览

### 输出级别定义

| 级别 | 名称 | 格式要求 | 适用场景 |
|------|------|----------|----------|
| **L1** | 结构化输出 | JSON/YAML Schema 定义，字段名+类型+必填性+取值范围+语义说明 | 代码审查、CI/CD、监控告警、安全审计、性能压测等需要机器解析的场景 |
| **L2** | 半结构化输出 | Markdown 表格 + 有序列表 + 结构化段落 | 架构设计、测试计划、安全加固方案、合规差距分析等半结构化场景 |
| **L3** | 自然语言输出 | 受限自然语言（限定领域术语 + 必含要素清单） | 需求分析、项目管理、文档编写、Bug修复描述等自然语言场景 |

### Schema文件索引

| `06_cicd_pipeline_output.schema.json` | 06_CI/CD | 场景A（流水线构建）、场景C（Docker/K8s部署） | CI/CD流水线配置结构化输出，含阶段、触发条件、质量门禁、密钥管理、回滚策略 |

| `09_performance_benchmark_output.schema.json` | 09_性能优化 | 场景A（性能评估与压测） | 性能压测结果结构化输出，含压测场景、性能指标（P50/P95/P99/QPS/错误率）、瓶颈分析、上线建议 |

### 语义一致性约定

为确保跨文档输出的语义一致性，所有Schema和L2级输出遵循以下字段命名约定：

| 语义 | 统一字段名 | 类型 | 使用范围 |
|------|-----------|------|----------|
| 问题严重级别 | `severity` | enum: P0/P1/P2/P3 | 04_审查、08_安全、07_告警 |
| 问题位置 | `location` | object{filePath, startLine, endLine} | 04_审查、08_安全 |
| 修复方案 | `fixSuggestion` | object{description, codeSnippet} | 04_审查、08_安全 |
| 质量评分 | `qualityScore` | enum: A/B/C/D | 04_审查、09_压测 |
| 上线建议 | `releaseRecommendation` | enum/string | 04_审查、09_压测 |
| 服务名称 | `serviceName` | string | 07_告警、08_安全 |

## 六、快速开始

### 新手快速通道（5 分钟上手）

新手不需要读完所有文档。按以下步骤即可开始使用：

**Step 1：确定当前阶段**

| 刚有产品想法 | `01_需求分析` → 场景 A |

| 准备上线 | `06_CI_CD` + `07_监控运维` |
| 项目已上线 | `08_安全合规` + `09_性能优化` |
| 写文档或复盘 | `10_文档沉淀` + `11_项目管理` |

**Step 2：找到场景模板**


**Step 3：填写占位符**

模板中的 `[内容]` 占位符替换为你的实际信息。

### 工作流接口转换规范

每个工作流YAML文件包含：
- **chain**：文档链路标识（如 `04→03→05`）
- **steps**：每步的document/action/interface_mapping
- **transformation_rules**：步骤间的接口转换规则（字段映射+类型转换+生成规则）
- **validation**：工作流完成验证条件

v2.0.0版本的工作流(review_fix_verify/requirement_design_coding)新增了transformation_rules，细化了接口转换规则：
- **字段映射**：源字段→目标字段的精确映射和转换函数
- **测试生成规则**：修复→测试的自动生成规则（回归/边界/异常/并发）
- **架构约束映射**：PRD→架构约束→编码规范的链式映射
- **编码规范映射**：架构选择→编码规则的派生规则

### 行业专用工作流

## 附录 B：提示词使用技巧

### B.1 通用技巧

1. **System Prompt 模式**：将全文粘贴到 AI 的 System Prompt，作为角色设定
2. **Task Prompt 模式**：复制对应场景的提示词模板，填入项目上下文，作为 Task 提交
3. **分步执行**：不要一次性要求 AI 完成所有步骤，按场景 A→B→C 逐步执行
4. **上下文携带**：每轮对话带上已产出的文档内容，保证连贯性
5. **迭代验证**：AI 输出后，用本节的「验收标准清单」逐项核对

### B.2 不同 AI 模型的适配策略

不同模型对提示词的响应模式存在差异，以下适配策略可提升输出质量：

| 模型类型 | 特点 | 推荐策略 | 不推荐的用法 |
|----------|------|----------|-------------|
| DeepSeek / Claude | 长上下文、擅长分步推理 | 全文 System Prompt + 分步 Task；CoT 效果显著 | 单次 Prompt 塞入过多并行任务 |
| GPT-4o / GPT-4 | 指令跟随能力强 | 结构化输出要求（JSON/Markdown 表格）；明确输出格式 | 模糊的「请分析一下」（需指定分析维度） |
| Gemini / Qwen | 中文理解好，但需明确边界 | 中文 Prompt 效果最佳；需明确「不需要做什么」 | 单一指令未带否定约束（易产生无用内容） |
| GitHub Copilot / Cursor | 行内补全为主 | 注释 + 类型签名引导；文件级上下文优于对话 | 长对话历史（截断后会失去上下文） |
| 代码审查类 (CodeRabbit 等) | 自动化 PR 审查 | 配合 `04_审查保障` 的审查清单一起使用 | 单独依赖 AI 审查（人类确认不可替代） |

### B.3 不同场景的最佳模式

| 场景 | 推荐模式 | 说明 |
|------|----------|------|
| 新建项目，需要完整架构设计 | System Prompt 模式 | 将 `02_架构设计` 全文设为 System Prompt |
| 审查一段具体代码 | Task Prompt 模式 | 复制 `04_审查保障` 的场景 A，粘贴代码 |
| 迁移代码语言（Python → Rust） | System Prompt + Task 组合 | System 设角色锚定，Task 描述具体转换项 |
| 排查线上故障 | Task Prompt 模式 + 实时数据 | 复制 `07_监控运维` 的场景 A，附上日志 |
| 编写 PRD | System Prompt 模式 | 将 `01_需求分析` 全文设为 System Prompt |

## 附录 C：进阶用法 — 多文档链式组合

对于复杂场景，可以串联多个提示词文档，形成端到端工作流。

### 常用链式工作流

```
场景：新功能从零到上线
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 01_需求  │ →  │ 02_架构  │ →  │ 03_编码  │ →  │ 04_审查  │ →  │ 06_CI/CD │
│  分析     │    │  设计     │    │  规范     │    │  保障     │    │  部署     │
│ (场景 A)  │    │ (场景 B)  │    │ (场景 A)  │    │ (场景 B)  │    │ (场景 A)  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

### 关键链式模式

| 工作流 | 文档链 | 关键交接点 | 适用场景 |
|--------|--------|-----------|----------|
| 功能全流程 | 01(A) → 02(B) → 03(A) → 04(B) → 06(A) | 需求文档传递给架构师；架构设计约束编码规范 | 全新功能开发 |
| 安全加固 | 08 → 04(C) → 03(修复) | 安全审计结果驱动审查清单；审查清单驱动编码修复 | 安全合规整改 |
| 性能优化 | 09 → 05(B) → 02(评估) → 03(优化) | 压测结果定位瓶颈；架构评估决定优化方向 | 性能瓶颈排查 |
| 线上故障排查 | 07(A) → 04(根因) → 03(修复) → 06(热修复) | 监控告警驱动根因分析；修复方案需审查后部署 | 线上事故响应 |
| 项目复盘 | 11 → 10(存档) → 01(迭代规划) | 复盘报告驱动下一轮迭代需求 | 迭代结束 |

### 使用技巧

1. **携带前序产物**：每步完成后，将前一步的产出文档摘要粘贴到下一步的 Prompt 开头
2. **角色切换**：不同步骤可能使用不同的 AI 角色（架构师 → 开发者 → 审查者），需切换 System Prompt
3. **增量输入**：不要每步都重复完整的上下文，仅携带关键输出摘要即可
4. **分离环境**：建议在独立的对话窗口中进行不同步骤，避免上下文污染

| **Major (X)** | 体系架构级变更 | 新增必含章节、改变文档结构规范、删除核心场景 | 全体系文档需评估联动 |
| **Minor (Y)** | 文档级功能变更 | 新增场景模板、优化提示词内容、补充输出规范章节 | 当前文档 + 直接下游依赖文档 |
| **Patch (Z)** | 修正性变更 | 修复术语不一致、修正格式偏差、补充遗漏字段 | 仅当前文档 |

### 9.2 核心文档 Major 变更时的受影响文档评估规则

当核心文档（01-12）发生 Major 变更时，按以下规则评估受影响文档：

1. **直接依赖文档**（文档依赖关系表中明确声明的下游）→ 必须同步评估，Minor+1
2. **间接依赖文档**（通过中间文档产生依赖）→ 评估是否受影响，如受影响则 Patch+1
3. **支撑文件**（_glossary、_project_context）→ 仅当新增/删除术语或项目上下文字段时 Patch+1
4. **独立补充文档**→ 仅当被核心文档显式引用且引用接口变更时 Patch+1
5. **00_总览**→ 任何核心文档 Major 变更均触发总览 Major+1

**评估流程**：
```
核心文档 Major 变更
  → 检查文档依赖关系表，识别直接依赖
  → 直接依赖文档 → Minor+1（同步适配）
  → 间接依赖文档 → 评估影响 → 有影响则 Patch+1
  → 00_总览 → Major+1
  → 更新 CHANGELOG.md
```
