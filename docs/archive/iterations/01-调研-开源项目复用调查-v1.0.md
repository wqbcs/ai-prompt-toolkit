## 1. promptfoo — Prompt测试与Red Teaming框架

| 属性 | 详情 |
|------|------|
| **名称** | promptfoo |
| **URL** | https://github.com/promptfoo/promptfooG |
| **Stars** | 23.7k |
| **版本** | npm最新（PyPI wrapper 0.1.4，2026-04-06） |
| **许可证** | MIT |
| **语言** | TypeScript (Node.js 20+) |
| **所属** | 已加入OpenAI，仍保持开源 |

### 核心功能
- **Prompt评估**：声明式YAML配置，对比多个模型（GPT/Claude/Gemini/DeepSeek等）的输出质量
- **Red Teaming**：内置漏洞扫描，生成安全报告，覆盖prompt injection/jailbreak/PII泄露等
- **CI3D集成**：CLI + Web Viewer + CI/CD自动化检查
- **Code Scanning**：GitHub PR自动审查LLM安全合规
- **Self-grading**：LLM-as-judge自动评分

### 关键Red Team Probe类型
- `prompt-injection` — 提示注入攻击
- `jailbreak` — 越狱攻击（DAN/Goodside/Grandma等）
- `harmful` — 有害内容生成
- `pii` — 个人信息泄露
- `contracts` — 合规性检查
- `hijacking` — 对话劫持
- `overreliance` — 过度依赖
- `competitors` — 竞品提及

### 评估指标体系
- **模型graded**：LLM-as-judge评分（0-1分 + 原因解释）
- **自定义断言**：Python/JS函数断言
- **内置指标**：exact match, regex, contains, similarity, latency, cost
- **聚合报告**：多模型多prompt矩阵对比

### 与 ai-prompt-toolkit 复用方向
1. **评估指标体系** → 复用其声明式YAML配置模式 + LLM-as-judge评分框架
2. **Red Team Probe** → 直接复用其probe类型定义，适配为Go版本的安全扫描器
3. **CI/CD集成模式** → 参考其GitHub Action实现，做CodeArts Pipeline集成
4. **Web Viewer** → 参考其评估矩阵可视化设计
5. **痛点**：仅支持TypeScript/Node.js，Python wrapper性能差；需要Go原生实现

## 3. DSPy — Prompt编程框架（Stanford NLP）

| 属性 | 详情 |
|------|------|
| **名称** | DSPy |
| **URL** | https://github.com/stanfordnlp/dspy |
| **Stars** | 36.4k |
| **许可证** | MIT |
| **语言** | Python |
| **所属** | Stanford NLP |

### 核心功能
- **编程而非提示**：用Python代码替代脆弱的prompt字符串
- **Module系统**：可组合的AI系统模块（Signature → Module → Program）
- **自动优化器（Optimizer/Compiler）**：自动搜索最优prompt和few-shot示例
- **Assertion/Suggest**：计算约束 + 自我修正

### 优化器/编译器设计
| 优化器 | 描述 |
|--------|------|
| `BootstrapFewShot` | 少样本自举优化 |
| `BootstrapFewShotWithRandomSearch` | 随机搜索 + 少样本 |
| `MIPROv2` | Multi-Proposal优化（指令+示例联合优化） |
| `BetterTogether` | Prompt优化 + 微调联合 |
| `GEPA` | 反射式Prompt进化（2025年新，号称超越RL） |

### 关键设计模式
- **Signature**：声明式输入→输出类型定义
- **Module**：可组合的变换（类比nn.Module）
- **Program**：Module的编排（Pipeline/Agent）
- **Teleprompter**：优化器基类，在训练集上编译Program
- **Assert/Suggest**：硬/软约束，失败时自动重试修正

### 与 ai-prompt-toolkit 复用方向
1. **Signature模式** → 参考其声明式输入/输出类型定义，设计Go版本的Prompt Schema
2. **Optimizer架构** → 复用MIPROv2/GEPA的prompt自动优化思想，实现prompt版本自动调优
3. **Module组合** → 参考其可组合Pipeline设计，实现prompt chain编排
4. **Assertion机制** → 复用其约束+自修正模式，做prompt输出的质量守卫
5. **痛点**：学习曲线陡峭、Python生态绑定、优化过程不可观测

## 关键痛点汇总

1. **语言绑定**：所有项目都是Python/TypeScript，缺乏Go原生实现
2. **评估速度**：每个metric需独立LLM调用，大规模评估极慢
3. **不可观测**：prompt优化过程（如DSPy compile）缺乏实时监控
4. **安全+评估割裂**：promptfoo做评估+安全，但与Langfuse/DeepEval的tracing/指标体系未打通
5. **MCP评估空白**：仅有DeepEval刚起步，其他项目均未支持
6. **华为云生态**：开源项目均未适配昇腾NPU和ModelArts
7. **llm-guard归档**：安全scanner领域出现真空，需要新项目填补
8. **多Turn评估不足**：除DeepEval外，多数框架只支持单Turn评估

---

## ai-prompt-toolkit 差异化方向建议

1. **Go原生实现** — 唯一用Go实现的prompt评估+安全框架，填补生态空白
2. **评估+安全+可观测三位一体** — 打通promptfoo(评估+安全) + Langfuse(可观测)的能力
3. **MCP评估先行** — 率先支持MCP Server/Tool的评估指标
4. **昇腾NPU原生支持** — 对接ModelArts/MaaS，华为云生态独家优势
5. **并行评估加速** — 利用Go并发特性，并行执行多个metric评估
6. **Multi-Turn+Agentic评估** — 对标DeepEval的agent指标体系
7. **Prompt自动优化** — 参考DSPy GEPA，实现Go版prompt进化优化器
