# 提示词设计原则 v2.0

> **文档版本**：v2.0
> **日期**：2026-05-29
> **来源**：基于三轮迭代(128次总计)提炼，从8条扩展到12条

---

## 原则1：Context Engineering优先

**核心观点**：架构完整上下文(System/Instruction/User/Tools/RAG)比调优文本更重要。

**迭代验证**：
- B3迭代为05/07/10补充工作方式后，角色设定维度+1.9
- C5嵌入OWASP/STRIDE/USL等专家知识后，准确率+4.5

**实践建议**：
- 角色定义必须包含：经验年限 + 专业领域 + 核心能力 + 工作方式
- 系统约束必须覆盖：技术 + 业务 + 安全 + 性能 四维度
- 工具声明必须包含：工具名 + 用途 + 使用时机 + 输出格式

## 原则2：结构化输出强制

**核心观点**：所有分析/审查类场景必须指定JSON/YAML输出格式。

**迭代验证**：
- B4补充JSON/YAML输出模板后，输出格式维度+1.1
- C6为全体系L1场景添加结构化输出指令后，结构合规率+3.0
- C10 Qwen JSON模式适配后，Schema合规率82%→95%

**实践建议**：
- 审查类输出：JSON `{summary, issues, score, recommendation}`
- 配置类输出：YAML (Pipeline/告警规则/部署配置)
- 文档类输出：Markdown模板 + 必含要素 + 禁止项

## 原则3：CoT是复杂分析必要条件

**核心观点**：推理深度>3的场景必须添加思维链(Chain-of-Thought)指令。

**迭代验证**：
- B6为04/08/09添加CoT指令后，推理模式维度+4.1
- C10 DeepSeek CoT+自纠错组合后，推理深度利用85→93

**实践建议**：
- 审查分析：逐步分析(理解→识别→评估→修复)
- 安全审计：攻击者思维(攻击面→STRIDE→攻击链→纵深防御)
- 性能优化：方法论驱动(基线→瓶颈→验证→优化→确认)

---

## 原则4：Few-shot格式>标签正确

**核心观点**：示例格式一致性比内容正确性更重要。

**迭代验证**：
- B1为03场景A补充Few-shot示例，推理模式维度+4
- B8为10场景D补充Few-shot示例，结构完整性+3

**实践建议**：
- 每个Few-shot示例：输入格式 → 推理过程 → 输出格式
- 示例数量：3-5个最佳（1正例+1边界+1异常）
- 格式要求：所有示例使用相同的格式模板

---

## 原则5：Self-Correction+外部工具

**核心观点**：纯LLM自纠错不够，必须结合lint/scan/test等外部工具验证。

**迭代验证**：
- B7为05/04添加Self-Correction+工具验证
- C10 DeepSeek CoT+自纠错组合：5步推理+4项自检+工具验证

**实践建议**：
- 自纠错指令模板：`完成后自检：[检查项] → 修正 → 使用[工具]验证`
- 验证循环：生成→自检→修正→工具验证→确认

---

## 原则6：可衡量才可优化

**核心观点**：建立量化指标+基线+评估闭环，否则优化是盲目的。

**迭代验证**：
- B9-B10执行六维度二次/三次全量评估
- C1建立八维度评估框架，C11引入LLM-as-Judge自动化评估
- 四次全量评估：80.5→85.8→89.2→92.5→96.5

**实践建议**：
- 建立基线：修改前必须记录当前分数
- 量化指标：八维度评估(6+2行业维度)，0-20分制
- 评估闭环：评估→分析差距→针对性优化→再评估
- 收敛判定：均分≥16 + 标准差≤1.0 + 连续达标

## 原则7：Prompt Chaining>巨型Prompt

**核心观点**：复杂任务拆子任务链，单一职责+输入输出契约。

**迭代验证**：
- B7为09场景B添加Prompt Chaining
- C7新增4条链式工作流+行业专用工作流

**实践建议**：
- 子任务粒度：每个子任务对应1个明确的输入→输出转换
- 契约定义：使用_interfaces/的YAML Schema
- 链式编排：使用_workflows/的YAML

## 原则8：版本管理不可少

**核心观点**：语义化版本+CHANGELOG+迭代追溯，三者缺一不可。

**迭代验证**：
- v3.0.0建立版本管理，v3.1-v5.0.0记录全部变更
- C1-C14追溯记录14批次trace JSON

**实践建议**：
- 版本号：vX.Y.Z（X=体系架构/Y=场景模板/Z=格式修正）
- CHANGELOG：按Keep a Changelog格式
- 追溯：五元组(迭代ID, 目标文档, 变更内容, 分数变化, 批次)

## 原则9：Agent-First优先（第三轮新增）

**核心观点**：对于复杂多步骤任务，优先设计多Agent协作模式而非单一巨型Prompt。

**调研依据**：
- R3-C1-03中Agent-First模式：LLM+工具+记忆+规划
- ReAct/Reflexion/Multi-Agent模式已被工业界验证

**迭代验证**：
- C6为02_架构设计添加4Agent协作(架构分析→技术选型→风险识别→综合评审)
- C12为05/06/07/10添加4组多Agent协作

**实践建议**：
- Agent定义：职责+输入+输出+协作协议
- Agent数量：2-4个最优(>4考虑分层)
- 协作模式：顺序/并行/分层/辩论
- 错误处理：每个Agent定义失败时的回退策略

## 原则10：行业垂直化（第三轮新增）

**核心观点**：通用提示词必须叠加行业专项知识(checklist+glossary+compliance)才能在特定行业达到专业级效果。

**调研依据**：
- 金融/医疗/电商行业有强监管要求，通用模板无法覆盖
- 行业术语/合规/检查清单是行业场景的核心壁垒

**迭代验证**：
- C8新增5行业3件套(checklist+glossary+compliance)，行业覆盖2.1→4.5
- C12新增3个行业专用场景模板(金融代码审查/医疗安全审计/电商性能优化)，行业覆盖4.5→8.0

**实践建议**：
- 行业3件套：checklist(≥10项) + glossary(≥30术语) + compliance(法规+标准)
- 行业与通用集成：P0级必选+P1级推荐
- 行业专用工作流：叠加行业约束的链式工作流
- 行业验收标准：行业法规对齐+行业风险覆盖

## 原则11：可评估性（第三轮新增）

**核心观点**：每个优化假设必须可通过A/B测试或LLM-as-Judge验证，否则是伪优化。

**调研依据**：
- R3-C1-01 LLM-as-Judge最佳实践
- A/B测试是验证提示词效果的黄金标准

**迭代验证**：
- C1建立八维度评估框架+LLM-as-Judge模板
- C11创建36个回归测试用例+5个A/B测试计划
- 四次全量评估验证收敛趋势

**实践建议**：
- LLM-as-Judge：每维度独立Prompt+3次采样+交叉评估
- A/B测试：控制组vs实验组，置信度95%，最小效应量5%
- 回归测试：核心场景≥10个用例/场景，P0全通过
- 收敛判定：均分+标准差+连续达标次数

---

## 原则12：生态开放（第三轮新增）

**核心观点**：提示词体系必须支持多模型适配和社区贡献，封闭体系无法持续演进。

**调研依据**：
- 国产模型各有所长(DeepSeek代码/Qwen中文/ERNIE合规/Kimi长文档)
- 开源社区是提示词工程发展的重要驱动力

**迭代验证**：
- C2创建4个国产模型画像+55场景适配矩阵
- C10深度适配(DeepSeek CoT+自纠错/Qwen JSON模式/Kimi长上下文)
- 7模型×55场景完整适配矩阵v3.0

**实践建议**：
- 模型画像：YAML格式，含能力/优势/劣势/最佳场景
- 适配矩阵：场景×模型适配级别(S/A/B/C)+适配效果评分
- 适配指令：每个模型特有的优化指令模板
- 贡献规范：新模型/新行业/新场景的贡献模板和评审流程
