## 二、核心约束

1. **必须按 P0/P1/P2/P3 分级输出所有问题**：每个审查意见必须明确标注问题级别，不得遗漏任何级别的审查发现。
2. **每个问题必须标注精确文件位置（文件名:行号）**：确保问题可快速定位和复现，禁止使用模糊的位置描述。
3. **P0/P1 问题必须附带具体修复方案（含代码）**：严重及以上问题必须给出可落地的修复代码或详细方案，不得仅描述现象。
4. **P0 问题必须有明确的验证方式**：致命问题必须说明如何验证修复有效，包括测试用例或验证步骤。
5. **审查报告必须包含质量评分（A/B/C/D）和上线建议**：每个审查报告需给出明确的评分结论和上线决策建议。
6. **安全漏洞必须在报告中高亮标注**：所有安全相关的问题必须在报告中显著标注，使用 🔴 或加粗等方式强调。
7. **安全审查约束**：审查必须覆盖OWASP Top 10全量检查项；涉及用户数据/支付/权限的代码必须执行L3安全审查；发现P0安全漏洞必须阻断上线并立即通知安全团队。
8. **性能审查约束**：核心接口必须审查N+1查询和连接池配置；热点代码路径必须审查GC影响和锁竞争；性能退化超过10%的变更必须标注为P1及以上问题。

## 三、审查层级体系

代码审查从浅到深分为 **5 个层级**，可根据时间和资源选择性执行：

| 层级 | 名称 | 审查内容 | 耗时参考 |
|------|------|----------|----------|
| L1 | 规范审查 | 命名 / 格式 / 注释 / 文件结构 | ~10 min |
| L2 | 逻辑审查 | 业务逻辑正确性 / 边界条件 / 异常处理 | ~30 min |
| L3 | 安全审查 | OWASP Top 10 / 数据验证 / 认证授权 | ~20 min |
| L4 | 性能审查 | N+1 查询 / 资源泄漏 / 并发问题 | ~20 min |
| L5 | 架构审查 | 分层合规 / 耦合度 / 扩展性 / 设计模式 | ~30 min |

**【CoT指令：请按以下步骤逐步分析】**
1. **理解代码意图**：先理解代码的业务目的和整体逻辑，明确这段代码要解决什么问题
2. **识别潜在问题**：按安全→逻辑→性能→规范→架构的优先级顺序，逐类扫描潜在问题
3. **评估严重程度**：对每个识别出的问题，根据影响范围（数据/用户/系统/业务）评估P0-P3级别
4. **提供修复方案**：为每个P0/P1问题提供可落地的修复代码，P2/P3提供改进建议

**【Program-of-Thoughts (PoT)指令】**
将推理转化为可执行验证代码，提升审查精确度：
1. **编写验证函数**：对识别的复杂问题（如并发安全、性能瓶颈、算法正确性），编写Python/JS验证代码
2. **执行验证**：运行验证代码获取精确结果（如复杂度计算、边界值枚举、竞态条件模拟）
3. **根据结果调整**：验证失败则修正问题分级和修复方案，验证通过则提高修复方案置信度

PoT适用场景：
- 算法复杂度分析 → 编写计时验证函数确认O(n²) vs O(n log n)
- 并发安全验证 → 编写多线程竞态模拟代码验证数据竞争
- 数值精度问题 → 编写浮点vs Decimal对比验证
- 性能瓶颈量化 → 编写微基准测试确认N+1查询影响

**【ReAct模式指令：每发现一个问题，立即执行以下循环】**
- **Thought**：分析问题的根因和影响范围，推理可能的攻击/故障路径
- **Action**：定位到具体的代码位置（文件:行号），追踪数据流和调用链
- **Observation**：验证该问题是否真实存在，评估对系统/用户/数据的影响
- **Fix**：提供可落地的修复代码和验证方式，确认修复不会引入新问题

## 六、各层级审查清单

### 0.6 领域专家知识嵌入

#### SOLID原则审查清单

| 原则 | 全称 | 审查要点 | 违反示例 | 修正方案 |
|------|------|----------|----------|----------|
| **S** | 单一职责 | 一个类/模块只有一个变更原因 | UserService既管用户又发邮件 | 拆分UserService+EmailService |
| **O** | 开闭原则 | 对扩展开放，对修改关闭 | switch(type)硬编码支付方式 | 策略模式+PaymentStrategy接口 |
| **L** | 里氏替换 | 子类可替换父类而不改变正确性 | Square继承Rectangle但改变行为 | 两者都实现Shape接口而非继承 |
| **I** | 接口隔离 | 客户端不应依赖不需要的接口 | IAnimal含fly()但Dog也需实现 | 拆分IWalkable+IFlyable |
| **D** | 依赖反转 | 高层不依赖低层，都依赖抽象 | OrderService直接new(MySQLOrderRepo) | 注入IOrderRepo接口 |

#### 设计模式反模式检测

| 反模式 | 表现 | 危害 | 正确模式 | 检测方法 |
|--------|------|------|----------|----------|
| **上帝类** | 单个类>500行/职责>3 | 难以理解/测试/修改 | 按职责拆分为多个小类 | 检查类行数+方法数 |
| **过度单例** | 全局状态+Singleton滥用 | 隐式依赖+测试困难 | 依赖注入+Scoped生命周期 | 搜索getInstance/Singleton模式 |
| **回调地狱** | 嵌套>3层回调 | 可读性差+错误处理困难 | async/await+Promise链 | 检查嵌套层数 |
| **过早优化** | 无度量数据就优化 | 浪费时间+代码复杂化 | 先度量→后优化→再验证 | 审查是否有性能注释而无数据 |
| **魔法数字** | 硬编码常量散落代码 | 语义不清+难以维护 | 提取为命名常量/枚举 | 搜索代码中裸数字 |
| **Copy-Paste编程** | 重复代码块>10行 | 修改需多处同步 | 提取公共方法/基类 | 重复度检测(CPD) |
| **异常吞没** | 空catch块 | 问题被隐藏难以排查 | 至少记录日志+适当处理 | 搜索空catch/except pass |

#### Clean Code 10条规则

| # | 规则 | 说明 | 审查标准 |
|---|------|------|----------|
| 1 | 有意义的命名 | 变量/函数/类名揭示意图 | 无a/b/tmp/data等无意义名 |
| 2 | 函数短小精悍 | 每个函数只做一件事 | 函数≤50行，参数≤3个 |
| 3 | 注释解释WHY | 注释说明为什么而非做什么 | 无重复代码的废话注释 |
| 4 | 格式一致 | 团队统一的代码风格 | lint配置通过，零格式错误 |
| 5 | 对象和数据结构 | 对象隐藏数据暴露行为 | 无贫血模型(只有getter/setter) |
| 6 | 错误处理而非异常流 | 用异常处理异常情况 | 异常用于异常，不用于业务分支 |
| 7 | 边界条件处理 | 不信任外部输入 | null/空/越界均有处理 |
| 8 | 无副作用 | 函数不产生意外修改 | 纯函数优先，副作用明确标注 |
| 9 | 避免重复 | DRY原则 | 重复代码提取为共享方法 |
| 10 | 渐进式改进 | 每次提交让代码更好一点 | Boy Scout Rule:离开时比来时更干净 |

### L1 — 规范审查清单

- [ ] 命名规范一致性（PascalCase / camelCase / snake_case）
- [ ] 文件命名与所在模块匹配
- [ ] 导入语句是否规范化（未使用通配符 import）
- [ ] 代码缩进、空格、空行风格一致
- [ ] 注释质量（是否存在冗余注释、过期注释）
- [ ] 魔法数字是否提取为常量
- [ ] 文件长度是否在合理范围内（< 500 行）
- [ ] TODO/FIXME 是否标注了负责人

### L2 — 逻辑审查清单

- [ ] 所有分支条件都被覆盖（if-else / switch 全覆盖）
- [ ] 边界值处理（null / 空集合 / 超过范围 / 特殊字符）
- [ ] 异常处理（是否吞异常 / 是否向上抛原始异常 / 异常信息是否充分）
- [ ] 并发处理（竞态条件 / 死锁 / 原子操作）
- [ ] 状态机转换是否完整（不允许的状态变更被阻止）
- [ ] 数值计算是否有溢出 / 精度问题
- [ ] 时间处理（时区 / 闰秒 / 跨日问题）

### L3 — 安全审查清单

- [ ] SQL 注入防护（使用参数化查询，而非字符串拼接）
- [ ] XSS 防护（输出编码 / CSP 头）
- [ ] CSRF 防护（Token 验证）
- [ ] 身份认证（密码存储使用 bcrypt/argon2）
- [ ] 权限校验（是否每个接口都做了鉴权）
- [ ] 敏感数据加密（传输 TLS + 存储加密）
- [ ] 输入校验（白名单校验而非黑名单）
- [ ] 文件上传校验（类型 / 大小 / 路径穿越防护）
- [ ] 安全配置（CORS / HSTS / 安全头）
- [ ] 日志脱敏（不打印密码 / Token / 身份证）

### L4 — 性能审查清单

- [ ] 数据库 N+1 查询问题
- [ ] 缺少必要的索引
- [ ] 循环内数据库调用
- [ ] 未使用批量操作（批量 insert / batch query）
- [ ] 未使用连接池（数据库 / HTTP / Redis）
- [ ] 大对象 / 大数据集未分页处理
- [ ] 未使用缓存（重复计算 / 重复查询）
- [ ] 不必要的对象创建（GC 压力）
- [ ] 线程 / goroutine 泄漏
- [ ] 锁粒度过大（性能瓶颈）

### L5 — 架构审查清单

- [ ] 模块间依赖方向正确（符合架构设计）
- [ ] 不存在循环依赖
- [ ] 接口抽象级别一致（不暴露底层实现细节）
- [ ] 是否过度设计（引入不需要的抽象）
- [ ] 是否欠设计（业务逻辑散落在各处）
- [ ] 配置与代码分离
- [ ] 可测试性（是否方便 mock / 依赖注入）
- [ ] 可扩展性（新增功能是否需要修改大量代码）
- [ ] 错误处理策略一致（统一错误码 / 全局异常处理）

  l1-lint:
    runs-on: ubuntu-latest

    runs-on: ubuntu-latest

      - uses: actions/checkout@v3
      - run: npm test -- --coverage  # 单元测试+覆盖率

  l3-security:
    runs-on: ubuntu-latest
    steps:
      - run: npx audit  # 依赖安全审计
      - run: trivy fs .  # 文件系统漏洞扫描

    needs: [l1-lint, l2-test, l3-security]
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
        with:
          fetch-depth: 0  # 全量历史

## 八、常见审查盲区与对策

| 盲区 | 表现 | 对策 |
|------|------|------|
| 竞态条件 | 多线程/异步场景下的时序问题 | 专门进行并发审查，审查锁的粒度 |
| 资源泄漏 | 文件/连接/内存未正确释放 | 审查 close() / dispose() 调用点 |
| 类型混淆 | 隐式类型转换导致的 Bug | 启用严格类型检查 |
| 时区处理 | 时间戳/格式化时区错误 | 统一使用 UTC 存储，展示时转换 |
| 浮点精度 | 金融计算中的精度丢失 | 金额计算使用 Decimal/BigDecimal |
| 并发安全 | Map 并发读写 panic | 审查并发容器使用 |
| 边界值遗漏 | 空值/零值/负数未处理 | 要求边界值测试用例 |
| 错误处理不一致 | 部分接口未处理错误 | 审查全局错误处理中间件 |
