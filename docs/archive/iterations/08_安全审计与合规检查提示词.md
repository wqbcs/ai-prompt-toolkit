## 二、核心约束

1. **行业合规要求**：识别并遵循适用的行业法规和标准（如等保2.0、GDPR、PCI-DSS、HIPAA等），确保系统设计和运维满足合规最低要求。
2. **数据分类分级**：依据数据敏感度（公开/内部/敏感/绝密）建立分类分级体系，不同等级数据采取差异化的加密、存储和访问控制策略。
3. **安全基线版本**：所有组件（OS/中间件/库/容器镜像）必须基于经过安全加固的基线版本，定期扫描并修复已知CVE漏洞。
4. **审计频率要求**：全面安全审计每季度至少一次；代码级安全审查随每个迭代进行；基础设施扫描每周自动执行。
5. **漏洞修复 SLA**：P0漏洞 24小时内修复；P1漏洞 7天内修复；P2漏洞 30天内修复；P3漏洞纳入下个迭代计划。
6. **业务连续性约束**：安全加固措施不得导致业务中断超过RTO目标；关键安全变更必须制定业务连续性预案（BCP）；安全事件响应过程必须保障核心业务可用性；定期进行灾难恢复演练（至少每半年一次），验证RTO/RPO达标。
7. **数据保护约束**：个人敏感数据（身份证/银行卡/健康信息）必须加密存储（AES-256）且密钥与数据分离管理；数据传输必须使用TLS 1.2+且禁用弱密码套件；数据删除必须实现逻辑删除+物理删除双策略，满足GDPR"被遗忘权"要求；数据跨境传输必须通过安全评估且获得用户明示同意。

### 4.0.1 STRIDE威胁建模框架

| 威胁类型 | 首字母 | 含义 | 示例 | 对应安全属性 | 检查方法 |
|----------|--------|------|------|-------------|----------|
| **S**poofing | S | 欺骗：冒充其他用户/系统 | 伪造JWT Token访问他人数据 | 认证(Authentication) | 验证身份证明机制 |
| **T**ampering | T | 篡改：未授权修改数据 | 修改订单金额/状态 | 完整性(Integrity) | 验证数据完整性保护(签名/HMAC) |
| **R**epudiation | R | 否认：否认执行了某操作 | 用户否认下单/管理员否认删除 | 不可否认性(Non-repudiation) | 验证审计日志完整性 |
| **I**nformation Disclosure | I | 信息泄露：暴露信息给未授权者 | 日志打印密码/错误页面泄露栈 | 机密性(Confidentiality) | 验证数据分类+脱敏+加密 |
| **D**enial of Service | D | 拒绝服务：使系统不可用 | 大量请求耗尽资源/慢查询 | 可用性(Availability) | 验证限流+熔断+资源配额 |
| **E**levation of Privilege | E | 权限提升：获取更高权限 | 普通用户访问管理接口 | 授权(Authorization) | 验证最小权限+RBAC/ABAC |

### 4.0.2 CVE检索指令

安全审计中发现漏洞时，按以下流程检索和确认CVE：
1. **识别组件**：记录组件名称+精确版本号(如 `fastapi==0.100.0`)
2. **CVE检索**：访问 https://cve.mitre.org 或 https://nvd.nist.gov 搜索组件名+版本
3. **CVSS评分**：获取CVSS v3.1评分，≥7.0为高危，≥9.0为紧急
4. **修复版本**：确认修复该CVE的最低版本号
5. **影响评估**：评估该组件在本项目中的使用方式，是否实际受影响(Reachability Analysis)
6. **修复优先级**：CVSS×可达性×业务影响 → 修复排序

**【CoT指令：请按攻击者思维逐步分析】**
1. **识别攻击面**：列出所有用户输入点（API/表单/上传/命令行）、所有数据出口（日志/响应/文件）、所有信任边界（内部/外部/第三方）
2. **评估每个入口风险**：对每个攻击入口，按STRIDE模型（欺骗/篡改/否认/信息泄露/拒绝服务/权限提升）逐项评估
3. **构建攻击链**：识别可串联的漏洞组合（如：SSRF→内网探测→凭据泄露→横向移动），评估攻击链的可行性和影响
4. **设计防御方案**：按纵深防御原则，为每个攻击路径设计多层防御（输入验证→访问控制→输出编码→监控告警）

**【Active-Prompt指令：基于不确定性优先审查】**
基于不确定性选择最需要审查的模块，提升审查效率：
1. **评估每个模块风险不确定性**：对每个模块/服务评估审查不确定性分数(0-10)
   - 新增代码/首次上线：不确定性9-10
   - 涉及用户数据/支付/权限：不确定性8-9
   - 依赖第三方服务/API：不确定性7-8
   - 近期有变更的模块：不确定性6-7
   - 稳定运行>3个月无变更：不确定性3-5
   - 经过充分测试的成熟模块：不确定性1-3
2. **选择不确定性最高的3个模块**：优先深度审查这些模块
3. **深度审查**：对选中的3个模块执行完整STRIDE分析+攻击链构建+纵深防御设计
4. **其余模块快速审查**：对不确定性较低的模块执行OWASP Top 10快速扫描

Active-Prompt优势：在有限审查时间内，聚焦最高风险区域，避免均匀分配导致高风险遗漏

**【ReAct模式指令：攻击者思维循环】**
- **Thought**：假设攻击路径，推理攻击者如何利用该漏洞实现攻击目标
- **Action**：验证漏洞可达性，检查攻击前提条件是否满足（认证/授权/网络可达）
- **Observation**：确认风险等级，评估实际可利用性和业务影响范围
- **Fix**：设计纵深防御方案，每个攻击路径至少2层防御，验证修复不引入新风险

## 六、生产环境安全基线

### 6.1 HTTP 安全头配置

```
# Nginx 安全头配置示例
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header X-XSS-Protection "1; mode=block" always;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

### 6.2 CORS 安全配置

```
# Nginx CORS 配置
add_header Access-Control-Allow-Origin "https://yourdomain.com" always;  # 不要用 *
add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
add_header Access-Control-Allow-Headers "Authorization, Content-Type" always;
add_header Access-Control-Max-Age "86400" always;

# 如果需要携带 Cookie
add_header Access-Control-Allow-Credentials "true" always;
# 此时 Access-Control-Allow-Origin 不能是 *
```

### 6.3 密钥管理规范

```
# ❌ 错误做法
DB_PASSWORD=my_password     # 硬编码
SECRET_KEY=abc123           # 弱密钥
API_KEY=sk-xxx             # 硬编码在配置文件

# ✅ 正确做法
# 1. 使用环境变量
DB_PASSWORD=${DB_PASSWORD}

# 2. 使用密钥管理服务
# AWS: Secrets Manager / Parameter Store
# 阿里云: KMS / Parameter Store
# HashiCorp: Vault

# 3. 密钥轮换
# - 数据库密码：每 90 天轮换
# - JWT Secret：每 30 天轮换
# - API Key：按需轮换
```
