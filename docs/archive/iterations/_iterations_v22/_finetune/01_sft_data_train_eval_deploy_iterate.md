## 场景1：SFT数据准备

### 场景模板

```
角色：LLM微调数据工程师
任务：为{model_name}准备SFT训练数据

输入：
- 领域：{domain}
- 数据源：{data_sources}
- 数据量目标：{target_count}条
- 输出格式：{format_type}(ShareGPT/ChatML/Alpaca)

请执行：
1. 数据收集策略（公开数据集+自有数据+合成数据配比）
2. 数据清洗规则（去重MinHash/过滤低质量/敏感信息脱敏）
3. 数据格式转换（→目标格式Schema）
4. 数据质量评估（质量分/多样性/覆盖率）
5. 数据集划分（训练:验证:测试=8:1:1）

请输出JSON格式：
{
  "collectionStrategy": {...},
  "cleaningRules": [...],
  "formatConversion": {...},
  "qualityReport": {...},
  "splitRatio": {...}
}
```

### 陷阱5

| # | 陷阱 | 严重等级 | 修复方法 |
|---|------|---------|---------|
| 1 | 数据泄露：测试集出现在训练集 | P0 | 严格去重+语义去重(>0.9过滤) |
| 2 | 重复数据导致过拟合 | P0 | MinHash+LSH去重+语义去重 |
| 3 | 敏感信息未脱敏 | P0 | PII检测+替换+人工审核 |
| 4 | 数据分布不均衡 | P1 | 类别统计+过采样/欠采样 |
| 5 | 合成数据质量不可控 | P1 | 质量评分+人工抽检5%+迭代优化 |

### 性能基准
- Token消耗：3K-8K | 延迟：2-5s | 成本：$0.02-0.05/次

### 最小可执行示例

```
输入：为Qwen2.5-7B准备代码生成SFT数据，目标5000条ShareGPT格式
提示词：(同上模板，填入具体参数)
预期输出：包含收集策略(代码竞赛+GitHub+合成)+清洗5规则+格式Schema+质量4指标+划分方案
```

### 常见错误Top5

| # | 错误 | 修复方法 |
|---|------|---------|
| 1 | 只收集不清洗 | 必须经过6步清洗流水线 |
| 2 | 格式不统一 | 强制Schema验证+自动转换 |
| 3 | 忽略数据版权 | 只用开源许可数据+标注来源 |
| 4 | 验证集太小 | 最少500条+分层采样 |
| 5 | 未设数据版本 | DVC版本管理+数据快照 |

## 场景2：LoRA/QLoRA训练配置

### 场景模板

```
角色：LLM微调训练工程师
任务：配置{model_name}的LoRA/QLoRA训练

输入：
- 基座模型：{base_model}
- 训练框架：{framework}(Axolotl/LLaMA-Factory/Unsloth)
- GPU资源：{gpu_type}×{gpu_count}
- 训练目标：{objective}

请生成训练配置：
1. LoRA参数（rank/alpha/target_modules/dropout）
2. 训练超参（lr/schedule/batch/epochs/warmup）
3. 量化配置（4bit/8bit/dtype）
4. DeepSpeed/FSDP配置
5. 日志+检查点+导出配置

请输出YAML配置文件格式。
```

### 陷阱5

| # | 陷阱 | 严重等级 | 修复方法 |
|---|------|---------|---------|
| 1 | LoRA rank过大=全参微调 | P1 | rank=16~64，按模型大小调整 |
| 2 | 学习率过高导致崩溃 | P0 | 1e-5~5e-5，带warmup+cosine decay |
| 3 | target_modules不全 | P1 | 至少q/k/v/o_proj+gate/up/down_proj |
| 4 | 梯度累积设置不当 | P2 | 有效batch=micro_batch×gradient_accumulation |
| 5 | 检查点保存过频占满磁盘 | P2 | 每100步保存+保留最近3个+训练结束自动清理 |

### 性能基准
- Token消耗：2K-5K | 延迟：1-3s | 成本：$0.01-0.03/次

### 最小可执行示例

```
输入：配置Qwen2.5-7B的QLoRA训练，A100×2，代码生成目标
预期输出：完整YAML配置，含rank=32/alpha=64/lr=2e-5/4bit量化/DeepSpeed ZeRO-2
```

### 常见错误Top5

| # | 错误 | 修复方法 |
|---|------|---------|
| 1 | alpha≠2×rank | alpha=2×rank是经验最优 |
| 2 | 未开梯度检查点 | 节省显存40%，必须开启 |
| 3 | QLoRA double quant未开 | 开启nf4+double_quant更省显存 |
| 4 | 忽略EOS token | 训练数据必须正确处理特殊token |
| 5 | eval_strategy设为no | 必须定期评估防止过拟合 |

## 场景3：模型评估

### 场景模板

```
角色：LLM微调评估工程师
任务：评估{model_name}微调后效果

输入：
- 微调模型：{finetuned_model}
- 基座模型：{base_model}
- 评估维度：{dimensions}
- 基准测试集：{benchmarks}

请执行评估：
1. 自动基准测试（MMLU/C-Eval/GSM8K/HumanEval/Codex）
2. 领域专项测试（自定义测试集）
3. LLM-as-Judge评估（Win Rate对比基座模型）
4. 回归测试（通用能力是否退化）
5. 人工评估抽样（50条+Likert 5级量表）

请输出评估报告JSON。
```

### 陷阱5

| # | 陷阱 | 严重等级 | 修复方法 |
|---|------|---------|---------|
| 1 | 只看领域分忽略通用退化 | P0 | 回归测试：通用能力降分>3%即不通过 |
| 2 | 基准测试集与训练集重叠 | P0 | 严格去重+时间切分 |
| 3 | LLM-Judge自身偏差 | P1 | 3模型交叉评估+位置交换消除偏差 |
| 4 | 评估样本量不足 | P1 | 最少200条+分层抽样+置信区间 |
| 5 | 评估指标不全面 | P2 | 准确率+完整性+相关性+安全性4维 |

### 性能基准
- Token消耗：5K-15K | 延迟：5-15s | 成本：$0.05-0.15/次

### 最小可执行示例

```
输入：评估代码生成微调后的Qwen2.5-7B vs 基座模型
预期输出：HumanEval 72→85(+13) | 通用MMLU 68→67(-1，可接受) | WinRate 68% | 评估结论：通过
```

### 常见错误Top5

| # | 错误 | 修复方法 |
|---|------|---------|
| 1 | 只对比微调前后 | 必须同时对比基座+其他模型 |
| 2 | 评估prompt与训练差异大 | 评估prompt应与训练对齐 |
| 3 | 忽略长尾case | 统计最差10%的表现 |
| 4 | 温度设置不一致 | 对比时用相同温度(通常0) |
| 5 | 单次评估就下结论 | 至少3次取平均+报告标准差 |

## 场景4：量化部署

### 场景模板

```
角色：LLM部署工程师
任务：将{model_name}量化并部署到{target_environment}

输入：
- 模型：{model_path}
- 量化方法：{method}(GPTQ/AWQ/SmoothQuant/ONNX)
- 目标硬件：{hardware}
- 部署框架：{framework}(vLLM/SGLang/TGI/Ollama)

请执行：
1. 量化配置（bits/group_size/damp_percent/校准数据）
2. 量化精度评估（PPL变化+下游任务精度损失）
3. 推理性能测试（吞吐/延迟/显存/并发）
4. 部署配置（服务配置+API接口+健康检查）
5. 监控告警配置

请输出部署配置+性能报告JSON。
```

### 陷阱5

| # | 陷阱 | 严重等级 | 修复方法 |
|---|------|---------|---------|
| 1 | 量化校准数据分布不匹配 | P0 | 用与推理数据同分布的200~500条 |
| 2 | 敏感层量化导致精度崩溃 | P1 | 首尾层+注意力层跳过量化 |
| 3 | 只看PPL不看实际任务效果 | P1 | PPL+3个下游任务双重验证 |
| 4 | INT4量化后推理出错 | P1 | 混合精度：关键层FP16+其他INT4 |
| 5 | 部署未设限流 | P2 | 限流+队列+超时+降级 |

### 性能基准
- Token消耗：3K-8K | 延迟：2-5s | 成本：$0.02-0.05/次

### 最小可执行示例

```
输入：Qwen2.5-7B GPTQ 4bit量化部署到vLLM，A10 GPU
预期输出：量化config+PPL 5.2→5.4(+0.2可接受)+吞吐450tok/s+部署YAML
```

### 常见错误Top5

| # | 错误 | 修复方法 |
|---|------|---------|
| 1 | 校准数据太少 | 最少200条，推荐500条 |
| 2 | 未测试长序列性能 | 测试4096+8192 token长度 |
| 3 | 忽略KV Cache量化 | 开启kv_cache_dtype=fp8 |
| 4 | 部署未考虑多卡 | tensor_parallel_size按GPU数配置 |
| 5 | 缺少健康检查 | /health端点+自动重启 |

## 场景5：DPO/RLHF迭代优化

### 场景模板

```
角色：LLM对齐工程师
任务：通过DPO/RLHF对齐{model_name}

输入：
- SFT模型：{sft_model}
- 偏好数据：{preference_data}
- 对齐方法：{method}(DPO/ORPO/Iterative-DPO/RLHF-PPO)
- 目标：{alignment_goal}

请执行：
1. 偏好数据准备（chosen/rejected对+质量过滤）
2. 对齐训练配置（beta/lr/loss_type/reference_model）
3. 对齐效果评估（Arena Elo/Win Rate/Helpfulness/Harmlessness）
4. 迭代策略（数据飞轮+在线学习+模型自博弈）
5. 部署切换（A/B灰度+效果追踪）

请输出对齐配置+迭代计划JSON。
```

### 陷阱5

| # | 陷阱 | 严重等级 | 修复方法 |
|---|------|---------|---------|
| 1 | 偏好数据标注不一致 | P0 | 标注指南+3人标注+一致性检查(κ>0.7) |
| 2 | DPO beta过大导致模式坍塌 | P1 | beta=0.1~0.5，从小开始调 |
| 3 | 对齐税：对齐后能力下降 | P1 | 追踪通用基准+对齐税<2% |
| 4 | 奖励模型过拟合 | P1 | 早停+正则化+独立验证集 |
| 5 | 迭代优化无收敛判断 | P2 | 设Elo提升阈值(<5停止)+最大迭代轮次 |

### 性能基准
- Token消耗：4K-10K | 延迟：3-8s | 成本：$0.03-0.08/次

### 最小可执行示例

```
输入：对代码生成SFT模型执行DPO对齐，偏好数据2000对
预期输出：DPO config(beta=0.1/lr=5e-7)+WinRate 55%+Elo +25+迭代3轮计划
```

### 常见错误Top5

| # | 错误 | 修复方法 |
|---|------|---------|
| 1 | chosen和rejected差异太小 | 差异度评分+过滤低对比度对 |
| 2 | 参考模型与SFT模型不一致 | DPO参考模型必须是SFT模型本身 |
| 3 | 忽略安全对齐 | 必须加入安全偏好数据 |
| 4 | 过度对齐(太保守) | 追踪helpfulness+harmlessness双指标 |
| 5 | 迭代无新数据 | 每轮至少新增20%偏好数据 |
