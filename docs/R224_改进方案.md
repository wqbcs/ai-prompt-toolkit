# R224 改进方案 — 从"能跑绿的CI"到"可信、可被采用、可自证"

日期：2026-10-02 · 版本基线：67.34.13（CI 已双绿）

R223 收口后，产品第一次真正站在 GitHub Actions 上跑绿（Prompt CI + OWASP Scan 双 success）。
但"CI 绿"只是可信度的**必要条件**，不是**充分条件**。本轮鬼才 PM 反问驱动，
把重心从"内部能跑"切到"外部可信、可被采用、可自证"。

---

## 一、定位反问（四个自问）

**1. 项目定位是啥？**
确定性的 Prompt 静态安全/质量门禁。零 LLM、可复现、<100ms、SARIF/CI 原生。
一句话：**"LLM 应用提示词的 ESLint，且结果每次都一样。"**

**2. 核心产品价值（可防守的 moat）是啥？**
不是规则多（261 条会被追平），而是**确定性 + 可复现 + 零 LLM 成本 + 毫秒级 + CI 原生**。
竞品（promptfoo/garak）全是 LLM 驱动：非确定、按次收费、慢、要 API key。
这是它们**结构性补不上**的楔子。

**3. 目前推进方向有啥问题？**
- 双基线（漏检 0.00% / 误报 0.91%）是核心可信度叙事，却锁在**私有仓库 + 深埋文档**，
  用户看不见、没法 2 条命令自证 → 可信度停在"自说自话"。
- README 首屏是**功能计数堆砌**（261规则/130维度/73 MCP/24 Provider），
  把楔子（确定性）埋在最下面 → 访客 3 秒看不到"为什么可信"。
- 仓库**未发布到 PyPI**（`pip install ai-prompt-toolkit` 还不真实存在）→ 采用路径断在第一步。
- **没有 copy-paste CI 片段** → 采用门槛高，竞品（promptfoo）都有现成 GitHub Action。

**4. 低价值打磨陷阱（明确不做）？**
- ✗ 再堆 50 条规则 / 加 130→180 维度 —— 稀释"确定性"叙事，用户不可见。
- ✗ A/B 测试 / 模板市场 / 24 Provider 深化 —— 引入 LLM 调用，直接对冲楔子。
- ✗ 行:列 全量重构（剩余 237 条文件级）—— 高风险低收益，R219 已判定。
- ✗ 把 mypy 基线从 0 抬高来"过门禁" —— 那是藏 bug，不是修 bug（本轮已拒绝）。

## 二、竞品调研结论（联网实证，2026-10-02）

| 竞品 | 是什么 | 暴露的痛点 / 信号 | 可借鉴 |
|------|--------|------------------|--------|
| **promptfoo** | LLM 驱动评估 + code-scan Action | 官方文档明说 *"LLM eval outputs are non-deterministic"*，要用 `repeat:3 repeat-min-pass:2` **多次采样**对冲；code-scan 要 `PROMPTFOO_API_KEY` + Node 24 运行时 | 我们**天生不用 repeat / 不用 Fisher / 不用 API key** —— 把这点做成对比卖点 |
| **garak** | 探针式 LLM 漏洞扫描 | 一篇 CI 门禁实践文：即便 pin 版本 + fixed seed，还要用 **one-sided Fisher 精确检验**对比基线，且 *"two rows alone turn about 54% of no-op PRs red"*（统计门禁误红率 54%） | **统计门禁必然有噪音**；确定性规则 = 无采样、无 Fisher、误红率≈0。这是楔子的硬证据 |
| **prompt-defense-audit** (ppcvote) | 确定性 regex 防御扫描器（**最像我们的竞品**） | 主张 *"The deterministic engine is the product. AI deep analysis is optional. Zero AI cost by default"*；**公开真实缺口统计**（97.8% 缺间接注入防御、78.3% 评分 F）；**诚实声明失效边界**（regex 是启发式，度量"防御意图"非"实际有效性"）；只支持 en + zh-T | ① 定位被验证（确定性楔子真实存在）② 公开缺口统计=社会证明 ③ 诚实声明边界=可信度 ④ 我们规则更广(261)+语言更全，但叙事没它锋利 |
| **taudit** (0ryant) | CI/CD 策略门禁（**采用最佳实践范本**） | Day0/Day1 采用清单；`--locked` 锁版本；**brownfield 采用：基线把 finding 分 NEW vs PRE-EXISTING，门禁只看 NEW**（解决存量噪音）；suppressions 文件；**分阶段采用 report-only → gate-on-high** | ① copy-paste CI 是采用的命门 ② "只看新增"是 brownfield 采用的关键特性（我们缺）③ 分阶段采用降低摩擦 |

**调研三条硬结论：**
1. **确定性楔子被验证**：最像我们的竞品（prompt-defense-audit）已在用同一主张，且把它当卖点。方向对，要更锋利。
2. **可信度要"可自证 + 公开数字"**：竞品公开缺口统计（97.8%/78.3%）；我们要让双基线**一条命令自证**，而非埋在私有文档。
3. **采用要"copy-paste + 分阶段 + 只看新增"**：没有现成 CI 片段和 brownfield 基线，好产品也用不起来。

## 四、PM 自审（写方案时反问的五个问题）

1. **"261 规则、130 维度、24 Provider"这些数字放首屏对吗？**
   不对。那是"我们做了什么"，用户关心"我为什么该信你"。
   → 首屏改为楔子叙事，功能计数降级到 feature 列表。

2. **"双基线 0.00% / 0.91%"写在私有仓库文档里，可信吗？**
   不可信。没有可执行自证 = 自说自话。
   → P0-1 让 `prompt-cli baseline` 在用户机器上可复现，数字才站得住。

3. **"确定性"是技术细节还是卖点？**
   竞品文档反复出现的痛点（non-deterministic / repeat:3 / Fisher / API key）
   就是我们的卖点清单。技术细节升级为对比卖点。

4. **11 个 Critical 模板问题修不修？**
   必须修。CI 门禁（我们卖的东西）拦住了自家模板——不修就是"卖尺子自己量不准"。
   183 high 记录 backlog，不阻塞发布。

5. **本轮做完后下一个陷阱是什么？**
   陷阱是"把 P1 全部做完再发布"——PyPI 发布只需要一次用户授权，
   不应等 P1-2/P1-3 做完。发布是最早该做的采用动作，不是最后收尾。
   → 本轮收口后立即请求用户做 PyPI 发布授权（一次性 5 分钟操作）。
