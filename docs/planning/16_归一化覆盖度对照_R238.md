## 3. 漏检面处置（诚实边界，登记不扩）

| 漏检形态 | 立项风险（为什么现在不立规则） | 登记 |
|---|---|---|
| hex 连续串 | FP 风险：CSS 色 `#hex`/哈希/十六进制配置是正常面（§2 良性面实证）；需"hex 承载注入关键词"的定向形态（对标 P260 base64 子面做法），≥2 独立 TP 探针才立 | 07 X2 |
| `\u00XX` ASCII 转义 | FP 风险**最高**：中文配置里 `\u4e2d\u6587` 是常态（§2 关键 TN）；P261 子3 刻意只取不可见字符区 `\u200x` 就是这个教训；未来形态必须是"注入关键词 ASCII 的转义"（如 `\u0069\u0067\u006e\u006f\u0072\u0065`），非通用转义 | 07 X2 |
| rot13 | 真实攻击语料中 ROT13 出现频率未证（RankClaw"表面扫描漏 60%"警示=归一化扩张有上限）；无 ≥2 TP 探针 | 07 X2 |
| leetspeak | 同上；leet 替换的合法面（口令/产品名）FP 风险未量化 | 07 X2 |
| homoglyph（西里尔混入拉丁） | 我方 P261 辖区是"不可见控制字符"，homoglyph 是"同形可见字符"=另一检测域（需同形字符映射表，维护成本面）；已知缺口 U+0301/U+00AD 同族，真实案例驱动重评 | 07 X2 |

**方法论结论**（进 02 反清单）：
1. **归一化≠覆盖**——prompt-guard 把 7 形态全归一化再匹配，但归一化本身
   引入新 FP 面（§2 良性面逐形态验证的必要性）；我方逐形态精确触发
   （P260 base64 子面/P261 不可见字符子3）是更稳的形态，覆盖窄但 FP 可控。
2. **漏检面登记是诚实资产**——29% 覆盖率的公开披露（发布后 P1-07 README）
   比"全归一化"的虚高覆盖更可信，与双基线时间序列叙事同构。
