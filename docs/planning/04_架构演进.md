# 04 · 架构演进（5 年生命周期设计）

> 目标：任意端（CLI/Action/npm/VS Code/WASM/前端）技术栈迭代不影响业务内核；
> 内核可被 5 年后的人读懂并扩展。原则：高内聚低耦合 + 奥卡姆剃刀（没有两个调用者不抽象）
> + 5 年不变量（01 §3）。本文是**设计与路线**，不含实现指令——实现任务在 02 总板（P4-*）。

---

## 1. 目标分层（四层 + 端适配）

```
┌─────────────────────────────────────────────────────────────┐
│  adapters（端适配层 — 可整体替换，随端技术栈自由迭代）           │
│  ├─ cli（Python argparse/click 命令）                        │
│  ├─ action（GitHub composite action 壳）                     │
│  ├─ npm-wr（Node 包装器：spawn 或 WASM，P1-04）              │
│  ├─ vs-code（TS 扩展：--stdio 桥，P1-05）                    │
│  ├─ docker（镜像打包壳）                                      │
│  └─ playground（前端，P2-13）                                │
├─────────────────────────────────────────────────────────────┤
│  io（输入输出层 — 文件格式与渲染，换格式不改内核）              │
│  ├─ inputs: .md/.txt/.json/.yaml 扫描 + 路径发现              │
│  ├─ outputs: SARIF / JSON / Markdown / CLI-text / --stdio    │
│  ├─ 配置发现: promptlint.toml + pyproject (P2-03, P4-04)     │
│  └─ 基线文件: baseline save/load/diff (linter/baseline.py)   │
├─────────────────────────────────────────────────────────────┤
│  rules（规则层 — 261 条，只依赖 kernel，未来插件化 P4-03）      │
│  ├─ 规则定义: id/pattern/severity/waiver提示/explain          │
│  ├─ 注册表: 包内注册(当前) → entry_points 插件(目标)          │
│  └─ 元数据: status(active/deprecated/removed) (P2-01)        │
├─────────────────────────────────────────────────────────────┤
│  kernel（内核 — 零第三方依赖，5 年不动区）                     │
│  ├─ finding 模型（稳定数据契约，P2-02 schema 版本化）         │
│  ├─ 引擎: 规则×模板 匹配调度（<100ms P99 性能不变量的执行体）   │
│  ├─ severity 体系 + waiver 语义 + verdict 计算                │
│  └─ 确定性保证: 同输入同规则版本→逐字节同输出                  │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向铁律**：只允许上层 import 下层（adapters→io→rules→kernel）；
rules 不得 import io（规则不关心输出格式）；kernel 零第三方依赖（stdlib only）。
任何违反依赖方向的 import = P4-01 测绘要抓的"违规边"。

## 2. 现状与差距（执行 P4-01 测绘时的已知疑点清单）

> 以下为本轮规划期的静态判断，**P4-01 测绘任务必须逐条核实并出依赖图**，测绘结果推翻本节判断时以测绘为准。

| # | 疑点 | 期望 | 若违背则 |
|---|---|---|---|
| G1 | `src/ai_prompt_toolkit/linter/` 是否 import click/CLI 层 | 不 import（规则层纯净） | 拆出 CLI 耦合进 io/adapters |
| G2 | kernel 级模块（finding 模型/verdict）是否混在 linter/ 包内 | 允许暂混，但 P4-01 要标出边界 | 后续抽 `kernel/` 子包（P4-07 延后窗口做） |
| G3 | 261 规则是否硬注册于单一模块 | 当前允许；目标 entry_points（P4-03） | P4-03 插件化任务 |
| G4 | 运行时 import 是否全在 pyproject 声明 | 全声明（历史教训：本地 venv jinja2 未声明→本地绿 CI 红） | P0-05 环境锁定 + import 审计步 |
| G5 | 输出格式是否散落在引擎内（SARIF 生成混在 lint 主路径） | 输出在 io 层 | 抽 OutputAdapter（P4-05） |
| G6 | 配置/waiver/基线参数是否散落各命令 | 当前允许；目标 config 模块单点（P4-04） | P4-04 统一 |
| G7 | CLI 各命令文件是否互相 import | lint_commands 等大文件内部耦合可接受，命令间不 import | P4-07 拆分（发布后 2 版本） |

## 3. 五个 5 年不变量 → 架构机制映射

| 不变量（01 §3） | 架构机制 | 机器护栏 |
|---|---|---|
| ① 核心零 LLM | kernel+rules 层无 LLM SDK 依赖；增强走独立命令（反清单） | import 审计步（P4-02）|
| ② 裁决可复现 | 引擎禁随机/时间/哈希序依赖；遍历规则按 id 排序；输出 JSON 键排序 | 复现性 e2e 测试（P3-01 含）+ OTEL 采样对比（P2-15）|
| ③ <100ms P99 | 规则数据 JSON 化（P2-14）为前端/WASM 端保留性能路径；引擎热点可 profile | 性能回归断言（P2-16）|
| ④ 规则与逻辑分离 | entry_points 插件（P4-03）+ 规则 JSON 导出（P2-14）+ deprecation 周期（P2-01）| 插件加载测试 + schema 版本测试（P2-02）|
| ⑤ 退出码契约稳定 | 退出码语义表进 README 契约区；新级别只加（3+）不改 0/1/2 | e2e 退出码断言（P3-01）|

## 4. 插件化路线（P4-03 详细设计）

**目标形态**：
```toml
# 外部包 pyproject.toml
[project.entry-points."promptlint.rules"]
my_rule_alpha = "my_pkg.rules:AlphaRule"
```

**分阶段**（每阶段独立可回滚，禁一步到位大重构——陷阱 T6/T10）：
1. **Phase 1（M）**：内核内先建 `RuleRegistry`（注册/查询/排序），261 规则改为经 registry 注册（行为不变，纯结构）；加 registry 测试
2. **Phase 2（L）**：registry 发现逻辑加 entry_points 源（`importlib.metadata`，stdlib 零依赖）；外部包可注册；包内规则保持内建（内建优先级/去重语义文档化）
3. **Phase 3（远期）**：规则 JSON 化导出（P2-14）对齐插件规则 schema；playground 可加载 JSON 规则

**去重语义（必须先定，再动 Phase 1）**：插件规则与内建规则 id 冲突时——
内建优先 + 警告（确定性优先：内建 id 永远指向内建语义）。写入 ADR。

## 5. 各端技术栈选型（"每端公认最优"，不被单一栈绑定）

| 端 | 选型 | 理由（为何是公认最优） | 绑定风险与逃生门 |
|---|---|---|---|
| CLI 核心 | Python 3.10+ stdlib+click | 确定性文本处理生态最成熟；<100ms 无压力 | click 可换 argparse（io 层封装，kernel 无感） |
| CI 集成 | GitHub composite action + SARIF | GH 生态事实标准；Code Scanning 原生消费 SARIF | SARIF 是 OASIS 标准，可移植到 GitLab/Azure DevOps（它们也收 SARIF）——**这是不被 GH 绑定的关键** |
| 编辑器 | VS Code 扩展（TS）走 `--stdio` 桥 | linter 类扩展事实架构（vscode-eslint 先例）；不绑 LSP | stdio JSON 行协议是纯文本契约，JetBrains 插件/Neovim 插件复用同一协议（P4-05 输出适配器） |
| JS/TS 端 | 先 uvx（零 npm 层），后 npm 薄包装 | uvx 是 Python 工具零安装跑的公认方案；npm 包装器若做只做参数/退出码透传 | 若 JS 端需求真实爆发再上 pyodide/WASM（P4-06 路线）——需求证明前不做 |
| 浏览器 playground | 静态站 + 规则 JSON + JS regex 子集引擎 | ESLint playground 形态；无后端=零运营成本（GH Pages） | 若 JS/Python regex 语义差异不可接受，降级为"只读展示+样例" |
| 容器 | ghcr + python:slim 多阶段 | 离线/air-gap ICP 硬需求；GH 原生 registry | 镜像只是安装介质，不是依赖面 |

**绑定检查纪律**：每轮收口问一句——"本端选型若 5 年后被废弃，迁移成本是多少？"
答案必须≤"换 adapter 层一个文件/目录"，否则架构设计有漏。

## 6. 演进顺序（防返工拓扑）

```
P4-01 测绘(依赖图+违规边)          ← 一切 P4 的前置，先测绘后动刀
   ├→ P4-02 核心零依赖验证/审计步    ← 与 P0-05 环境锁定合流
   ├→ P4-04 config 模块统一          ← 前置 P2-03(promptlint.toml)
   ├→ P4-05 OutputAdapter           ← 前置 P2-02(schema)
   └→ P4-03 插件化 Phase1→2         ← 前置 P4-01；去重语义 ADR 先行
P2-14 规则 JSON 导出               ← P2-13 playground / P4-03 Phase3 / P1-04 远期 WASM 的共同数据基础
P4-07 大文件拆分                   ← 严格延后到 PyPI 发布后 2 个版本（陷阱 T6）
P4-06 多语言绑定路线                ← 仅文档占位，无实现
```

**关键纪律**：
1. 测绘未完成前，任何 P4 实现任务不得开工（P4-01 的依赖图是唯一施工图）
2. 每步结构变更必须带：门禁链全绿 + 双基线不回归 + 测试数不降（陷阱 T10）
3. 发布窗口期（P0 完成前）冻结一切结构变更——只加文件不动结构
4. 每个 P4 任务完成后更新本文 §2 差距表（已消除的差距划掉）

## 7. 高可读性/可维护性约定（给未来读者的）

1. **kernel 层每个模块 ≤300 行**，规则注册表/finding 模型/verdict 各自独立文件
2. **模块头 docstring 三行**：职责一句话 + 依赖谁 + 被谁依赖（P4-01 测绘时批量补齐）
3. **禁止跨层 import 的 CI 检查**：`scripts/check_layering.py`（ast 扫描 import 边对 §1 依赖图，违规即红）——P4-01 产出违规清单后登记为 P4-10
4. **ADR 覆盖所有跨层决策**（P4-09）：插件去重语义、退出码扩展、schema 升级策略
5. **文档导航**：README 只留"是什么/怎么装/怎么用/契约"，架构细节全在 docs/（P4-08 目录治理后）
