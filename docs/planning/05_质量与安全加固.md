# 05 · 质量与安全加固（门禁工具自身的质量）

> 定位约束：我们是一个**安全门禁工具**——"尺子本身必须比被量物更可信"。
> 任何加固任务不得破坏 5 年不变量（01 §3）；任何"藏问题过门禁"的动作都是红线（陷阱 T5）。
> 任务编号对齐 02 总板 P3-*，本文是详细设计，02 是权威状态。

---

## 1. CI 门禁体系加固（P0/P3 交集，最高优先）

### Q1. push 硬门禁作业（P0-02）
- **现状缺陷**：`prompt-quality-gate` 作业仅 `pull_request` 触发——直推 main 从无硬门禁。
  我们卖"CI 门禁"却在自己最常用的路径（直推）上没开门禁，叙事自相矛盾。
- **方案**：
  1. `.github/workflows/prompt-ci.yml` 加 `on: push: branches: [main]` 触发的 gate 作业
  2. gate 内容 = 现有 PR gate 全量（templates+prompts lint --gate、双基线棘轮、版本一致性、docs drift、SARIF 合法性）
  3. **注意**：push 作业不能对同一 commit 重复跑 pytest（矩阵减重见 P6-03：push 作业只跑 gate 不跑测试矩阵，测试仍走 PR 触发的 test 矩阵）
  4. 分支保护：main 要求 gate 作业通过（Settings→Branch protection）
- **验收**：构造一个违规模板直推（test 分支实验）→ 红；合规直推 → 绿
- **不做**：不引入第三方 gate SaaS（数据主权，CI 原生）

### Q2. 环境锁定（P0-05）
- **根因史**（4 连红）：ruff 未钉版（行为漂移）→ click 8.5.0 类型漂移（CI 装最新 vs 本地 8.3.3）→ mypy 版本差 → 管道吞退出码假绿
- **方案（按依赖面从紧到松）**：
  1. **dev 依赖钉死**：ruff/mypy/black 等工具链全部 `==` 钉版（现状部分已钉，全量核查）
  2. **运行时依赖**：`click` 加**下界+上界**（`>=8.1,<9`）——上界是保险丝，click 9 破坏 API 时 CI 先红而非静默漂移；**同时**核心代码对 click 的使用收敛到稳定 API 子集（sys.stdin 模式已是对抗类型漂移的修复方向，保持）
  3. **锁文件**：`uv lock` 生成 `uv.lock`（仅 dev/CI 用途，wheel 用户不受影响）→ CI 用 `uv sync --locked` 装环境 → 本地/CI 逐字节同版本
  4. **依赖清单一致性步**：CI 加 `scripts/check_dep_manifest.py`——断言"src 运行时 import ⊆ pyproject core 依赖"（jinja2 未声明事故的反向护栏，固化记忆项）
- **验收**：连续 10 轮 CI 与本地 `pip list` diff = 0
- **注意**：uv 引入是 dev 工具链（不进 wheel 依赖），符合"不被单一栈绑定"——uv 只是锁文件生成器，CI 也可换回 pip+hash 方案

### Q3. 门禁链脚本化（P0-06）
- **现状缺陷**：收口门禁链靠手工命令序列，已 3 次出错（2 次漏 gen_rules_doc、1 次管道吞退出码假绿）
- **方案**：`scripts/release_gate.py`——单入口跑完整链，每步独立子进程+真实退出码（禁管道吞码）：
  ```
  1. pytest 全量
  2. ruff check src/ tests/
  3. ruff format --check src/ tests/
  4. mypy 棘轮（对比基线，只减不增）
  5. 双基线（FP 0.91% / miss 0.00%）
  6. gen_rules_doc.py（非 --check 模式，真重生成）
  7. sync_badges.py + sync_readme_metrics.py
  8. check_version_consistency.py
  9. check_dep_manifest.py（Q2-4）
  10. SARIF 输出合法性校验（schemastore 2.1.0，C4）
  ```
  失败即停（`--fail-fast` 默认开）+ 每步耗时报告 + `--step N` 单独重跑
- **验收**：人为注入一个 format 漂移 → gate 在 step 3 红且退出码非 0
- **纪律**：此后收口一律 `python scripts/release_gate.py`，禁手工拆步

### Q4. 行级定位折中（P2-06，质量安全交叉）
- **决策**（R219 已定，执行细则在此）：只对 **critical/high 规则**（约 30 条）做行级定位
- **方案**：
  1. 规则引擎匹配时记录 `re.Match.span()`（仅 critical/high 规则启用 span 捕获，medium/low 保持文件级——性能与复杂度都省）
  2. finding 模型加 `line: int | None`（向后兼容：None=文件级，SARIF 省略 region 字段合法）
  3. 多命中规则：取**全部** span（SARIF 一规则多 result），上限 50 个（防单行刷屏，超出折叠计数）
- **不做**：237 条 medium/low 全量行级（陷阱 T2）；AST 级定位（prompt 是自由文本不是代码）
- **验收**：critical/high finding 在 VS Code Code Scanning 里点击可跳行

## 2. 测试金字塔（P3-01/02/09）

### 现状盘点（执行时先核实数字）
- 5987 测试（截至 67.34.16），偏单元；无覆盖率门禁；无 e2e 子进程测试；无 property/fuzz

### T1. e2e 子进程层（P3-01）
- **为什么必须真子进程**：本轮 click stdin 类型漂移只在真进程暴露（CliRunner 不触发 `get_text_stream` 路径）——CliRunner 测试绿 ≠ 真 CLI 绿
- **方案**：`tests/e2e/` 目录，`subprocess.run([sys.executable, "-m", "ai_prompt_toolkit", ...])`
  - 覆盖矩阵（≥20 条）：
    - exit code 三态（0/1/2）× 各 gate 组合
    - SARIF/JSON/MD 文件落盘 + 内容断言
    - 管道 stdin（`echo "text" | prompt-cli lint -s -`）——click 漂移的永久回归护栏
    - `--incremental` 全链（save→存量放行→新增拦截）
    - `baseline` 命令自证（0.00%/0.91% 数字断言）
    - `gap-report` JSON schema 断言
  - 运行方式：标记 `@pytest.mark.e2e`，CI 全量跑，本地 `pytest -m e2e`
- **注意**：e2e 依赖包可 import（`python -m ai_prompt_toolkit` 走 src 布局，venv 内 -e 安装即可，不依赖发布）

### T2. 属性测试（P3-02）
- **工具**：hypothesis（03 §C1）
- **核心 property（≥10 条）**：
  1. waiver 幂等：`lint(waive(waive(x))) == lint(waive(x))`
  2. severity 单调：waiver 不会让 finding 变高 severity
  3. SARIF 不变量：输出恒为合法 JSON + runs/results 结构稳定
  4. baseline 对称性：`compare(a,a).new == []` 且 `compare(a,b).new + compare(b,a).new` 覆盖差异全集
  5. 规则确定性：同输入跑 3 次输出逐字节相等（对随机生成 prompt 串）
  6. 退出码与 verdict 一致性：gate 红 ⟺ 存在超阈 finding
  7. 增量完备性：`full_findings == new + pre_existing`（集合划分，不重不漏）
  8. 行级定位（Q4 后）：line ∈ [1, file_lines] 恒成立
- **策略**：`st.text()` + 中文/emoji/零宽字符/长串（>10KB）边界策略——prompt 的输入域就是"任意文本"

### T3. 覆盖率棘轮（P3-09）
- **工具**：coverage.py（03 §C8）
- **门槛**：linter/ 与 kernel 级模块 ≥90%；全局棘轮（只升不降，初始值取当前实测）
- **CI**：`coverage xml` + Actions summary 表格展示（不传 codecov.io——数据主权）
- **纪律**：棘轮数字是单向阀，PR 降低即红；抬基线=陷阱 T5

## 3. 检测器自攻击（P3-03/04/05）

### A1. 变异测试（P3-03）
- **工具**：mutmut（03 §C2）
- **定向范围**：`src/ai_prompt_toolkit/linter/rules_*.py`（261 规则是探针集要保护的对象）
- **判读**：
  - 变异体被现有测试杀掉 = 测试覆盖到该行为的断言
  - 变异体存活 = 探针集/测试缺口 → 自动产出补探针清单（反哺 P2-11）
- **CI 策略**：变异测试慢（预计 30-90min）——不进每轮 CI，周频 schedule workflow（`cron: 0 2 * * 0`）+ 报告入库 `docs/mutation_report.md`
- **基线**：首轮跑出杀死率基线（预计 70-85%），棘轮只升
- **注意**：mutmut 对 regex 字面量变异能力有限——需人工核对"regex 字符类变异"存活项（这是规则误报/漏检风险最高的变异类型，存活=必补探针）

### A2. Fuzz（P3-04）
- **工具**：atheris（03 §C2）
- **入口**：`lint_template(text: str) -> list[Finding]`（单函数 fuzz，最稳）
- **种子**：golden_attacks.json 113 探针 + templates 26 文件 + 手工边界集（零宽/BiDi/超长/嵌套引号/全中文/全 emoji）
- **CI 策略**：短 fuzz 5min/轮（进 prompt-ci）；长 fuzz 72h 周频
- **断言**：无 crash/无 AssertionError；超时（单输入 >500ms）记 ReDoS 嫌疑（与 A3 联动）
- **崩溃处理纪律**：发现 crash → 最小化用例进 golden 探针集 → 修根因 → 重跑。**禁止**加 try/except 吞异常（陷阱 T5 变体：藏 crash 不是修 crash）

### A3. ReDoS 审计（P3-05）
- **调研结论**（03 §C4）：Python 生态无事实标准静态 ReDoS 检测器 → 行为审计
- **方案**：`scripts/audit_redos.py`
  1. 提取全部 261 规则 regex
  2. 每规则 × 退化输入集（`a{1024}`、`aaaa...!`、嵌套量词触发串 `((a?)?)b` 型）
  3. `signal.alarm`/`multiprocessing` 限时 50ms（50ms 是 100ms 预算的一半留余量）
  4. 超时 → 报告规则 id + 触发串 + 实际耗时 → CI 红
- **CI**：每轮跑（261 规则 × 5 串 × 50ms 上限 ≈ 最坏 66s，可接受；实测大概率 <10s）
- **联动**：fuzz 超时项自动进审计嫌疑名单；审计修复后必须带 TN 探针（防修出漏检）

## 4. 供应链与依赖安全（P3-06 + P4-02）

| # | 措施 | 工具 | 频率 | 红线 |
|---|---|---|---|---|
| S1 | pip-audit | `pip-audit --strict` | 每轮 CI | 高危=阻断；中危=24h 处置时限 |
| S2 | Dependabot | GH 原生（python ecosystem） | 自动 | 依赖更新 PR 必须过门禁链 |
| S3 | 依赖面冻结 | `check_dep_manifest.py`（Q2-4） | 每轮 CI | 核心层（kernel+rules）运行时 import 必须 ⊆ {stdlib, click} |
| S4 | 锁文件 | uv.lock（Q2-3） | 变更即重锁 | CI `--locked` 校验漂移 |
| S5 | 构建审计 | `check-wheel`（PEP 517 构建无源码执行） | 发版前 | wheel 用户安装过程零任意代码执行 |
| S6 | 密钥卫生 | gitleaks/secret-scanning（GH 原生） | 每轮 CI | 0 容忍（本轮凭据走 GH Actions secret 已有先例） |
| S7 | 第三方 Action 审计 | 固定 `@v1` + commit hash 双锁 | 引入时 | 所有 `uses:` 必须 hash 锁定（supply chain 标准实践） |

**依赖审计的元纪律**：我们审计 prompt，但自身的依赖面是更大的攻击面——
核心零依赖（S3）意味着运行时攻击面=click 单一第三方，这是 S4"标准"阶段可展示的安全数字。

## 5. 安全工具自身的威胁面（我们被攻击的路径）

> 门禁工具被投毒/绕过的后果=下游所有 CI 集体失明。威胁模型：

| # | 威胁 | 攻击路径 | 缓解 | 状态 |
|---|---|---|---|---|
| TH1 | 规则投毒 | 恶意 PR 改规则 regex → 下游放行注入 | PR gate 对 `rules_*.py` 变更要求 **2 人 review + 探针测试必过**（CODEOWNERS） | ⬜ 登记 P3-13 |
| TH2 | 探针集投毒 | 篡改 golden_attacks.json → 基线数字造假 | 探针文件进 CODEOWNERS；基线数字变更必须独立 commit+理由（现有纪律扩展至探针） | ⬜ 登记 P3-13 |
| TH3 | 供应链 | click 等依赖被投毒 | S1-S7 全套 | ⬜ 随 P3-06 |
| TH4 | CI 绕过 | 恶意 PR 改 workflow 关 gate | GH 分支保护"Require branches to be up to date" + workflow 文件进 CODEOWNERS + `pypa/gh-action-pypi-publish` 已 hash 锁定 | ⬜ 部分已有，补 CODEOWNERS |
| TH5 | 路径穿越 | 恶意路径参数 → CLI 读任意文件 | lint 扫描范围限制在指定目录；e2e 加 `--path /etc/passwd` 型用例；CodeQL 路径穿越套件（P3-07） | ⬜ 随 P3-07 |
| TH6 | SARIF 注入 | prompt 文本含 SARIF 特殊字符 → 下游 scanner 渲染注入 | SARIF 输出 JSON 序列化（json.dumps 天然转义）——e2e 断言"恶意文本进 SARIF 后是纯数据" | ⬜ 登记 P3-14 |
| TH7 | 基线文件伪造 | 提交者替换基线 → 存量全放行 | 基线文件进 CODEOWNERS；`--incremental` 时基线 hash 变更告警（不阻断但报告） | ⬜ 登记 P3-15 |

**CODEOWNERS（P3-13 交付物）**：
```
/src/ai_prompt_toolkit/linter/rules_*.py  @maintainers
/tests/golden_*.json  @maintainers
/.github/workflows/  @maintainers
/baselines/  @maintainers
```

## 6. 加固任务执行顺序（关键路径）

```
Q3(release_gate.py) ← 第一优先级：止血手工链错误
Q1(push硬门禁) ← 第二：补最大叙事漏洞
Q2(环境锁定) ← 第三：防 4 连红复发（与 Q3 的 dep 审计步合流）
   └→ S1-S7(供应链)  ← 依赖锁定后才谈审计
T1(e2e) ← 与 Q1/Q2 并行（CI 子进程测试是 Q1 的护栏）
A3(ReDoS) ← 规则层加固，独立可先行
T2(property) ← 依赖 finding 模型稳定（P2-02 前只做现有面）
A1(变异)/A2(fuzz) ← 周频基建，晚于每轮 CI 稳定
Q4(行级) ← 体验项，P2-02 schema 定稿后
```
