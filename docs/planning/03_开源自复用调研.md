## A. CI 与采用路径

### A1. GitHub Action
- **参考**：
  - `promptfoo/promptfoo` code-scan Action（MIT）：composite action 形态、API key 处理、Node 运行时版本固定（反面教材：要 Node 24 + key，我们把依赖压到"只要 Python"）
  - `astral-sh/ruff-action`（MIT）：**最像我们的先例**——Python 工具做的 composite action：setup-python→pip install(钉版)→check→SARIF/文本输出→gate 退出码
  - `github/codeql-action`（Apache-2.0）：SARIF upload 标准姿势
  - `golangci/golangci-lint-action`（MIT）：`--new-from-rev` 增量模式在 Action 层的暴露方式（`only-new-issues: true` 一个布尔开关）
- **借鉴点**：composite action 三参数（paths/增量开关/SARIF 开关）；`only-new-issues` 语义直接映射我们 `--incremental`
- **不抄**：promptfoo 的 Node 运行时依赖（我们是纯 Python，setup-python 即可）
- **任务**：P1-01

### A2. pre-commit 钩子
- **参考**：
  - `pre-commit/pre-commit-hooks`（MIT）：官方钩子包形态
  - `astral-sh/ruff-pre-commit`（MIT）：**Python 工具注册 pre-commit 的黄金先例**——`.pre-commit-hooks.yaml` 声明 + entry 指向 CLI + `additional_dependencies` 声明包依赖（用户仓库无需装 Python 也能跑）
- **借鉴点**：`.pre-commit-hooks.yaml` 结构；`language: python` + `additional_dependencies: [ai-prompt-toolkit==x]`；`files: \.(md|txt)$`
- **不抄**：无（直接对齐其形态）
- **任务**：P1-02

### A3. Docker 镜像
- **参考**：`python:3.12-slim` 官方镜像 best practice（多阶段：builder 装依赖→runtime 只带 site-packages）；`ghcr.io` 推送（GH 原生，无外部 registry 依赖）
- **借鉴点**：多阶段构建防镜像膨胀（目标 <150MB）；`--no-cache-dir`；非 root 用户运行
- **不抄**：无
- **任务**：P1-03

### A4. npm 包装器（JS 端）
- **参考**：
  - `uv/uvx`（MIT，astral）：**重要替代方案**——`uvx ai-prompt-toolkit lint .` 零安装跑任意 pip 包，JS 用户 `npx -p uv uvx ...` 或 shell 调 uvx。先验证 uvx 在 Node CI 环境的可用性，**可用则 npm 包装器降级为远期**（奥卡姆剃刀：能不加 npm 层就不加）
  - `pyodide/pyodide`（MIT）：Python→WASM 黄金先例，playground 浏览器端跑规则的唯一成熟路径
  - `esbuild`（MIT）：python→wasm 性能对照（esbuild 用 Go，我们若走 WASM 需 Rust 重写规则引擎=P4-06 路线，当前不做）
- **借鉴点**：若做 npm 包：`node-gyp` 不可用（无 C 扩展），走"包内嵌下载 python standalone 构建（python-build-standalone）+ spawn" 或 pyodide；CLI 参数透传 + exit code 透传是包装器全部职责
- **不抄**：不做 pyodide 全量 Python（体积 10MB+ 且我们规则引擎依赖轻，可裁剪）
- **任务**：P1-04（先做 uvx 验证，npm 层可能整个砍掉）

### A5. VS Code 扩展（编辑器端）
- **参考**：
  - `microsoft/vscode-eslint`（MIT）：**CLI linter → 扩展桥接的黄金先例**——扩展内起 server 进程（`--stdio`），协议通信，问题映射到编辑器 diagnostics。这是 linter 类扩展的默认架构（不是每文件起进程）
  - `astral-sh/vscode-ruff`（MIT）：Ruff 走 LSP server 路线（更重，适合要补全/重格式化）；纯 linter 用 vscode-eslint 的轻量 stdio 桥更合适
- **借鉴点**：`--stdio` 常驻 server 模式（我们 CLI 需加 `prompt-cli lint --stdio` JSON 行协议）；diagnostics 的 severity 映射；文档/配置引用 hover（映射 `prompt-cli explain`）
- **不抄**：LSP 全套（纯文本检测不需要补全/跳转/重格式化——奥卡姆剃刀，只走 diagnostics）
- **任务**：P1-05（前置：CLI 加 `--stdio` 协议，约 S 工作量，登记 P1-05a）

### A6. 双语 README
- **参考**：`mamba-org/mamba`、`astral-sh/ruff`（MIT）：英文主 README + `_zh.md` 版本 + 顶部切换 banner（`[English | 中文]`）；不生成不翻译（维护成本失控）
- **借鉴点**：手写双版本（非 i18n 脚本生成）；badge 区两版一致（由 sync_badges.py 同时写两文件）
- **不抄**：i18n 自动翻译流水线（漂移灾难）
- **任务**：P1-07

## B. 门禁与基线（产品核心）

### B1. 增量门禁（只看新增）
- **参考**：
  - `golangci/golangci-lint`（Apache-2.0）：**第一方 `--new-from-rev`/`--new` 是业界标准形态**——按 git diff 范围算增量，比我们"基线文件"更自动（无需手动 baseline-save）。我们基线文件方案的优势=不依赖 git 历史（air-gap 可用），两者可共存
  - `taudit`（研究性）：NEW vs PRE-EXISTING 二分语义（已借鉴进 adoption.md）
  - `eslint`（MIT）：`--max-warnings N` 预算制（我们的 `--max-warnings` 已对齐）
- **借鉴点**：`--new-from-rev` 作为基线文件的**补充**（有 git 时更自动，无 git 时回退基线文件）——登记为 P2-17 新增待办
- **不抄**：golangci 的缓存目录方案（我们 <100ms 不需要缓存）
- **任务**：P1-01 已落地 `--incremental`；补充项 P2-17

### B2. 缺口统计报告
- **参考**：`ppcvote/prompt-defense-audit`（最像竞品，调研已毕）：公开缺口占比数字（97.8%/78.3%）作为社会证明；诚实声明"度量防御意图非实际有效性"
- **借鉴点**：口径声明句式已抄进 gap_report.py docstring；"最大缺口风险"突出展示
- **不抄**：其 AI 深度分析可选路径（对冲确定性叙事，陷阱 T9）
- **任务**：已落地（67.34.16）

### B3. 质量门 verdict 机制
- **参考**：`checkstyle`（Apache-2.0）：violation→severity→threshold 的 verdict 计算；`golangci-lint --max-issues`：预算数字
- **借鉴点**：verdict 计算与输出渲染分离（我们 quality_gate.py 已满足）
- **不抄**：无
- **任务**：—（已满足，防过度设计）

## C. 质量与安全加固

### C1. 属性测试
- **参考**：`hypothesis`（MIT，pytest 官方推荐）：`@given` 装饰器策略库

- **不抄**：无

### C2. Fuzz 检测器
- **参考**：

- **不抄**：无

### C3. 变异测试
- **参考**：`engstie/mutmut`（BSD-3）：Python 变异测试事实标准，`mutmut run --paths-to-mutate src/ai_prompt_toolkit/linter/` 默认变异点=代码变更
- **借鉴点**：对规则 regex 定向变异（mutmut 可指定）；"探针集是否杀掉变异体"=探针强度度量，直接反哺 P2-11 补探针清单
- **不抄**：无
- **任务**：P3-03

### C4. ReDoS 审计
- **参考**：
  - `hugovk/safe-regex` 类（Python 侧成熟方案少——**调研结论：Python 无事实标准的 ReDoS 静态检测器**，Go 侧 `safetycheck`、JS 侧 `safe-regex` 都不适用）

- **借鉴点**：退化输入生成模式（`a{N}!` 嵌套量词触发串，参考 safetycheck 测试集思想）
- **不抄**：不引静态 ReDoS 库（Python 生态无成熟品，奥卡姆剃刀选行为审计）
- **任务**：P3-05

### C5. 依赖审计

## D. 发布与生态

### D1. PyPI trusted publishing
- **参考**：`pypa/build` 官方文档的 OIDC 示例（GH Actions `id-token: write` + `pypa/gh-action-pypi-publish`，**无需 API token 入库**）；`astral-sh/ruff`（Python 项目）的发布作业是现成参照

- **参考**：`googleapis/release-please`（Apache-2.0）：conventional commits 驱动版本+changelog+tag；Python 模板（`release-please-python`）自动改 pyproject

## E. 架构与插件

### E1. 规则插件机制
- **参考**：
  - `pycodestyle/pycodestyle` + `flake8`（MIT）：flake8 的 entry_points 插件发现（`flake8.extension` 组）= Python 生态标准；pycodestyle 本体零插件（纯核心）——我们目标形态：内核纯+规则可插
  - `ast-grep/ast-grep`（MIT）：**规则=声明式 YAML**（模式/元变量/修复建议）——若未来规则数据 JSON 化（P2-14）走向"规则外置"，ast-grep 的规则 schema 是最佳参照（但我们是 regex 引擎不是 AST，schema 思想借鉴，引擎不抄）
- **借鉴点**：entry_points 组名 `promptlint.rules`；每条规则一个 entry point（可独立装卸）；规则元数据（id/severity/deprecated 状态）集中注册
- **不抄**：ast-grep 的 AST 引擎（我们是文本/regex 层，确定性来自规则即代码）
- **任务**：P4-03

### E2. 配置发现
- **参考**：`astral-sh/ruff`（MIT）：`ruff.toml`/`.ruff.toml`/`pyproject [tool.ruff]` 三级发现+目录向上查找+项目根锚定；`.ruffignore`
- **借鉴点**：`promptlint.toml` + `pyproject [tool.promptlint]` 双位置；向上查找至 git root 锚定；配置合并规则（就近优先）
- **不抄**：ruff 的配置项全集（我们只需 rules/waivers/thresholds/baseline 四类）
- **任务**：P2-03

### E3. Playground
- **参考**：
  - `astral-sh/ruff` playground（MIT）：**pyo3+wasm-bindgen 把整个引擎跑进浏览器**——金标准但需 Rust 重写（P4-06 路线，远期）
  - `eslint` 官方 playground（MIT）：node server 跑引擎+浏览器 UI（重但有现成形态）
  - `pre-commit` playground（MIT）：GitHub Pages 静态站
  - **务实路径**：规则数据 JSON 化（P2-14）+ 纯前端 JS 实现 regex 引擎（JS 原生 `RegExp` 与 Python `re` 的 Unicode 语义有差异——需对照测试子集，或 playground 只做规则展示+样例不真跑）
- **借鉴点**：UI 形态（左侧输入/右侧 findings 树/规则点击 explain）
- **不抄**：ruff 的 pyo3 全量方案（当前 Rust 重写不成立，陷阱 T8 边界）
- **任务**：P2-13（先做 P2-14 数据导出，playground 分两期：一期只读展示，二期前端真跑）
