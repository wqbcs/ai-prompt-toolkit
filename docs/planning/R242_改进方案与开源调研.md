### 2.3 痛点/需求信号

- **采用摩擦仍是第一障碍**（R235/R237 实证延续）：LintLang 用 `uvx` 一键 +
  first-party Action/pre-commit 把"装+接"压到最小。我方 pip+零配置已是
  对标面，但 Action/pre-commit 卡 D1/D3 授权。**可纯仓库动作消解的=README
  把差异化数字摆明**（P2-12），让 clone 者 3 秒看到"这工具有别人没有的
  可验证确定性"。

  review"机器化，是可信度叙事的制度背书（P3-13）。

## 5. 对抗审查（鬼才 PM 视角）

**审查问题 1：为什么不继续加规则（P268），而做这三件"非检测"事？**
→ 第一性原理：产品核心承诺是"可验证的确定性"，不是"规则最多"。267 规则
的边际价值已低于"让用户看见我们已有的可验证性"——差异化（双基线时序+
多语言分基线+OWASP 2026）全是内部资产，clone 者 3 秒看不到"分语言漏检率"
=这张牌没打出。P2-12 把已算好的数字（run_miss_rate per_language 既有输出）
摆到明面=零成本兑现差异化。加 P268 需完整证据链（2 独立 TP+全量重验+原型
+三源零误报），而凭据族自然生长已趋近天花板（SSN/Secret 正确推迟在观察区
=刹车正常）。**奥卡姆：用已有数据兑现卖点，不为凑数造新检测**。

**审查问题 2：P2-14 导出规则 JSON 会不会范围蔓延（"每端最优技术栈"是陷阱吗）？**
→ 不蔓延，因为它只导**数据**不动**逻辑**。对抗点："playground/npm/WASM
都没人用，导 JSON 给谁看？"——答：它不是为某一端做的，是为"**内核不绑定
技术栈**"这个 5 年架构不变量做的唯一数据前置：规则逻辑留 Python（内核零
依赖既有），元数据 JSON 化=任何端（前端/Node/未来 Rust）消费同一份数据的
事实标准（ESLint meta 形态=行业先例，§2.1 S 级）。没有它，P2-13/P1-04/
P4-06 全是空头支票；有了它，任意端迭代不碰业务内核（用户"架构可演进 5 年"
硬需求的落地路径）。零行为面改动+零 FP 面=低风险架构投资，非功能蔓延。

**审查问题 3：CODEOWNERS 在单人仓库里是不是形式主义？**
→ 不是。①GitHub 无分支保护的仓库 CODEOWNERS 也展示 ownership=对 clone
者/未来贡献者声明"哪些文件是尺子"（探针/基线/规则/workflow 变更需双人
review 制度化=TH1/TH2/TH4 威胁面缓解，05 §5）②赛道拥挤后"谁的基线数字
不可被投毒"是竞争焦点——CODEOWNERS 是"我们的尺子有保护"的可见制度背书，
与 P3-15 基线篡改检测（机器面）互补（制度面+机器面双保险）③未来转组织
仓库/收外部贡献时零迁移成本。纯声明文件=零风险。

**审查问题 4：为什么不直接把发布（D1-D4）当本轮主项推？**
→ 发布需用户授权 4 个一次性操作（转公开/PyPI/Action/pre-commit），技术上
无法代执行（账号权限边界）。但**发布前的仓库内容**可以最大化：P2-12
（差异化数字可见）+P3-13（信任制度可见）+P2-14（多端叙事可证）全让
"转公开那一刻"的仓库状态强一个档次——授权是用户的动作，仓库就绪度是我的
动作，本轮把后者做满。

**审查问题 5：三项并做会不会超一轮负荷？**
→ 负荷核对：P2-12=1 脚本（~80 行）+README 小节；P3-13=1 声明文件（~15 行）
+CONTRIBUTING 一句；P2-14=1 命令（~120 行，复用 to_dict/explainer 聚合零
新逻辑）+10 测试。全部纯增量零回归面，无规则面改动（双基线不回归=必然，
零新探针零新规则）。若超负荷则 P2-14 顺延 R243（P2-12/P3-13 是纯文档/文件
面，必保）。
