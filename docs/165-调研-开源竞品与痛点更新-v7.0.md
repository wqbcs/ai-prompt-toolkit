## 一、重大行业事件（影响定位）

### 1.1 OpenAI 收购 Promptfoo（2026 年初）
- OpenAI 于 2026 年初收购 Promptfoo（企业级 AI 安全与评估工具），同期收购 Astral（Ruff/ruff linter 母公司）。
- **信号解读**: 提示词安全/评估工具的价值被顶级生态官方确认；"linter for AI 资产"是当前公认的赛道。
- **对我项目的影响**:
  - ✅ 赛道验证：做 Prompt Lint/安全/评估方向没错。
  - ⚠️ 差异化必须强化：Promptfoo 被 OpenAI 收购后走向企业/生态绑定，我们的差异化定位应坚持
    **本地优先（零 LLM 调用 Lint）+ 中文/国产模型生态 + 华为云/鸿蒙合规纵深 + MCP 原生**，
    这是被收购后的大厂产品短期不会回归的中立工具位。

### 1.2 2026 行业叙事："Prompt Engineering is Dead, Evals Rise"
- 多来源共识：单靠手工 prompt 不足以支撑生产系统；行业转向 **evals/回归测试/LLM-as-judge/监控**。
- 开发者痛点 Top 列表（Reddit "After 3000 hours"、Conner Ardman、treyworks、DigitalApplied 等）：
  1. 脆弱性与漂移（措辞微调/模型版本更新即静默失效）
  2. 缺回归测试（手工构造不可扩展）
  3. 指令堆叠（instruction-stacking）/ 单 prompt 过载
  4. few-shot 污染、格式靠示例（format-via-example）
  5. 模糊指令、缺输出格式规范
  6. 陈旧上下文 / context blindness
- **对我项目的影响**: 现有能力（Lint 静态检查 + 基线/语义 Diff + 声明式测试套件 + 评估）正中痛点 1/2；
  痛点 3/4/5 可转化为**新规则内容**（见改进清单 C5，先查重再新增，避免与 P001-P030 重复）。

## 二、可复用资源与"不造轮子"决策

### 2.1 模型定价数据 → 直接采用 LiteLLM 事实标准（F3 依据）
- [BerriAI/litellm](https://github.com/BerriAI/litellm) 的 `model_prices_and_context_window.json` 是**行业事实标准**
  （多家第三方定价站直接标注 "Pricing source: LiteLLM model_prices_and_context_window.json"）。
- **决策**: F3 定价外部化时**直接兼容 LiteLLM schema**（`input_cost_per_token`/`output_cost_per_token`/`max_tokens`/`max_input_tokens`），
  不自造格式；内置精简子集 + 用户侧覆盖（`.prompt-toolkit/pricing.json`）+ 可选加载 LiteLLM 全量文件。

### 2.2 OTel GenAI 语义约定 → 对齐 gen_ai.* 命名空间（F1 依据）
- GenAI 语义约定已迁至独立仓库 [open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)，
  以 Weaver 管理；`gen_ai.system`、`gen_ai.request.model`、`gen_ai.usage.input_tokens/output_tokens` 等属性进入稳定版本。
- 覆盖范围从 LLM 调用扩展到 agent 推理与多智能体工作流（与本项目 Agent/多Agent 规则域呼应）。
- **决策**: otel_tracer 的 span 属性命名对齐 semconv；保持零 SDK 硬依赖（可选 extra）。

### 2.3 LLM-as-a-Judge 去偏 → swap + 一致性过滤 + 异构集成（F2/F4 依据）
- 文献结论（Shi et al. 《A Systematic Study of Position Bias in LLM-as-a-Judge》；Xu et al. 2026；Gu et al. 2026 综述）：
  - 位置偏置是**系统性**的（非随机噪声），前沿模型裁判仍有 50%+ 位置偏置测试失败率（Adaline.ai, 2026-04）；
  - **交换位置/排列 + 聚合**是性价比最高的去偏手段；swap 结果不一致时丢弃或重问（一致性过滤）；
  - 集成有效的前提是**偏差去相关**（异构裁判），而非简单堆数量。
- **决策**: F2 实现 `swap_positions=True`（双评取一致/均值）+ `ensemble_n`（可选多裁判）+ swap 一致性过滤；
  资源: [CSHaitao/Awesome-LLMs-as-Judges](https://github.com/CSHaitao/Awesome-LLMs-as-Judges) 持续跟踪。

### 2.4 promptfoo 生态位
- promptfoo 的声明式 `promptfooconfig.yaml` 已成为红队扫描器生态的集成标准（如 argus 基于其配置）。
- **对我项目**: test_suite 的声明式 YAML 设计方向正确；保持与 promptfoo config 的**概念互通**（不强制兼容）。

## 附: C5 反模式规则查重结论(R173)

调研1.x提到的三大反模式(few-shot污染/指令堆叠/格式靠示例)经查重**均已被现有规则实质覆盖**, 不新增规则:
- 指令堆叠/约束过多 → P015(约束过多) + P004(过长)
- few-shot问题 → P018(缺失Few-shot) + P024(示例与指令不一致) + token_analyzer"过多示例(>3个可精简)"
- 格式规范缺失 → P002(缺失输出格式) + P052(格式约束, 相关但触发面不同)
结论: 遵循"质量>数量"主旋律, 反模式方向**零新增规则**。后续若发现真实缺口, 走"先查重→改写现有规则→才立新规"流程。
