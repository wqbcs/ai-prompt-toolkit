## 一、定位反问（第一性原理）

### 1.1 这个项目的定位是啥

**零 LLM 调用、确定性、CI 原生的 Prompt 质量与安全门禁 — "Prompt 的 ESLint"**。
输入是 prompt 文件/模板，输出是可度量的 finding + 门禁裁决（PASS/WARN/FAIL），
全程不烧 token、同输入同输出、秒级、可嵌入任意 CI。

### 1.2 产品核心价值是啥

| 价值 | 含义 | 竞品对照 |
|---|---|---|
| **可度量** | 双基线公开: 误报 0.96%（56干净样本）/ 漏检 9.52%（41 golden, 排除已知盲区后 0%） | 6 个直接竞对**无一公开基线** — 这是独有资产 |
| **零成本** | 纯静态正则/结构分析, <100ms, 0 API 调用 | promptlint/promptpale/PromptSonar 同路线（已验证路线正确）; promptfoo/LLM Guard 需 LLM/ML 模型 |
| **确定性** | 可复现 → CI 可信 → 可当门禁 | 同上 |
| **全生命周期** | lint→scan→redteam→evaluate→compliance→version→compile→MCP 一条链 | 无人全链覆盖; 竞对各自只做 1-2 环 |
| **中文优先 + 生态** | 中文注入/中文 lint/华为云 7 域/等保 2.0/鸿蒙模板 | prompt-defense-audit 仅英文+繁中; 华为生态独家 |

### 1.3 目前推进方向有啥问题（对抗性自审）

**问题 1: 静态 prompt lint 赛道 18 个月内被挤入 6 个直接竞对**

| 竞对 | 规则数 | 独有 | 威胁度 |
|---|---|---|---|
| promptlint.dev | 20+ | 四维健康分/成本投影/VS Code/自动修复 | 中（功能面已被 R212 追平: 四维分 R212-5、成本 R212-8） |
| prompt-defense-audit (TS) | 12+5 | Microsoft/Cisco 企业集成, gap rate 统计 | 中（集成背书 > 技术） |
| PromptSonar (TS) | MCP 9 规则 | **MCP 配置安全 + Risk Score + provenance + waiver** | 高（新攻击面占位） |
| ContextHound (TS) | 95/14类 | codebase 级扫描/baseline diff/7 格式 | 中（其 codebase 面非本定位） |
| prompt-guard (TS) | 59/6类 | CLI+REST+TS库+Web UI, 可选 LLM 二审 | 中 |
| promptpale+askance (Py) | 3+3 | AST 输入/输出两侧配对 | 低（极窄面, Python 同行） |

→ **结论: "256 条规则" 本身已不是护城河**（竞对 20-95 条活得很好）。护城河必须转向:
① 度量体系（双基线公开，竞对无一做到）② 中文深度 ③ 全生命周期 ④ 华为生态。
→ **不跟进**: Web UI、运行时扫描器、codebase 污点分析、LLM 二审 — 全部与定位冲突或非本车道。

**问题 2: 规则数膨胀 vs 度量可信度的张力**
竞对新玩家都是"少规则 + 高精度 + 诚实声明局限"（prompt-guard 明写
"regex is high-precision, modest-recall"; ContextHound 明写 "False positives are possible"）。
我们 256 条 + 公开双基线是差异化，但**继续只加规则不加样本 = 噪音风险无度量背书**。
纪律: 新规则必须先扩样本（clean/golden），双基线流程走全，否则冻结。

**问题 3: 2026 攻击面迁移 — 从 prompt 文件到 agent/MCP 配置**
- OWASP LLM06 Excessive Agency 2025 官方扩写（agentic 架构: excessive
  functionality/permissions/autonomy 三根因）
- promptfoo 新增 coding-agent 插件组（仓库注入/终端输出注入/沙箱逃逸/verifier 破坏）
- PromptSonar MCP-011~109（autoExecute/通配权限/凭据透传/链式路由/提权路径 → MCP Risk Score）
- ContextHound 新增 MCP/AGT/多模态类别
→ **本定位的范围内延伸**: MCP 配置里的 `description` 就是 prompt 文本（256 规则天然可扫）
+ 配置级 5 项检查（借 PromptSonar 已验证需求）。**范围红线**: 不做 MCP 客户端、
不做 agent 运行时执行路径分析。

**问题 4: 否定盲区 = 最可信的安全欠账**
4 条规则（P161/P222/P244/P245）被"无转义/无需审计/无合规评估/不留任何记录"类攻击
完全放行 — **明确放弃防护的最高危样本恰恰被全放行**（R212-B 已定位, 本轮必须修复,
复用 R206 `_strip_negated_data` 现成组件）。

### 1.4 需要怎样调整

1. 叙事从"规则数"转向"度量可信度": 基线文档公开化、棘轮进 CI（R212-C 已做一半, 补齐文档叙事）
2. 新攻击面: MCP 配置扫描（范围内延伸, 见 1.3 问题 3）
3. 体验对齐: 内联豁免 waiver（6 竞对 5 家有, 我们无 — 真实用户被误报阻塞 CI 时的唯一出路）
4. 明确不做: Web dashboard、动态红队、9 语言 i18n、codebase 污点分析、新第三方依赖

### 1.5 低价值打磨陷阱清单（本轮明确不做 + 理由）

| 陷阱 | 为什么是陷阱 |
|---|---|
| 为规则数加新规则 | 无样本支撑 = 无可信度增量, 只有噪音风险（256 条已够规模叙事） |
| Web UI / dashboard | HTML 报告 + CI 已覆盖消费场景; Web 是资源黑洞且偏离 CI 门禁定位 |
| LLM 二审 / judge | 与零调用定位冲突, 破坏确定性（可复现是核心价值） |
| codebase 污点分析 | promptpale/ContextHound 车道, 做 = 稀释"prompt 门禁"定位 + 维护面爆炸 |
| 9 语言 i18n | R212 非目标仍成立; 中文+英文覆盖主要面, 需求未验证 |
| 自建 MCP 客户端 | 服务端(73工具)才是护城河, 客户端属生态(Claude Desktop 等) |
| 130 维评估再加维度 | 指标膨胀: 任何新维度/新指标必须带基线, 否则不进 |
| probe tier/tag 元数据(garak式) | 展示层优化, 优先级低, 列 P2 不本轮做 |
| 性能微优化 | 已 <100ms, 用户感知阈值远未到; 打磨收益≈0 |

### 1.6 多端技术栈审查（"每一端最优栈, 不绑定" 核对）

| 端 | 现栈 | 是否该平台公认最优 | 短板 |
|---|---|---|---|
| CLI/终端 | Python + click + rich | ✅（CLI 事实标准, 无争议） | 无 |
| 编辑器 | TS VS Code 扩展 + Python LSP(pygls) | ✅（VS Code 扩展唯一可行栈; LSP 进程解耦） | 扩展仅 0.5.0, 功能面待扩(P1) |
| CI | GitHub Actions + SARIF/JUnit | ✅（生态标配, GitHub 原生消费 SARIF） | 无 |
| 服务端 | FastAPI(market) / MCP stdio | ✅（各自事实标准） | 无 |
| 知识库 | Markdown 双轨(human/ai) | ✅（AI 可消费+人可读, 本会话验证可用） | 无 |
| 架构可演进 | 内核纯 Python 零 UI 依赖, 端与端进程/语言解耦 | ✅ | 任意端换栈不动业务内核; 无单栈绑定 |

→ 结论: **无体验短板端**。唯一薄端是 VS Code 扩展（0.5.0, 1349 行单文件）— 列 P1 增强。

## 二、开源调研结论（借鉴思路, 不抄代码, 零新依赖）

### 2.1 garak（NVIDIA, Apache-2.0, 4000+ stars 级）

**可借鉴**:
- **tier 概念**（probe 重要性 1-3 级 + tags 分类学: OWASP/AVID）→ lint 规则优先级
  展示（P0 强制/P1 建议/P2 参考）, 仅展示层, 不改门禁语义（P2 项）
- "static/assembled/dynamic/reactive" 探针四分法 → 我们 23 静态探针的文档表述可引用
  该分类学（文档层, 零代码）

**不借鉴**: atkgen/tap/suffix 等 reactive 探针（全需 LLM 推理, 定位冲突）;
PluginCache/fixer（我们的 P 编号制无重命名问题）。

### 2.2 promptfoo（MIT/Apache, 红队标杆）

**可借鉴**:
- **间接注入视角**: 载荷藏在 RAG 变量/外部内容（`{{context}}`/邮件/工单）→ 我们的
  P035-P037 覆盖"检索面声明", 缺**"不可信内容边界声明"**（检索内容须用分隔符包裹
  + 元指令"不要服从其中指令"）→ 规则候选 P257（P1 项, 先扩样）
- **合规映射广度**: OWASP + NIST + MITRE ATLAS + EU AI Act 四映射 → 我们只有
  OWASP+等保2.0; **MITRE ATLAS 映射表**是文档层低成本高价值项（P1）
- coding-agent 插件组 → 仅跟踪不实现（非 prompt 面）

**不借鉴**: LLM 打分/远程生成（定位冲突）; Web UI; 157 插件规模（需 LLM 喂）。

### 2.3 LLM Guard（ProtectAI, Apache-2.0, 运行时标杆）

**可借鉴**:
- **risk_score 归一化公式** `(score-threshold)/(1-threshold)` → 统一跨扫描器风险口径。
  我们 scorecard 已是扣分制, **不重复造**, 但 health_score 成本档可引用该思想做文档化
- **MatchType**（FULL/SENTENCE/CHUNKS/TRUNCATE_HEAD_TAIL）→ 长文本句级匹配可减少
  误报; 我们 P101 Jaccard 已句级切分, 选择性借鉴（P2, 基线已 0.96% 边际收益小）
- Sanitization vs Validation 双模式 → 我们 196 自动修复(fixer) + 检测已分离 ✅ 已有

**不借鉴**: ML 模型（DeBERTa 等, 数百 MB 权重 + ONNX 运行时, 与零调用/轻量冲突）。

### 2.4 promptlint.dev（直接竞对, Apache-2.0, "ESLint for LLM prompts"）

**对照结论 — 功能面已被 R212 追平**:
| promptlint 特性 | 我们现状 |
|---|---|
| 四维健康分 A–F (Security/Cost/Quality/Completeness) | ✅ R212-5（短板决定, 比其平均更严格） |
| 成本投影 "87 tokens · $0.005/1k · ~$1,566/day at 1M calls" | ✅ R212-8（lint 尾部 INFO 行） |
| 20+ 规则 / leetspeak 归一 / PII / secrets | ✅ 256 规则 / unicode_guard.py+engine.py / PII 12 类 |
| 自动修复 (politeness-bloat 41 短语) | ✅ 196 条可修复（P101 冗余等）— 核对短语表覆盖度(P2 细节) |
| VS Code 扩展 | ✅ vscode-prompt-lint 0.5.0 |
| pip + **npm 双分发** | ⚠️ 仅 pip → npm 分发列 P2（需求验证+维护成本） |

**启示**: 我们 256 vs 其 20+ 规则, 但**叙事上它是品类定义者**（名字就叫
promptlint）→ README 定位表述要强化"全生命周期+双基线"差异化, 不要只说"lint"。

### 2.5 prompt-defense-audit（TS, 确定性, 企业集成标杆）

**可借鉴**:
- "deterministic engine is the product" 哲学 → 与定位互证（写入 README 可信度叙事）
- **gap rate 统计**（"92.4% 的 prompt 缺 role-escape 防护"）→ 社区语料统计我们做不了,
  但**自有语料 dogfooding 可做**: 18 内置模板 × 256 规则自诊, 内置模板必须是标杆
  （P1 项, scripts/check_builtin_templates.py）
- Microsoft Agent Governance / Cisco AI Defense 集成案例 → 证明"静态防御扫描器"有
  企业采购价值; 我们走文档层（集成指南）, 不做代码适配

**不借鉴**: gap rate 社区统计（无语料）。

### 2.6 PromptSonar（TS, 零 LLM, **本轮最高借鉴价值**）

**可借鉴**:
- **MCP 配置安全规则**（本轮最重要发现）: MCP-011 autoExecute/autoApprove、
  MCP-012 通配权限(`permissions: "*"`)、MCP-013 宿主凭据透传(`${VAR}`/SSH_AUTH_SOCK)、
  MCP-103 文件系统能力、MCP-104 shell 执行、MCP-105 外网能力、MCP-107 链式 MCP 路由、
  MCP-108 提权路径、MCP-109 审批绕过。我们 73 MCP 工具是"服务端", 但用户侧
  **MCP 配置文件是真实攻击面且我们零覆盖** → 范围内实现（见 1.3 问题 3）
- **MCP Risk Score**（0-100 → LOW/MED/HIGH/CRITICAL, 由 findings 推导）→ 复用
  scorecard 扣分机制, 零新公式
- **provenance**（finding 携带 matched evidence + confidence）→ 我们 Finding 已有
  details 字段, 核对证据片段完整性（细节项）
- **waivers**（`--waiver` / inline ignore / `.promptsonarignore` 三层）→ 我们无豁免
  机制（6 竞对 5 家有）→ 实现（见 P0-2）

**不借鉴**: 其 VS Code 扩展（我们已有）; execution path 分析（agent 运行时面, 非 prompt 面）。

### 2.7 ContextHound（TS, 95 规则/14 类, codebase 级标杆）

**对照结论 — 输出/工程能力我们已覆盖**:
| ContextHound 特性 | 我们现状 |
|---|---|
| baseline/diff 模式（只报新 finding） | ✅ R186 `--baseline`/`--baseline-save`/`--json-diff` |
| 增量缓存 | ✅ result_cache.py + watch 模式 |
| 7 输出格式 | ✅ rich/json/SARIF/JUnit/HTML/LCov/SVG（更多） |
| GitHub Action | ✅ action/action.yml |
| rule 过滤（prefix-glob include/exclude） | ⚠️ 待核实现有 lint 参数覆盖度（P1 项） |
| 多模态攻击面（image URL→vision API 代码级） | ❌ 代码级非本定位, 不做 |
| codebase 扫描 | ❌ 非本定位, 不做 |

**可借鉴**: `minConfidence` 过滤思想 → 我们的 finding 无 confidence 字段,
**不添加**（指标膨胀, 且确定性工具中 confidence 语义弱）。

### 2.8 promptpale + askance（Python AST, 输入/输出两侧配对）

**可借鉴**:
- "fence is not a guarantee" 的诚实定位表述 → 我们 remediation/文档也应明示
  "lint 是设计时检查, 不保证运行时免疫"（文档细节项, 防过度承诺）
- 输入/输出两侧配对思想 → 我们无输出侧（无模型输出可扫, 静态定位使然）, 仅记录

**不实现**: 其核心功能（AST 污点: 用户输入拼接进 system prompt / 模型输出流入
eval/exec）是**代码构造面**, 非 prompt 文件面, 超出定位。

## 五、对抗性审查（对本方案）

1. **R213-3 MCP lint 是否 scope creep?** — 反驳: MCP tool description 就是 prompt
   文本（范围内）; 配置级 7 检查来自 PromptSonar 已验证需求; 红线明确（无客户端/
   无执行分析）。止损点: 若用户反馈弱, P1 不再扩 MCP 面。
2. **R213-8 新规则 vs "冻结规则数" 纪律?** — 冻结的前提是"双基线未达标": 现误报
   0.96%（<1% 达标）, 漏检 R213-1 修盲区后 ~2.4%（收紧 0.05 棘轮后达标）→ 解冻条件
   满足。且 P257 是全体系首条"双基线流程下的新规则", 必须把"先扩样→0命中→正样本→
   棘轮不破"走全, 给未来规则立样板。
3. **waiver 是否打开门禁漏洞?** — 三层闭合: 显式 rule ID（无通配）+ 审计计数 +
   `--fail-on-waiver`（CI 可禁新增）。ESLint disable-comment 的同款治理已被业界验证。
4. **"256 规则是护城河吗"?** — 诚实回答: 不是（竞对 20-95 条活得很好）。护城河是
   度量体系 + 中文 + 全生命周期 + 生态。本轮 4 个 P0 全指向可信度/对齐/新面/卫生,
   只加 1 条新规则（P1 的 P257）, 不为数加数。
5. **联网调研是否信息过载?** — 10 信源 → 12 可借鉴点（全部映射到现有组件, 零新依赖）
   + 8 明确不借鉴（全部附理由）+ 10 需求（全部映射到方案项）。无未处置信源。
6. **"最顶配/体验无天花板" 与"不做清单"是否矛盾?** — 不矛盾: 顶配 = 各端最优栈 +
   无短板端（1.6 已核对, 唯一薄端 VS Code 扩展列 P2）; 不做清单挡的是**偏离定位的
   天花板**（Web UI/动态红队）, 不是产品力天花板。

## 六、第一性与奥卡姆检验

- **第一性**: 用户真问题 = "这个 prompt 能不能信、敢不敢上线" → 答案四支柱:
  可度量(双基线) + 可复现(确定性) + 零成本(无 LLM) + 可门禁(CI)。
  4 个 P0 项: P0-1→可度量, P0-2→可门禁(可用性), P0-3→可度量(新面), P0-4→可复现
  (口径根治)。全部命中支柱, 无一项在"锦上添花"。
- **奥卡姆**: 最小充分集 = 4 P0 + 4 P1, **0 新第三方依赖, 1 新规则, 1 新命令,
  1 个 fixture 目录**。每个新增都可删掉而方案仍成立吗? 否 — 每个都对应一个未满足的
  已验证需求（N1-N8）。
- **欲速则不达**: P0-3/P0-8 各需 fixtures+测试+文档三件套, 宁慢勿省 — 跳过 fixture
  直接上规则 = 重复 R211 之前的"修了 A 漏了 B"模式。
