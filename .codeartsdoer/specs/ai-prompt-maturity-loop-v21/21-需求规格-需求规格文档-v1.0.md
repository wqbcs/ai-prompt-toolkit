# 2. 行业痛点调研

## 2.1 Prompt工程领域核心痛点

基于OWASP LLM Top 10 2025、promptfoo社区Issue、garak Discussions、Langfuse Roadmap分析：

| 痛点编号 | 痛点描述 | 影响范围 | 严重程度 |
|----------|----------|----------|----------|
| P01 | **Prompt注入防御难**: OWASP LLM01，攻击手段日新月异，静态规则覆盖有限 | 全行业 | CRITICAL |
| P02 | **Prompt质量不可量化**: 缺乏统一的Prompt质量度量标准，团队无法做数据驱动决策 | 企业用户 | HIGH |
| P03 | **Prompt版本混乱**: 多人协作时Prompt版本冲突，缺乏diff/merge/revert能力 | 团队用户 | HIGH |
| P04 | **评估成本高**: LLM API调用费用高，62维度全量评估耗时长、费用高 | 企业用户 | HIGH |
| P05 | **红队覆盖不足**: 已有Probe远不能覆盖新型攻击(如多模态注入/Agent注入) | 安全用户 | HIGH |
| P06 | **CI/CD集成门槛高**: 需要写YAML配置文件，缺乏低代码/零代码集成方案 | DevOps | MEDIUM |
| P07 | **本地模型支持弱**: Ollama/LM Studio等本地模型无法接入测试 | 开发者 | MEDIUM |
| P08 | **Prompt可观测性差**: 生产环境Prompt调用缺乏tracing/metrics/alerting | 运维 | MEDIUM |
| P09 | **多语言翻译质量低**: 规则翻译无法处理语境差异，LLM辅助翻译缺失 | 国际化用户 | LOW |
| P10 | **模板市场生态弱**: 缺乏社区贡献/评分/认证机制 | 社区 | LOW |

## 2.2 鬼才洞察：隐形痛点

| 隐形痛点 | 描述 | 鬼才巧思 |
|----------|------|----------|
| "写完Prompt不知道好不好" | 用户写完Prompt后没有即时反馈，必须手动运行评估 | 编辑时实时Lint+评分浮层，像IDE的实时语法检查 |
| "安全扫描结果看不懂" | 15条INJ规则结果对非安全专家是黑话 | 每条Finding附加"人话解释"+修复步骤向导 |
| "A/B测试不会设计" | 用户不知道怎么设计对照组、怎么选统计方法 | 智能推荐实验设计，一键生成TestConfig |
| "红队报告只会PASS/FAIL" | 漏洞报告缺乏修复优先级和具体修复方案 | 漏洞分级+修复SOP+自动生成防御Prompt |
| "模板太多不知道选哪个" | 51个场景模板没有推荐机制 | 基于用户上下文(模型/行业/语言)智能推荐模板 |

- **描述**: 将5种Probe扩展至50+，覆盖OWASP LLM Top 10 2025全部风险项，参考garak的probe架构
- **用户场景还原**: 安全工程师使用redteam命令扫描模型，当前仅5种攻击向量，无法覆盖DAN/jailbreak/编码绕过/多模态注入等主流攻击，安全报告可信度低
- **参考开源项目**: 
  - garak (https://github.com/NVIDIA/garak) — 100+Probe，probe/detector/harness三层架构
  - promptfoo redteam — 30+红队策略，Web UI可视化
- **预期效果**: Probe覆盖从5→50+，漏洞检出率提升300%+，OWASP LLM Top 10覆盖100%
- **量化指标**: Probe数量≥50，OWASP LLM01-LLM10每项至少2个Probe
- **优先级**: P0
- **预估工作量**: 8人日
- **赛事贴合**: ★★★★★（安全赛道核心能力）

# 6. EARS格式需求

## 6.1 P0级需求

### REQ-P0-01: 红队Probe扩展

**当** 用户执行`prompt-cli redteam`命令，**系统应当** 加载至少50种Probe探测器，覆盖OWASP LLM Top 10 2025全部10项风险，**如果** 目标模型支持在线调用，**则** 在线执行探测并返回漏洞报告，**否则** 执行离线静态分析。

**验收标准**:
1. Probe总数≥50，每类至少5个Probe
2. OWASP LLM01-LLM10每项至少2个Probe
3. 新增Probe类型: DAN(10种)/越狱(8种)/编码绕过(5种)/多轮诱导(5种)/多模态注入(3种)/Agent注入(5种)/供应链(3种)/隐私泄露(5种)/有害内容(3种)/幻觉(3种)
4. 每个Probe可独立启用/禁用
5. 兼容现有redteam命令接口

### REQ-P0-02: 多Provider接入

**当** 用户配置Provider，**系统应当** 支持至少15种Provider类型，**如果** 用户选择本地模型Provider(Ollama/LM Studio)，**则** 自动检测本地服务端口并建立连接，**否则** 使用httpx连接池调用云端API。

**验收标准**:
1. Provider总数≥15
2. 新增: Ollama/LM Studio/Azure OpenAI/AWS Bedrock/Google Gemini/Cohere/LiteLLM Proxy/vLLM/HuggingFace Inference/Groq/Mistral/本地REST
3. 本地Provider支持自动端口检测+健康检查
4. BaseProvider统一接口，新增Provider仅需实现`invoke()`方法
5. 所有Provider支持CostTracker费用追踪

### REQ-P0-03: Playground React化

**当** 用户访问Playground Web UI，**系统应当** 渲染React组件化界面，使用Tailwind CSS+shadcn/ui组件库，**如果** 用户调整浏览器窗口，**则** 界面自适应响应式布局，**否则** 保持默认布局。

**验收标准**:
1. React组件≥20个，使用TypeScript+Tailwind+shadcn/ui
2. Compile/Lint/Scan/Evaluate 4个Tab保持功能完整
3. 新增: 结果保存/分享、多模板对比、主题切换
4. Lighthouse性能评分>90
5. 首屏加载<2s
6. 后端FastAPI API保持向后兼容

## 6.2 P1级需求

### REQ-P1-01: Prompt版本管理

**当** 用户修改Prompt模板并保存，**系统应当** 自动创建新版本快照，**如果** 用户查看历史版本，**则** 显示版本diff和元数据，**否则** 仅显示最新版本。

**验收标准**:
1. 版本号自动递增(v1→v2→v3)
2. 支持版本diff(高亮变更行)
3. 支持版本回滚
4. 版本元数据: 作者/时间/评分/变更说明
5. 版本存储使用SQLite

### REQ-P1-02: 评估结果持久化

**当** 用户执行62维度评估，**系统应当** 将评估结果持久化存储，**如果** 用户查看历史评估，**则** 显示趋势图和回归告警，**否则** 仅显示当前评估结果。

**验收标准**:
1. 评估结果存储到SQLite
2. 支持历史趋势折线图(按时间/版本)
3. 回归检测: 任一维度评分下降>15%自动告警
4. A/B对比: 两个版本评分并排对比
5. CLI/Playground均可查看历史

### REQ-P1-03: A/B测试高级统计

**当** 用户配置A/B测试，**系统应当** 支持贝叶斯推断/Thompson Sampling/序贯分析三种高级方法，**如果** 样本量<30，**则** 推荐使用贝叶斯方法，**否则** 推荐频率学派方法。

**验收标准**:
1. 新增贝叶斯A/B测试(后验概率+可信区间)
2. 新增Thompson Sampling多臂老虎机
3. 新增序贯分析(SPRT)
4. 统计方法推荐器: 根据样本量自动推荐
5. 与现有t-test/Mann-Whitney U/Cohen's d共存

### REQ-P1-04: CI/CD低代码集成

**当** 用户在GitHub仓库配置CI/CD，**系统应当** 提供一行配置即可集成的GitHub Action/Docker/pre-commit hook，**如果** 用户选择GitHub Action，**则** 自动安装prompt-lint Action并运行，**否则** 提供Docker镜像或pre-commit hook。

**验收标准**:
1. GitHub Action发布到Marketplace
2. Docker镜像<200MB，支持`docker run`一键扫描
3. pre-commit hook: `.pre-commit-config.yaml`配置
4. 三种方案共享同一套引擎逻辑
5. 含示例YAML配置和文档

### REQ-P1-05: Finding可读性增强

**当** 用户查看安全扫描结果，**系统应当** 为每条Finding提供三段式描述(是什么/为什么/怎么修)，**如果** Finding存在自动修复方案，**则** 显示一键修复按钮，**否则** 显示手动修复步骤。

**验收标准**:
1. 每条Finding包含: 问题描述(人话)/风险原因/修复步骤
2. 风险等级可视化(CRITICAL红色/HIGH橙色/MEDIUM黄色/LOW绿色)
3. 可修复Finding显示一键修复按钮
4. CLI/HTML报告/Playground三种输出格式均支持
5. 修复步骤可执行(调用Fixer)

### REQ-P1-06: Lint规则P031-P040

**当** 用户对RAG/Agent/Multimodal类型Prompt执行Lint，**系统应当** 检测P031-P040规则，**如果** 模板template_type为rag，**则** 执行RAG专属规则，**否则** 执行通用规则。

**验收标准**:
1. 新增10条规则(P031-P040)
2. 3个新分类: Agent(4条)/RAG(3条)/Multimodal(3条)
3. 支持template_type感知(与P001-P030一致)
4. 至少2条规则支持自动修复
5. 规则集(recommended/strict)同步更新

### REQ-P1-07: 模板市场REST API

**当** 用户访问模板市场API，**系统应当** 提供搜索/过滤/分页/评分/收藏等REST端点，**如果** 用户搜索关键词，**则** 返回匹配模板列表(支持模糊搜索)，**否则** 返回全部模板(分页)。

**验收标准**:
1. REST API≥10个端点: 搜索/列表/详情/评分/收藏/提交/审核/部署/分类/标签
2. SQLite持久化(替代JSON)
3. 模糊搜索(标题+描述+标签)
4. 分页(默认20/页，最大100/页)
5. FastAPI自动生成OpenAPI文档

## 6.3 P2级需求

### REQ-P2-01: 实时Lint增强

**当** 用户在VS Code中编辑Prompt文件，**系统应当** 在500ms内返回Lint结果，**如果** 文件变更，**则** debounce 300ms后重新Lint，**否则** 保持上次结果。

### REQ-P2-02: 红队报告增强

**当** 用户查看红队报告，**系统应当** 为每个漏洞显示CVSS风格评分+修复SOP+防御Prompt，**如果** 漏洞可自动修复，**则** 生成防御Prompt并提示应用，**否则** 仅显示手动修复步骤。

### REQ-P2-03: LLM辅助翻译

**当** 用户执行i18n翻译，**系统应当** 使用LLM辅助翻译并保留术语一致性，**如果** 术语表中存在术语，**则** 优先使用术语表翻译，**否则** 使用LLM翻译并标记为"待审校"。

### REQ-P2-04: 性能基准CI集成

**当** PR提交到main分支，**系统应当** 自动运行11项基准测试，**如果** 性能回归>10%，**则** 在PR评论中告警，**否则** 记录基准结果。

### REQ-P2-05: 评估智能降频

**当** 用户对已评估过的模板再次评估，**系统应当** 仅评估变更相关的维度，**如果** 模板内容未变更，**则** 直接返回缓存结果，**否则** 仅重新评估受影响维度。

### REQ-P2-06: 智能模板推荐

**当** 用户浏览模板市场，**系统应当** 根据用户上下文(模型/行业/语言)推荐最匹配的3个模板，**如果** 用户无上下文信息，**则** 推荐评分最高的3个模板，**否则** 基于上下文匹配推荐。

## 6.4 P3级需求

### REQ-P3-01: Prompt自动优化

**当** 用户对Prompt执行自动优化，**系统应当** 通过评估反馈自动迭代改进Prompt(≤5轮)，**如果** 优化后评分提升≥1.0分，**则** 推荐采用优化版本，**否则** 提示优化效果有限。

### REQ-P3-02: 约束生成引擎

**当** 用户使用约束生成功能，**系统应当** 确保LLM输出符合指定的正则/CFG/JSON Schema，**如果** 约束为JSON Schema，**则** 生成严格符合Schema的JSON输出，**否则** 按正则或CFG约束生成。

### REQ-P3-03: 可观测性Tracing

**当** 用户启用可观测性模式，**系统应当** 记录每次Prompt调用的完整Trace(编译→Provider→评估)，**如果** 调用延迟超过阈值，**则** 自动告警，**否则** 记录Trace到存储。

### REQ-P3-04: 鸿蒙模板深化

**当** 用户搜索鸿蒙相关模板，**系统应当** 提供至少20个鸿蒙场景模板，**如果** 用户开发HarmonyOS NEXT应用，**则** 推荐元服务/ArkUI-X/分布式场景模板，**否则** 推荐基础ArkTS模板。

### REQ-P3-05: 多模态Prompt检测

**当** 用户对多模态Prompt(含图片)执行Lint，**系统应当** 检测5条多模态Lint规则，**如果** Prompt包含图片引用，**则** 检测图片描述缺失/图文不一致等规则，**否则** 仅执行文本规则。

### REQ-P3-06: 情感化彩蛋

**当** 用户获得Lint满分(100分)或零问题时，**系统应当** 播放庆祝动画(撒花/彩虹)，**如果** 用户首次使用工具，**则** 显示欢迎引导，**否则** 静默运行。
