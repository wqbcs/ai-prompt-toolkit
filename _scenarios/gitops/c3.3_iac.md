# 基础设施即代码

## 场景概述

基础设施即代码（Infrastructure as Code, IaC）是GitOps实践的重要补充，将云资源、网络、存储等基础设施的配置以代码形式管理。本场景覆盖Terraform、Pulumi和华为云ROS三大IaC工具的核心实践，以及状态管理和漂移检测的关键问题。

## 核心覆盖

- **Terraform**：声明式HCL语言，Provider生态丰富，State管理成熟，是IaC事实标准
- **Pulumi**：通用编程语言（Go/Python/TypeScript）定义基础设施，支持测试和复用
- **华为云ROS**：资源编排服务，声明式模板+资源栈管理，与华为云深度集成
- **状态管理**：远程状态存储、状态锁定、状态隔离和跨团队共享
- **漂移检测**：基础设施状态偏离IaC定义的检测和修复策略

## 🚨 陷阱（5项）

### 陷阱1：状态文件锁定冲突

Terraform状态文件在远程后端（如S3/OBS）存储时依赖DynamoDB/Redis实现锁定。当锁定服务不可用或网络分区时，可能出现锁定泄漏（stale lock），导致所有后续操作被阻塞。多人协作场景下，长时间运行的Apply操作持有锁定，其他开发者无法执行Plan。更危险的是，部分团队在CI流水线中未正确配置状态锁定，并发流水线同时修改状态导致状态文件损坏。

### 陷阱2：Terraform Provider版本不一致

团队不同成员使用不同版本的Terraform Provider，导致Plan结果不一致。开发者A本地使用华为云Provider v1.50，CI环境使用v1.48，同一份代码产生不同的Plan。Provider版本未在代码中显式声明（缺少`required_providers`配置），Terraform自动使用最新版本，可能引入不兼容变更。更严重的是，State文件中记录的Provider版本与当前使用的版本不匹配时，可能导致状态迁移失败。

### 陷阱3：华为云ROS模板语法错误

ROS模板使用JSON/YAML格式，语法错误排查困难。特别是Fn::Sub、Fn::Join等内部函数的嵌套使用，容易产生引号转义、缩进错误。ROS模板的依赖关系声明不完整（DependsOn缺失），导致资源创建顺序错误。跨Region部署时，不同Region的资源引用和输出值传递容易出错。ROS模板验证工具不如Terraform的`terraform validate`成熟，很多错误仅在部署时才暴露。

### 陷阱4：漂移检测与自动修复冲突

IaC漂移检测发现资源被手动修改后，自动修复（terraform apply）会覆盖手动修改。但某些手动修改是故意的（如紧急扩容、安全补丁），自动修复会回退这些必要变更。更复杂的情况是，漂移检测发现AWS Console修改了资源属性，但Terraform代码中该属性由`ignore_changes`排除，导致检测与修复行为不一致。当多个IaC工具管理同一资源时，A工具的自动修复可能覆盖B工具的修改。

### 陷阱5：IaC模块版本失控

共享IaC模块未使用版本标签，所有消费者引用main分支最新代码。模块维护者推送破坏性变更后，所有引用该模块的项目同时报错。模块的git引用使用commit SHA保证版本固定，但无法获知可用的新版本。私有模块仓库缺乏访问控制和版本管理策略，任何人可发布不兼容更新。模块间依赖形成深层嵌套，顶层模块的版本升级需要逐级验证所有传递依赖的兼容性。

## ⚡ 性能（5项）

### 性能1：Terraform Plan执行优化

- 使用`-target`参数限定Plan范围，大型State文件中仅检查变更相关资源
- 启用`-refresh=false`跳过状态刷新，配合手动`terraform refresh`在低峰期执行
- State文件按环境/组件拆分，单个State管理资源数控制在500以内
- Provider配置启用`parallelism`参数控制并发API调用数，默认10，华为云API限流场景下调至3-5
- 使用`terraform plan -out=tfplan`保存Plan结果，Apply时直接使用避免重复Plan

### 性能2：状态文件存储优化

- 远程状态后端选择低延迟存储：AWS S3、华为云OBS、阿里云OSS，避免跨Region访问
- State文件启用版本控制，但定期清理历史版本释放存储空间
- 大型State文件考虑按组件拆分为多个State，使用`terraform_remote_state`跨State引用
- State文件启用服务端加密（SSE-S3/SSE-KMS），加密对性能影响可忽略
- 状态文件压缩：Terraform 1.5+支持State文件JSON压缩，减少传输和存储开销

### 性能3：华为云ROS部署效率

- ROS资源栈部署启用`TimeoutInMinutes`避免无限等待，设置为预期时间的1.5倍
- 使用`DeletionPolicy`控制资源删除行为，Retain策略减少不必要的资源重建
- 大型模板拆分为嵌套资源栈（NestedStack），并行部署无依赖的子栈
- ROS模板参数使用DefaultValue减少交互式输入，适配CI/CD自动化部署
- 启用资源栈策略（StackPolicy）保护关键资源不被意外更新或删除

### 性能4：IaC模块复用

- 建立组织级私有模块仓库（Terraform Private Registry/华为云ROS模板库），版本化发布
- 模块接口设计遵循单一职责原则，每个模块管理一组强相关资源
- 模块输入变量设置合理默认值，减少消费者必须提供的参数数量
- 模块输出值包含所有下游可能需要的属性，避免消费者通过data源二次查询
- 使用Terratest或Pulumi Automation API对模块进行自动化测试，确保版本发布质量

### 性能5：漂移检测频率优化

- 环境差异化检测频率：生产环境每4小时、预发布每8小时、开发环境每日
- 使用`terraform plan -detailed-exitcode`区分"无变更"和"有漂移"两种状态
- 漂移检测结果缓存，未变更的资源跳过重复检测
- 按资源类型设置不同检测策略：计算资源高频检测、存储资源低频检测
- CI流水线集成漂移检测，仅在有代码变更时触发全量Plan

## 🔒 安全（3项）

### 安全1：状态文件中敏感数据泄露

Terraform State文件默认以明文存储所有资源属性，包括RDS密码、AK/SK等敏感信息。远程State后端权限配置不当，任何有存储读取权限的人员均可获取敏感数据。State文件版本历史中同样包含敏感信息，即使当前版本已移除，历史版本仍可访问。`terraform show`和`terraform output`命令可能意外暴露敏感值。

**应对措施**：State后端启用服务端加密和严格访问控制；敏感值使用` sensitive = true`标记并在output中标记`nonsensitive`时谨慎使用；使用Vault或华为云DEW管理敏感值，IaC代码通过data源引用；定期审计State文件访问日志。

### 安全2：IaC模板注入攻击

Terraform的`templatefile()`函数和`heredoc`字符串可能遭受模板注入。用户输入直接拼接到Cloud-Init脚本、IAM策略等模板中，未经过滤和转义。Pulumi使用通用编程语言，理论上可执行任意代码，CI环境中运行不受信任的Pulumi项目存在代码执行风险。华为云ROS模板的`Fn::Sub`变量替换同样可能注入恶意内容。

**应对措施**：所有用户输入经过验证和转义后再传入模板；Terraform使用`templatefile()`而非字符串拼接；Pulumi项目在沙箱环境中执行；CI流水线限制IaC代码的执行权限；ROS模板使用`AllowedValues`约束参数取值。

### 安全3：华为云ROS权限过大

ROS资源栈使用具有管理员权限的AK/SK部署，可创建任意华为云资源。资源栈策略未限制可创建的资源类型和数量，可能导致资源超配或创建非预期资源。跨账号部署时，ROS的代理角色（Delegate）权限过大，可操作被代理账号的所有资源。

**应对措施**：为ROS创建专用IAM用户/委托，遵循最小权限原则限定可操作的服务和操作类型；启用资源栈策略限制可创建的资源类型；跨账号部署使用细粒度委托而非全局代理；ROS操作启用CTS审计追踪。

## 🔍 故障排查（5项）

### 故障排查1：Terraform Apply失败

| 失败阶段 | 典型错误 | 排查步骤 |
|---------|---------|---------|
| Init | Provider下载失败 | 检查网络代理配置；确认Provider Registry可达；设置`TF_PLUGIN_CACHE_DIR`使用本地缓存 |
| Plan | State锁定超时 | 检查DynamoDB/Redis锁定表状态；手动释放stale lock；确认无其他进程持有锁定 |
| Apply | 资源创建API错误 | 检查华为云API错误码和消息；确认IAM权限和配额；检查参数格式是否正确 |
| Apply | 依赖循环 | 检查`depends_on`和隐式依赖是否形成环；使用`terraform graph`可视化依赖关系 |
| Apply | 部分失败 | 检查State文件是否已更新部分资源；使用`-target`逐个修复失败资源 |

### 故障排查2：状态文件损坏

- **症状识别**：`terraform plan`报错"state was modified by another process"或"invalid state file"
- **版本回退**：从S3/OBS版本历史恢复到最近一个有效的State文件版本
- **State重建**：使用`terraform import`逐个导入已有资源重建State，工作量大但可靠
- **State移动**：`terraform state mv`在不同State间迁移资源，修复State结构错误
- **预防措施**：State后端启用版本控制和加密；CI流水线在Apply前自动备份State；禁止直接手动编辑State文件

### 故障排查3：华为云ROS部署回滚

1. **查看资源栈事件**：ROS控制台→资源栈→事件，查看每个资源的创建/更新状态和错误信息
2. **回滚行为分析**：ROS默认在部署失败时自动回滚，确认回滚是否成功执行
3. **回滚失败处理**：回滚失败时需要手动修复或联系华为云支持，使用`DisableRollback: true`阻止自动回滚以便排查
4. **资源残留清理**：回滚后检查是否有未清理的残留资源，手动删除或使用`DeletionPolicy: Retain`保护
5. **模板修正**：根据错误信息修正模板，使用`ros template validate`预验证

### 故障排查4：漂移检测超时

- **State过大**：单个State管理超过1000个资源时，`terraform refresh`可能超时，拆分State
- **API限流**：华为云API调用频率超限，在Provider配置中设置`max_retries`和增加请求间隔
- **网络延迟**：跨Region访问资源，使用同Region的运行环境执行Plan
- **依赖链过长**：`data`源查询链过长，减少不必要的data源或使用缓存
- **并发冲突**：CI中多个Plan任务并发运行，增加状态锁定超时时间或串行执行

### 故障排查5：IaC模块依赖冲突

| 冲突类型 | 表现 | 解决方案 |
|---------|------|---------|
| Provider版本冲突 | 模块A要求v1.50，模块B要求v1.48 | 在根模块统一声明Provider版本，子模块使用`configuration_aliases` |
| 资源命名冲突 | 不同模块创建同名资源 | 模块内资源命名添加模块前缀，使用`name_prefix` |
| 输出值类型不匹配 | 模块升级后输出值类型变更 | 模块遵循语义版本控制，Major版本变更允许破坏性更新 |
| 循环依赖 | 模块A的输出被模块B引用，反之亦然 | 引入中间data源或重构模块边界，消除双向依赖 |
| State引用不一致 | `terraform_remote_state`引用已删除的State | 使用明确的State Key约定，引用前验证State存在性 |

## 🔄 替代方案（3项）

| 维度 | Terraform | Pulumi | 华为云ROS |
|------|-----------|--------|-----------|
| **语言** | HCL声明式语言 | Go/Python/TypeScript等通用语言 | JSON/YAML声明式模板 |
| **学习曲线** | 中等，HCL语法简洁但高级用法复杂 | 因语言而异，熟悉Go/Python的开发者上手快 | 较低，模板语法简单但内部函数需学习 |
| **状态管理** | 自带State管理，支持多种远程后端 | 自带State管理，Pulumi Cloud或自托管 | 资源栈自动管理，无需额外配置 |
| **Provider生态** | 最丰富，覆盖几乎所有云厂商和SaaS | 基于Terraform Provider转换，生态兼容 | 仅华为云服务，第三方资源需自定义 |
| **测试能力** | Terratest（Go）或pytest-terraform | 原生支持单元测试和集成测试 | 无原生测试框架，需自行搭建 |
| **团队协作** | Terraform Cloud/Enterprise | Pulumi Cloud/Enterprise | 华为云控制台 + ROS API |
| **成本管理** | 开源免费，Cloud/Enterprise付费 | 个人免费，Team/Business付费 | 按资源栈数量和API调用计费 |
| **适用场景** | 多云/混合云场景，成熟IaC实践的团队 | 偏好编程语言定义基础设施的开发团队 | 华为云专属场景，追求低运维成本 |

## ⚠️ 已知限制

1. **Terraform State是单点故障**：State文件损坏或丢失将导致IaC管理完全失效，恢复成本极高。虽然远程State后端提供高可用存储，但State逻辑一致性无法保证，部分Apply失败可能导致State与实际资源不一致
2. **Pulumi对华为云支持滞后**：Pulumi的华为云Provider基于Terraform Provider转换，新服务和新特性通常比Terraform Provider晚1-3个月。华为云ROS对新服务的支持最快，但功能仅限于华为云生态
3. **IaC漂移检测存在盲区**：`terraform plan`只能检测Terraform管理资源的漂移，无法发现Terraform代码中未定义但实际存在的"幽灵资源"。需要配合云厂商的Config服务（如华为云Config）实现全量漂移检测
4. **IaC模块测试成本高**：完整的IaC模块测试需要实际创建云资源，费用高且耗时长。Mock测试无法覆盖Provider的实际行为差异，测试可靠性不足。Plan测试（`terraform plan -json`输出断言）是折中方案但覆盖面有限
5. **华为云ROS跨云支持缺失**：ROS仅支持华为云资源，多云/混合云场景无法使用统一模板管理。需要跨云编排时，必须结合Terraform或Pulumi实现多云资源管理
