# c2.2 网络故障注入

## 概述

本场景覆盖网络层混沌工程实践，包括延迟注入、丢包注入、网络分区模拟、DNS故障注入和带宽限制。适用于验证服务在网络异常条件下的容错能力、超时配置合理性以及降级策略有效性。

---

## 1. 陷阱（5项）

### 陷阱1：网络故障注入影响范围过大

- 使用iptables/tc规则注入网络故障时，未精确限定目标端口和协议，导致同节点上所有网络流量受影响
- 在Kubernetes中注入网络故障时，未指定目标Pod标签和命名空间，导致整个节点的网络受影响
- 未考虑网络故障对健康检查的影响：延迟注入可能使Liveness/Readiness Probe超时，触发非预期的Pod重启
- 多个网络故障实验同时运行时，iptables规则叠加产生不可预期的复合效果
- 必须在注入前明确：源/目标IP、端口、协议、方向（入站/出站）、概率，确保影响范围最小化

### 陷阱2：延迟注入参数不当

- 延迟注入仅设置固定延迟（如1000ms），未模拟真实网络抖动（延迟波动±200ms），导致超时配置验证不充分
- 延迟值设置过大（如>30s），超出大多数服务的超时配置，实验仅验证了"超时是否生效"，未验证"延迟下的行为"
- 未区分延迟注入的分布模式：固定延迟（uniform）、正态分布（normal）、帕累托分布（pareto）适用不同场景
- 延迟注入未考虑相关性：真实网络延迟通常是突发的（burst），而非持续均匀的
- 建议从P95延迟的2倍开始注入，逐步增加到P99的5倍，观察服务在不同延迟梯度下的行为变化

### 陷阱3：分区模拟不对称

- 网络分区（partition）模拟仅阻断单向流量，未同时阻断双向流量，导致分区不完全，一端仍能发送请求
- 分区模拟仅隔离网络层，未考虑通过共享存储、消息队列等非网络通道的数据交互
- 分区恢复后，两端状态不一致（如脑裂后的数据冲突），未在实验设计中包含分区恢复后的状态一致性验证
- 分区模拟期间，未监控"分区泄漏"（通过DNS缓存、连接池复用等途径绕过分区）
- 分区模拟必须双向阻断，并验证两端完全隔离后才开始观察，恢复时先验证状态一致性再放行流量

### 陷阱4：DNS故障未清理

- DNS故障注入修改了/etc/resolv.conf或CoreDNS配置，实验终止后未恢复原始配置，导致服务持续无法解析域名
- DNS缓存（应用层/JVM/操作系统）在DNS故障恢复后仍持有错误解析结果，需主动刷新缓存
- CoreDNS的ConfigMap被修改后，未触发CoreDNS Pod重载配置，导致修改未生效或未恢复
- DNS故障注入影响了Kubernetes内部服务发现（Service名称解析），导致集群内部通信异常
- 实验终止后必须验证：/etc/resolv.conf恢复→CoreDNS配置恢复→DNS缓存刷新→服务解析正常

### 陷阱5：带宽限制粒度过粗

- 带宽限制仅设置总带宽上限（如1Mbps），未区分不同流量类型的优先级，导致关键流量（如心跳/健康检查）也被限制
- 带宽限制粒度为节点级，无法精确到容器级或Pod级，导致同节点上所有容器共享受限带宽
- 未考虑TCP拥塞控制对带宽限制的放大效应：带宽限制可能触发TCP重传和超时，实际有效带宽远低于限制值
- 带宽限制未模拟丢包相关性：真实低带宽场景通常伴随高丢包率，两者应组合注入
- 建议使用tc的htb（Hierarchical Token Bucket）队列，为不同流量类型设置不同优先级和带宽配额

## 2. 性能（5项）

### 性能1：延迟注入精度优化

- 使用tc的netem队列规则实现高精度延迟注入，支持固定延迟、延迟分布、延迟相关性配置
- 延迟分布选择指南：固定延迟→验证超时阈值；正态分布→模拟网络抖动；帕累托分布→模拟长尾延迟
- 延迟相关性（correlation）配置：设置25%相关性可模拟突发延迟模式，更接近真实网络行为
- 延迟注入的Jitter参数：在固定延迟基础上增加随机抖动（如1000ms±200ms），避免请求被均匀分散
- 精度验证：注入延迟后使用tcpdump抓包验证实际RTT，确保注入精度误差<5%

### 性能2：丢包模式设计

- 丢包模式应区分：随机丢包（random）、突发丢包（burst）、相关性丢包（correlation）、状态丢包（state）
- 随机丢包：适合验证重试机制，建议从1%开始，逐步增加到5%/10%/20%
- 突发丢包：适合验证批量操作的重试和幂等性，使用Gilbert-Elliott模型模拟Good/Bad状态切换
- 状态丢包：模拟网络设备的间歇性故障，使用Markov链定义Good→Bad和Bad→Good的转移概率
- 丢包注入应区分方向：入站丢包（服务端视角的请求丢失）和出站丢包（客户端视角的响应丢失），行为差异显著

### 性能3：分区模拟策略

- 分区模拟应采用"完全分区"模式（双向阻断），使用tc的fw规则结合iptables标记实现精确分区
- 分区拓扑设计：一对一分区（A↔B隔离）、脑裂分区（A↔C↔B，A和B通过C通信但C故障）、多区域分区
- 分区恢复策略：先恢复网络连通性→等待连接池重建→验证状态一致性→逐步恢复流量
- 分区期间的数据一致性验证：对比分区两端的数据版本号/时间戳/校验和，确保可检测不一致
- 分区模拟应包含时长梯度：1分钟（瞬时分区）→5分钟（短期分区）→30分钟（长期分区），验证不同时长的恢复策略

### 性能4：DNS故障注入优化

- DNS故障类型：域名解析失败（NXDOMAIN）、解析超时（timeout）、解析到错误IP（wrong resolution）
- 优先使用CoreDNS插件注入DNS故障（而非修改/etc/resolv.conf），确保影响范围可控且易于清理
- DNS故障注入应设置TTL覆盖：即使DNS记录恢复，客户端可能仍使用缓存的错误结果，需等待TTL过期或主动刷新
- 域名解析超时注入：修改CoreDNS的响应延迟，模拟DNS服务器过载场景
- DNS故障注入应配合应用层DNS缓存刷新验证：确认应用在DNS恢复后能否正常重新解析

### 性能5：带宽限制动态调整

- 使用tc的htb队列实现分级带宽限制：为关键流量（健康检查/心跳）分配保障带宽，为数据流量分配剩余带宽
- 带宽限制动态调整策略：从正常带宽的50%开始，逐步降低到25%/10%/5%，观察服务在不同带宽下的降级行为
- 带宽限制应配合延迟注入：真实低带宽场景通常伴随高延迟，组合注入更贴近真实
- 带宽限制的burst参数：允许短时间突发流量超过限制值，模拟真实网络的突发特性
- 带宽限制粒度优化：在Kubernetes中使用CNI插件（如Calico）的带宽限制能力，实现Pod级精确限流

## 3. 安全（3项）

### 安全1：网络故障注入导致数据不一致

- 网络分区期间，分布式系统的不同分区可能独立接受写入，分区恢复后产生数据冲突
- 延迟注入可能使写操作超时，客户端重试导致重复写入，若服务不具备幂等性则产生脏数据
- 丢包注入可能使请求或响应丢失，若重试机制与业务逻辑不匹配，可能导致状态机异常
- 网络故障注入期间，应暂停或限制数据写入操作，或确保所有写入操作具备幂等性和冲突检测能力
- 分区恢复后，必须执行数据一致性校验（checksum/版本号对比），确认无数据冲突后再放行流量

### 安全2：网络策略冲突

- 混沌工程注入的iptables规则可能与Kubernetes NetworkPolicy冲突，导致不可预期的网络行为
- 多个网络故障实验同时运行时，各自的iptables规则可能相互覆盖或冲突
- iptables规则插入顺序影响优先级：混沌注入的规则必须插入在NetworkPolicy规则之前，否则可能被绕过
- 网络故障注入可能影响安全设备（WAF/IDS/IPS）的流量检测能力，导致安全策略失效
- 建议在注入前导出当前iptables规则快照，注入后验证规则链完整性，清理后对比确保规则完全恢复

### 安全3：跨命名空间影响

- 网络故障注入在节点级（tc/iptables）执行时，不受Kubernetes命名空间隔离限制，可能影响同节点上其他命名空间的Pod
- 共享节点的多租户环境中，一个租户的网络故障实验可能影响其他租户的服务可用性
- 网络故障注入未考虑Kubernetes的Service Mesh（如Istio）的流量管理规则，可能与之冲突
- 建议在专用节点上执行网络混沌实验（使用nodeSelector/taint），避免影响同节点的其他工作负载
- 或使用Service Mesh层（如Istio的Fault Injection）注入网络故障，实现更精确的命名空间级隔离

## 4. 故障排查（5项）

### 故障排查1：延迟注入未生效

- **现象**：实验状态正常，但目标服务响应时间未增加
- **原因A**：tc规则未应用到正确的网络接口，检查`tc qdisc show dev <interface>`确认规则是否存在
- **原因B**：容器使用hostNetwork模式，tc规则应注入到宿主机网络接口而非容器虚拟接口
- **原因C**：流量走了Service Mesh的sidecar代理（如Envoy），延迟注入应在sidecar层面而非网络层
- **解决**：确认目标网络接口→确认网络模式→检查Service Mesh配置→使用tcpdump验证延迟

### 故障排查2：丢包率异常

- **现象**：实际丢包率与注入值不一致（注入10%但实际丢包30%）
- **原因A**：多个tc规则叠加，丢包率被放大（两个10%丢包规则叠加≈19%丢包率）
- **原因B**：网络本身已有丢包（如网卡缓冲区溢出），注入的丢包率与基础丢包率叠加
- **原因C**：丢包注入仅针对特定端口，但应用使用了动态端口范围，部分流量未被覆盖
- **解决**：检查tc规则是否叠加→测量基础丢包率→确认端口范围→调整注入参数补偿叠加效应

### 故障排查3：分区模拟未恢复

- **现象**：实验终止后，两个分区间仍无法通信
- **原因A**：tc规则未完全清理，残留的规则仍阻断流量，检查`tc qdisc show`确认无残留
- **原因B**：iptables规则未恢复，检查`iptables -L -n -v`确认规则链已恢复
- **原因C**：连接池中的连接在分区期间被标记为不可用，分区恢复后连接未自动重建
- **解决**：手动清理残留tc/iptables规则→重启连接池→验证网络连通性→检查应用层连接状态

### 故障排查4：DNS故障持续

- **现象**：DNS故障实验终止后，服务仍无法解析域名
- **原因A**：/etc/resolv.conf未恢复，检查文件内容是否还原
- **原因B**：CoreDNS ConfigMap未恢复或未重载，检查`kubectl get configmap coredns -n kube-system`
- **原因C**：应用DNS缓存仍持有错误结果，需重启应用或等待缓存TTL过期
- **解决**：恢复resolv.conf→恢复CoreDNS ConfigMap并重载→刷新应用DNS缓存→验证解析正常

### 故障排查5：带宽限制未释放

- **现象**：实验终止后，服务吞吐量仍受限
- **原因A**：tc的htb队列未删除，残留的队列仍限制带宽，使用`tc qdisc del`清理
- **原因B**：CNI插件的带宽限制注解未移除，检查Pod注解`kubernetes.io/egress-bandwidth`
- **原因C**：TCP拥塞窗口在带宽限制期间被缩小，限制解除后窗口恢复需要时间（TCP慢启动）
- **解决**：删除残留tc队列→移除CNI带宽注解→等待TCP窗口恢复或重置连接→验证吞吐量

## 5. 替代方案（3项）

### 替代方案对比

| 维度 | Chaos Mesh网络故障 | Toxiproxy | Linux TC |
|------|-------------------|-----------|----------|
| **部署方式** | K8s DaemonSet，自动注入 | 独立代理服务，需修改应用连接 | 命令行工具，直接操作内核 |
| **故障类型** | 延迟/丢包/分区/带宽/DNS/HTTP | 延迟/丢包/超时/慢连接/分段 | 延迟/丢包/带宽/分区/重排序 |
| **精度控制** | 高，支持延迟分布和相关性 | 中，支持固定延迟和随机丢包 | 最高，支持所有netem参数 |
| **侵入性** | 低，无需修改应用 | 中，需将流量路由到Toxiproxy | 低，透明注入 |
| **K8s集成** | 原生CRD，声明式管理 | 无，需手动部署和管理 | 无，需手动执行命令 |
| **清理能力** | 自动清理，实验终止即恢复 | 自动清理，关闭Toxic即恢复 | 手动清理，容易遗漏 |
| **应用层控制** | 支持HTTP故障注入 | 支持TCP层故障注入 | 仅网络层，无应用层能力 |
| **可观测性** | 集成Prometheus/Grafana | 自带API和简单Dashboard | 无，需自行监控 |
| **适用场景** | K8s环境下的声明式网络混沌 | 开发/测试环境的TCP代理故障 | 精确网络故障注入和调试 |
| **学习曲线** | 低，YAML定义 | 低，API/CLI操作 | 高，需理解tc/netem语法 |

### 替代方案1：Chaos Mesh网络故障

- 适合Kubernetes环境，需要声明式管理和自动化清理的团队
- 优势：原生K8s集成、CRD定义实验、自动清理、支持HTTP层故障注入
- 劣势：依赖DaemonSet特权模式、部分故障类型精度不如Linux TC

### 替代方案2：Toxiproxy

- 适合开发/测试环境，需要快速模拟TCP层故障的场景
- 优势：轻量级、API友好、支持实时开关故障、无需K8s环境
- 劣势：需修改应用连接配置（指向Toxiproxy）、不支持网络分区、生产环境不推荐

### 替代方案3：Linux TC

- 适合需要最高精度网络故障注入的场景，如网络性能调优和协议行为研究
- 优势：最全面的netem参数支持、内核级精度、无额外依赖
- 劣势：命令行操作、需深入理解tc语法、手动清理容易遗漏、无可视化管理

## 6. 已知限制（≥3项）

1. **容器网络复杂性**：Kubernetes的网络模型（CNI插件、Service Mesh、eBPF）使得网络故障注入的生效位置难以精确控制，注入到veth接口、bridge、还是宿主机接口的效果不同
2. **Service Mesh干扰**：使用Istio/Linkerd等Service Mesh时，网络故障注入可能与Sidecar代理的流量管理规则冲突，建议优先使用Service Mesh自带的故障注入能力
3. **TCP连接状态影响**：网络故障注入对已建立的TCP连接和新连接的行为不同，已建立连接可能不受延迟/丢包注入影响（取决于注入位置），需考虑连接复用场景
4. **DNS故障不完整**：DNS故障注入通常仅影响新解析请求，已缓存的结果不受影响，且不同语言的DNS缓存行为差异大（JVM默认缓存永久、Go默认无缓存），实验设计需考虑缓存策略差异
5. **iptables性能开销**：大量iptables规则（多个并发实验）会增加内核网络栈的处理延迟，影响非目标流量的性能
