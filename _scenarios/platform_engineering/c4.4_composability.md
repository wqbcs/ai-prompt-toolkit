# 平台可组合性

## 场景概述

平台可组合性是平台工程的架构核心，决定了平台能力能否像乐高积木一样按需组合和扩展。本场景覆盖平台切片（Thinnest Viable Platform）、能力插件、多租户隔离、API网关和服务网格五大维度，探讨如何构建灵活、可扩展且安全的平台架构。

## 核心覆盖

- **平台切片**：最小可行平台理念，仅提供组织最需要的能力，按需扩展而非大而全
- **能力插件**：标准化的插件接口，第三方和内部团队可开发可插拔的平台能力
- **多租户隔离**：命名空间级和集群级的租户隔离，确保资源、数据和配置的安全边界
- **API网关**：统一的流量入口，实现路由、认证、限流、熔断和可观测性
- **服务网格**：服务间通信的基础设施层，实现流量管理、安全策略和可观测性

## 🚨 陷阱（5项）

### 陷阱1：平台切片粒度过粗

平台团队试图一次交付所有能力（CI/CD+监控+日志+安全+成本管理），导致交付周期长、质量不可控。更常见的是，平台切片虽然划分了但粒度过粗，"开发环境"切片包含了CI/CD+监控+日志+配置管理，开发者要么全用要么全不用。切片之间的依赖关系不清晰，"日志"切片依赖"监控"切片的告警能力，但未声明依赖。

### 陷阱2：插件接口不兼容

平台插件接口缺乏版本化设计，接口变更后旧插件无法运行。插件API从v1升级到v2时未提供兼容层，所有插件必须同时升级。更严重的是，插件接口的设计未考虑向前兼容性，新增字段后旧版本平台无法加载新插件。插件间依赖的共享库版本冲突：插件A依赖lib v1.0，插件B依赖lib v2.0，无法在同一平台运行。

### 陷阱3：多租户隔离不彻底

多租户隔离仅在Kubernetes命名空间层面实现，但集群级资源（ClusterRole、CustomResourceDefinition、PersistentVolume）未隔离。租户A创建的ClusterRole影响租户B的权限。节点级资源（GPU、本地存储）未隔离，租户A的Workload占用了所有GPU资源。控制平面资源（etcd、API Server）未按租户限流，一个租户的API风暴影响所有租户。

### 陷阱4：API网关成为瓶颈

API网关作为所有流量的唯一入口，成为系统可用性和性能的单点故障。网关实例资源不足导致请求排队，P99延迟飙升。网关插件（认证、限流、日志）串行执行，每个插件增加延迟。更危险的是，网关的配置更新需要全量推送和热加载，大规模路由规则更新时可能导致短暂的服务中断。网关与下游服务的健康检查不协调，下游服务已不可用但网关仍路由流量。

### 陷阱5：服务网格配置复杂

Istio/SMC的配置项数量庞大（VirtualService/DestinationRule/PeerAuthentication/AuthorizationPolicy等），配置错误难以排查。流量管理规则优先级不清晰，多个VirtualService匹配同一请求时的行为不可预测。Sidecar代理（Envoy）消耗大量内存（每个Pod额外100-200MB），大规模集群中Sidecar的资源开销显著。服务网格的调试工具不足，请求在网格中的路由路径难以可视化追踪。

## ⚡ 性能（5项）

### 性能1：平台切片懒加载

- 切片按需加载：用户首次访问某能力时才初始化对应切片，减少平台启动时间
- 切片依赖图预计算：平台启动时解析切片依赖，延迟加载无依赖的切片
- 切片资源冷热分离：核心切片（认证、路由）常驻内存，边缘切片按需加载
- 切片预加载提示：用户导航到某功能区域时预加载对应切片，减少等待感
- 切片卸载：长时间未使用的切片自动卸载释放资源，用户再次访问时重新加载

### 性能2：插件热加载优化

- 插件使用独立的Worker进程/容器运行，热加载不影响主进程
- 插件代码缓存：已编译的插件代码缓存在内存或磁盘，热加载时直接复用
- 插件依赖预解析：加载前检查依赖兼容性，不兼容的插件快速失败而非运行时崩溃
- 插件沙箱隔离：使用V8 Isolate或WASM沙箱运行插件，热加载不影响其他插件
- 增量热加载：仅加载变更的插件代码而非全量替换，减少加载时间

### 性能3：多租户资源隔离优化

- Kubernetes ResourceQuota按命名空间设置CPU/内存/存储上限，防止单租户资源抢占
- LimitRange设置Pod级别的资源请求和限制默认值，简化租户配置
- 优先级和抢占（PriorityClass）：关键租户Workload优先级高于普通租户
- 节点池隔离：不同租户的Workload调度到专用节点池，物理隔离消除噪音
- API Server限流：使用API Priority and Fairness按租户分配API调用配额

### 性能4：API网关路由缓存

- 路由规则缓存：网关实例缓存路由表，规则变更时增量推送而非全量刷新
- 响应缓存：对幂等API响应设置短期缓存（Cache-Control: max-age=30），减少后端压力
- 连接池复用：网关到后端服务使用长连接池，减少TCP连接建立开销
- 路由匹配优化：使用前缀树（Trie）或基数树（Radix Tree）数据结构加速路由匹配
- 插件流水线优化：无依赖的插件并行执行，减少请求处理延迟

### 性能5：服务网格Sidecar资源控制

- Sidecar资源配置：Request设为50m CPU/50Mi Memory，Limit设为200m CPU/200Mi Memory
- Sidecar范围限定：使用`exportTo`字段限定服务发现范围，减少每个Sidecar的配置量
- 连接池设置：DestinationRule配置连接池上限，防止Sidecar连接数爆炸
- 熔断器配置：OutlierDetection设置熔断条件，异常后端快速失败而非超时等待
- 选择性注入：仅对需要网格能力的Pod注入Sidecar，减少资源开销

## 🔒 安全（3项）

### 安全1：插件权限越界

插件以平台主进程的权限运行，可访问平台的数据库、密钥和配置。恶意或编写不当的插件可能读取其他插件的敏感数据、修改平台配置、甚至执行任意代码。更常见的是，插件的API调用权限未按最小权限原则限制，插件可调用平台的所有内部API而非仅限声明需要的API。

**应对措施**：插件在沙箱环境（WASM/V8 Isolate/独立容器）中运行，与主进程隔离；插件声明所需权限（如读取配置、调用特定API），平台按声明授予权限；插件API调用通过代理层，代理层校验权限和限流；插件代码审核流程，第三方插件需安全扫描后才能安装；插件运行时监控，检测异常行为（如高频密钥读取）。

### 安全2：多租户数据泄露

多租户隔离失败导致租户间数据泄露。常见原因：数据库查询缺少租户ID过滤条件，返回了其他租户的数据；对象存储的访问策略过于宽松，租户A可读取租户B的OBS桶；日志聚合服务未按租户隔离，租户A的日志可被租户B搜索到；共享缓存（Redis）的Key未添加租户前缀，数据串读。

**应对措施**：数据库强制使用Row-Level Security，查询条件自动注入租户ID；对象存储按租户独立Bucket，Bucket Policy限制跨租户访问；日志服务按租户隔离Index，查询权限按租户过滤；缓存Key使用`{tenantId}:{key}`格式，确保命名空间隔离；定期执行租户隔离渗透测试，验证数据泄露风险。

### 安全3：API网关认证绕过

API网关的认证配置存在漏洞：部分路由未配置认证（如健康检查端点暴露了内部API）；JWT验证未校验`aud`和`iss`字段，接受任何签名的Token；API Key认证的Key在URL参数中传递，被日志和浏览器历史记录捕获；OAuth2的回调URL未严格校验，可被重定向攻击利用。

**应对措施**：所有路由默认启用认证，显式标记公开路由（如`/healthz`）；JWT验证严格校验`aud`、`iss`、`exp`和签名；API Key仅通过HTTP Header传递，禁止URL参数传递；OAuth2回调URL白名单校验，防止重定向攻击；定期审计网关路由配置，检测未认证路由。

## 🔍 故障排查（5项）

### 故障排查1：平台切片加载失败

| 症状 | 可能原因 | 解决方案 |
|------|---------|---------|
| 切片初始化超时 | 依赖服务不可达或启动慢 | 检查依赖服务健康状态；增大初始化超时；实现降级逻辑 |
| 切片功能不可用 | 切片加载成功但功能异常 | 检查切片配置是否完整；查看切片日志定位错误 |
| 切片注册失败 | 切片元数据不符合平台Schema | 使用Schema验证工具检查切片定义；修正不合规字段 |
| 切片间通信失败 | 切片间依赖未正确声明 | 检查切片依赖图；确认依赖切片已加载；验证通信接口版本 |
| 切片资源不足 | 切片所需资源（数据库/缓存）未就绪 | 检查资源初始化顺序；增加资源就绪性检查 |

### 故障排查2：插件冲突

- **版本冲突**：两个插件依赖同一库的不同版本，使用沙箱隔离每个插件的依赖
- **配置覆盖**：两个插件修改同一配置项，检查插件优先级和覆盖规则
- **资源竞争**：两个插件争抢同一资源（端口/文件/数据库连接），分配独立资源
- **事件冲突**：两个插件订阅同一事件但处理逻辑矛盾，检查事件处理优先级
- **调试方法**：逐个禁用插件定位冲突方，使用插件的调试模式查看详细日志

### 故障排查3：多租户资源争抢

1. **监控资源使用**：`kubectl top pods -A`按命名空间查看CPU/内存使用情况
2. **检查ResourceQuota**：`kubectl get resourcequota -n <tenant-ns>`查看配额使用百分比
3. **分析调度失败**：`kubectl describe pod <pod>`查看调度失败原因（资源不足/亲和性冲突）
4. **识别噪音租户**：Prometheus查询`topk(10, container_cpu_usage_seconds_total)`找出CPU消耗Top租户
5. **隔离策略**：将噪音租户迁移到专用节点池，或降低其Workload优先级

### 故障排查4：API网关路由异常

| 异常类型 | 排查方向 |
|---------|---------|
| 路由不匹配 | 检查路由规则的匹配条件（path/method/header）；确认规则优先级和覆盖关系 |
| 路由到错误后端 | 检查路由的upstream配置；确认服务发现是否返回了正确的后端实例 |
| 502/503错误 | 检查后端服务健康状态；确认网关到后端的网络连通性；查看后端服务日志 |
| 限流误触发 | 检查限流策略配置（QPS/并发数）；确认限流Key是否正确；查看限流计数器 |
| 认证失败 | 检查认证插件配置；确认JWT/OAuth2配置正确；查看认证插件日志 |

### 故障排查5：服务网格Sidecar注入失败

- **检查注解**：确认Pod的`sidecar.istio.io/inject`注解设置为`"true"`或命名空间已启用自动注入
- **检查MutatingWebhook**：`kubectl get mutatingwebhookconfiguration`确认istio-sidecar-injector Webhook存在且正常
- **检查Injector日志**：`kubectl logs -n istio-system deploy/istio-sidecar-injector`查看注入失败原因
- **检查资源配额**：Sidecar注入后Pod资源请求增加，可能超过命名空间ResourceQuota
- **检查Pod安全策略**：PSP/PSS可能阻止Sidecar容器的特权操作（如NET_ADMIN capability）

## 🔄 替代方案（3项）

| 维度 | Backstage插件 | Kong+Keycloak | Istio+华为云CCE |
|------|-------------|--------------|-----------------|
| **能力扩展** | Backstage插件生态，前后端一体化 | API网关+认证授权，基础设施层 | 服务网格+CCE集群，运行时层 |
| **插件开发** | React前端+Node.js后端插件 | Lua/Go插件或Serverless函数 | WASM Filter或Envoy Filter |
| **多租户** | Backstage无原生多租户 | Keycloak Realm隔离 | CCE命名空间+Istio Namespace隔离 |
| **API管理** | 通过插件集成第三方API网关 | Kong原生API管理（路由/限流/认证） | Istio Gateway+VirtualService |
| **认证授权** | Backstage依赖外部认证 | Keycloak OIDC/SAML/OAuth2 | Istio PeerAuthentication+AuthorizationPolicy |
| **可观测性** | Backstage集成Grafana/Prometheus | Kong Prometheus Plugin+Grafana | Istio Kiali+Jaeger+Prometheus |
| **学习曲线** | 中等，需了解Backstage架构 | 中等，Kong配置+Keycloak管理 | 较高，Istio概念和配置复杂 |
| **适用场景** | 开发者门户+能力扩展 | API统一入口+认证授权 | 服务间通信管理+流量控制 |

## ⚠️ 已知限制

1. **平台切片的边界定义主观性强**：TVP（Thinnest Viable Platform）的理念强调"最小可行"，但"最小"的定义因组织而异。过于激进的切片可能导致平台能力碎片化，开发者需要组合多个切片才能完成一个任务；过于保守的切片则退化为传统的大而全平台
2. **插件接口的稳定性与演进矛盾**：插件接口需要稳定以保证生态兼容性，但平台演进又需要接口变更。SemVer可以约定版本兼容性，但实际中Minor版本的"兼容性变更"仍可能破坏边缘场景。WebAssembly的沙箱隔离解决了运行时兼容性，但接口语义的兼容性仍需人工保证
3. **多租户隔离的性能开销**：命名空间级隔离通过ResourceQuota和LimitRange实现，但调度器需要逐个检查配额约束，大规模集群中调度延迟增加。节点池隔离实现了物理隔离但资源利用率低（节点碎片）。vCluster等虚拟集群方案增加了管理复杂度
4. **API网关与服务网格的功能重叠**：API网关和服务网格都提供流量管理、认证、限流和可观测性能力，功能边界模糊。南北向流量（外部到内部）由API网关管理，东西向流量（内部到内部）由服务网格管理，但实际场景中边界不清晰（如微服务网关BFF）。两套系统的配置和运维增加了复杂度
5. **服务网格的Sidecar资源开销显著**：每个Pod注入的Envoy Sidecar额外消耗50-200MB内存和50-200m CPU，在大规模集群（1000+ Pod）中累计开销显著。Ambient Mesh模式去除了Sidecar但引入了ztunnel和waypoint代理，整体资源开销并未完全消除
