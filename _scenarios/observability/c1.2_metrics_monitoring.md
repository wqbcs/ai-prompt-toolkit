# 指标监控与告警场景模板

> 覆盖工具链: Prometheus / Grafana / 华为云CloudEye / 自定义指标 / 智能告警

---

## 1. 陷阱（5项）

### 1.1 指标基数爆炸导致存储与查询崩溃
- 高基数标签（user_id、request_id、ip_address）直接作为Prometheus标签，导致时间线数量指数级增长
- 单个指标的时间线超过百万级别后，Prometheus内存占用暴增、查询超时、写入延迟飙升
- 华为云CloudEye自定义指标按维度计费，高基数维度直接导致账单失控
- 缺乏指标基数治理机制，新标签无审批流程，基数在不知不觉中失控
- VictoriaMetrics/Thanos等长期存储方案对高基数指标的压缩效率急剧下降

### 1.2 告警疲劳导致重要告警被淹没
- 告警规则过于敏感（阈值偏低、持续时间偏短），导致大量误报告警，团队逐渐忽视
- 告警缺乏分级（P0/P1/P2/P3），所有告警同等对待，重要告警无法及时关注
- 告警未做收敛和去重，同一问题触发多条告警，通知渠道（钉钉/企微/短信）被轰炸
- 华为云CloudEye告警策略未配置静默规则，维护窗口期告警仍然触发
- 缺乏告警复盘机制，无法识别和消除持续产生无效告警的规则

### 1.3 聚合粒度不当导致指标失真
- 使用avg聚合掩盖了长尾分布，P99延迟正常但avg正常，真实用户体验劣化被隐藏
- 聚合窗口过大（5m/10m），短暂延迟尖刺被平滑掉，无法及时发现瞬时问题
- histogram桶边界设置不合理（默认桶过宽），导致P99/P999计算不准确
- 华为云CloudEye的聚合周期固定（1m/5m），无法自定义更细粒度的聚合
- counter指标未使用rate/increase计算速率，直接使用原始值导致告警规则和面板失真

### 1.4 缺失指标导致监控盲区
- 依赖/中间件（Redis/MySQL/Kafka）缺乏关键指标监控（连接池、慢查询、消费者延迟）
- 业务指标（订单量、支付成功率、库存）未纳入监控体系，业务异常无法及时发现
- 基础设施指标（CPU/内存/磁盘/网络）覆盖完整，但应用层指标（线程池、队列深度）缺失
- 华为云CloudEye默认监控指标有限，自定义指标未补充导致监控盲区
- 缺乏指标覆盖率度量，无法量化监控完善程度

### 1.5 延迟指标误读导致错误决策
- 将avg延迟作为SLO指标，无法反映长尾用户体验，P99/P999才是关键
- histogram的quantile计算使用插值算法，在桶边界附近的分位值不准确
- 混淆服务端延迟与客户端感知延迟，服务端P99正常但客户端因网络延迟体验差
- 使用irate计算短时间速率，波动过大导致告警频繁触发；使用rate计算长时间速率，对突发变化响应慢
- 华为云CloudEye的延迟指标聚合方式（平均/最大/最小）无法替代分位数统计

## 2. 性能（5项）

### 2.1 指标采集频率优化
- Prometheus默认15s抓取间隔，高流量服务可调整为30s降低负载，关键指标保持15s
- 使用scrape_interval按Job/Instance粒度配置差异化采集频率
- Pushgateway场景下合理设置推送间隔，避免高频推送导致Prometheus写入压力
- 华为云CloudEye自定义指标上报频率控制在1分钟以上，避免API限流
- 高基数指标降低采集频率或改用事件驱动采集，低基数关键指标保持高频采集

### 2.2 PromQL查询优化
- 避免在PromQL中使用高基数标签做group_left/join，改用recording rule预计算
- 对高频查询使用recording rule预聚合，减少实时查询的计算量和时间范围
- 查询时间范围限制在合理区间（避免30d全量查询），使用变量模板化时间范围
- 使用offset和@修饰符时注意性能影响，避免对大范围历史数据做复杂运算
- 华为云CloudEye API查询使用分页和合理的时间范围，避免单次查询数据量过大

### 2.3 Grafana面板渲染优化
- 单个Dashboard面板数量控制在20个以内，避免页面渲染性能问题
- 使用变量（Variables）和模板化查询减少重复面板，提高复用性
- 面板刷新间隔合理设置：关键指标10s、一般指标30s、历史趋势60s
- 避免在单个面板中使用过多query，合并相似查询减少Prometheus负载
- 使用Grafana的Explore模式进行临时查询，避免在Dashboard中保留探索性面板

### 2.4 华为云CloudEye API调优
- 自定义指标上报使用批量接口，单次上报多个指标减少API调用次数
- 告警策略配置合理的评估周期和持续时间，避免频繁评估导致API限流
- 使用华为云CloudEye的聚合指标功能，减少客户端聚合计算量
- 控制自定义指标的维度数量（建议≤5个），降低计费和查询复杂度
- 华为云API调用配置重试和退避策略，应对限流和临时故障

### 2.5 自定义指标成本控制
- 建立指标审批流程：新指标必须评估基数、采集频率、存储成本后方可上线
- 定期审计现有指标的使用率，删除无人查询的废弃指标和面板
- 高基数标签改用Exemplar（关联TraceID）或日志分析，不作为指标标签
- 华为云CloudEye自定义指标按维度计费，严格控制维度组合数量
- 使用指标分层策略：L1核心指标（高频率、长期存储）、L2诊断指标（中频率、中期存储）、L3调试指标（低频率、短期存储）

## 3. 安全（3项）

### 3.1 指标数据泄露
- Prometheus的/metrics端点默认无鉴权，暴露内部架构、服务版本、业务量等敏感信息
- Grafana面板截图或导出数据可能包含业务敏感指标（收入、用户数、交易量）
- 华为云CloudEye的指标数据跨账号共享时，可能泄露业务运营数据
- 自定义指标中直接包含用户信息（如user_id维度），违反数据最小化原则
- 缓解措施：/metrics端点配置网络策略限制访问、指标标签脱敏、Grafana配置RBAC

### 3.2 告警静默滥用
- 运维人员为消除告警噪音，对告警规则设置长期静默，导致真实故障无法及时发现
- 告警静默规则缺乏审批流程和过期时间，临时静默变为永久静默
- 华为云CloudEye告警静默未与变更管理流程关联，维护窗口外的静默缺乏审计
- 告警静默后缺乏自动恢复机制，问题解决后静默规则仍残留
- 建议：静默规则强制设置过期时间（最长7天）、审批流程、静默原因记录、定期审计

### 3.3 监控端点未鉴权
- Prometheus的/metrics、Grafana的/api/datasources、华为云CloudEye API未配置严格鉴权
- 攻击者可通过未授权访问的/metrics端点获取服务拓扑、版本信息、业务量等情报
- Grafana默认凭据未修改或弱密码，导致监控数据被未授权访问或篡改
- 华为云CloudEye API的AK/SK泄露可导致指标数据被读取或告警规则被篡改
- 缓解措施：网络策略限制访问源、启用mTLS、定期轮换凭据、API调用审计日志

## 4. 故障排查（5项）

### 4.1 指标采集中断排查
- **现象**: Grafana面板显示No Data或指标断点，Prometheus targets页面显示DOWN
- **排查步骤**:
  1. 检查Prometheus targets页面，确认目标状态和最近抓取时间
  2. 检查目标服务的/metrics端点是否可访问（curl/prometheus http_sd）
  3. 检查网络策略/防火墙是否阻断了Prometheus到目标的访问
  4. 检查Prometheus日志中的scrape错误信息（connection refused/timeout）
  5. 华为云CloudEye检查自定义指标上报任务状态和API调用成功率
- **根因模式**: 服务不可用 > 网络阻断 > 端口变更 > Prometheus配置错误 > API限流

### 4.2 告警未触发排查
- **现象**: 服务明显异常但未收到告警通知，事后发现告警规则存在但未触发
- **排查步骤**:
  1. 检查告警规则的表达式和阈值，手动执行PromQL确认当前值
  2. 检查告警规则的for持续时间是否过长，短暂异常未满足持续时间条件
  3. 检查Alertmanager的路由和静默配置，确认告警未被静默或路由到错误接收者
  4. 华为云CloudEye检查告警策略的触发条件和通知渠道配置
  5. 检查告警通知渠道（钉钉/企微/邮件）是否正常工作
- **根因模式**: 阈值/表达式错误 > for持续时间过长 > 静默规则拦截 > 通知渠道故障 > 评估周期不匹配

### 4.3 Grafana面板空白排查
- **现象**: Grafana面板显示No Data或N/A，数据源配置正常但无法显示数据
- **排查步骤**:
  1. 使用Grafana Explore模式手动执行查询，确认数据源是否返回数据
  2. 检查面板的时间范围是否在数据保留期内
  3. 检查PromQL表达式中的标签匹配是否正确（job/instance/app标签变更）
  4. 检查数据源连接是否正常（Prometheus/华为云CloudEye API连通性）
  5. 检查Grafana变量是否正确解析，变量值是否匹配实际标签值
- **根因模式**: 标签不匹配 > 时间范围超出保留期 > 数据源连接异常 > 变量解析错误 > 查询语法错误

### 4.4 华为云CloudEye数据延迟排查
- **现象**: 华为云CloudEye指标数据延迟数分钟甚至数十分钟，无法实时反映系统状态
- **排查步骤**:
  1. 确认自定义指标上报是否及时，检查客户端上报日志和API响应时间
  2. 检查CloudEye的数据聚合延迟（聚合周期+1分钟为预期延迟）
  3. 确认API调用是否触发限流，检查429状态码和重试日志
  4. 检查网络延迟和DNS解析时间
  5. 华为云工单确认CloudEye服务端是否存在已知延迟问题
- **根因模式**: 上报延迟 > 聚合周期延迟 > API限流 > 网络延迟 > 服务端问题

### 4.5 自定义指标丢失排查
- **现象**: 自定义指标上报后无法在Grafana/CloudEye中查询到
- **排查步骤**:
  1. 确认指标名称和标签是否与查询匹配（命名规范、大小写、前缀）
  2. 检查Prometheus是否配置了对应的scrape目标或华为云CloudEye指标命名空间
  3. 检查指标是否因基数过高被丢弃（Prometheus的label_limit/sample_limit）
  4. 华为云CloudEye确认自定义指标是否在配额限制内
  5. 检查指标上报的时间戳是否在合理范围内（未来时间戳会被丢弃）
- **根因模式**: 命名不匹配 > 未配置采集目标 > 基数限制被丢弃 > 配额超限 > 时间戳异常

## 5. 替代方案（3项）

### 对比表格

| 维度 | Prometheus | Datadog | 华为云CloudEye |
|------|-----------|---------|---------------|
| **部署模式** | 自建（单机/HA/Thanos） | SaaS | SaaS |
| **数据采集** | Pull模式（主动抓取） | Push模式（Agent上报） | Push模式（Agent/API上报） |
| **查询语言** | PromQL | Datadog Query Language | CloudEye API + Grafana |
| **多维度支持** | 标签（Label） | Tag | 维度（Dimension） |
| **长期存储** | Thanos/VictoriaMetrics/Cortex | 内置（15个月） | 内置（93天） |
| **告警能力** | Alertmanager（规则+路由+静默） | 内置（智能告警+异常检测） | 内置（阈值+趋势告警） |
| **仪表盘** | Grafana集成 | 内置Dashboard | 内置+Grafana集成 |
| **成本模型** | 自建基础设施成本 | 按Host/按指标计费 | 按维度计费/包年包月 |
| **华为云集成** | 需手动对接 | 需手动对接 | 原生集成 |
| **AIOps能力** | 无（需第三方） | 异常检测+预测 | 趋势告警+智能分析 |
| **适用场景** | Kubernetes原生、灵活定制 | 全球化SaaS、开箱即用 | 华为云深度用户 |

### 5.1 Prometheus — 云原生监控的事实标准
- 优势：CNCF毕业项目、Kubernetes原生集成、Pull模式简化采集、PromQL强大灵活、社区生态丰富
- 劣势：单机存储有限（本地TSDB约50万时间线）、长期存储需Thanos/VictoriaMetrics等扩展、运维成本高
- 推荐场景：Kubernetes环境、已有Prometheus生态、需要灵活定制查询和告警

### 5.2 Datadog — 全栈可观测性SaaS标杆
- 优势：开箱即用、APM+日志+指标一体化、智能告警和异常检测、多语言Agent、全球基础设施
- 劣势：成本高（按Host计费+按指标计费）、数据存储在海外（合规风险）、定制能力有限
- 推荐场景：全球化业务、需要快速建立全栈监控、团队无自建可观测性能力

### 5.3 华为云CloudEye — 华为云生态的监控首选
- 优势：与ECS/CCE/RDS等华为云服务原生集成、按维度计费成本可控、无需运维基础设施
- 劣势：自定义指标功能有限（维度≤10、聚合周期固定）、查询能力不如PromQL灵活、数据保留期短（93天）
- 推荐场景：华为云深度用户、基础设施监控为主、成本敏感、无Prometheus运维团队

## 6. 已知限制（≥3项）

### 6.1 Prometheus本地存储的容量瓶颈
- 单机Prometheus本地TSDB建议不超过50万活跃时间线，超过后查询和写入性能急剧下降
- 本地存储默认保留15天，长期存储需Thanos/VictoriaMetrics/Cortex等扩展方案
- 远程读写（Remote Write）在高QPS场景下可能成为瓶颈，需调优batch_size和queue_size

### 6.2 华为云CloudEye自定义指标的限制
- 自定义指标维度数量上限为10个，超过则无法上报
- 自定义指标聚合周期固定为1分钟和5分钟，无法支持更细粒度
- 自定义指标数据保留期为93天，无法查询更早的历史数据
- API调用频率有限流（每分钟/每天调用次数限制），高频率上报需使用批量接口

### 6.3 告警规则的表达力限制
- PromQL不支持跨数据源关联查询（指标A与指标B的比值/差值需要同一数据源）
- 告警规则无法直接引用外部数据（如CMDB中的服务优先级、值班表）
- 华为云CloudEye告警策略的条件表达式不如PromQL灵活，复杂条件需多策略组合
- 告警恢复通知缺乏上下文信息（恢复原因、影响范围），不利于复盘分析

### 6.4 高基数指标的治理困境
- 高基数指标（按user_id/tenant_id标签）一旦进入Prometheus，删除需要重启实例
- recording rule无法解决高基数问题，预聚合后的中间结果仍可能产生大量时间线
- 华为云CloudEye按维度计费模式下，高基数维度的成本难以预估和控制
- 缺乏自动化的指标基数监控和告警机制，基数增长往往是被动发现的

### 6.5 多集群监控的 federation 复杂度
- Prometheus联邦查询在大规模多集群场景下性能较差，全局视图查询延迟高
- Thanos的全局查询需要Query Frontend做查询拆分和缓存，架构复杂度高
- 华为云CloudEye的多账号监控需要配置委托和跨账号访问，权限管理复杂
- 不同集群的指标标签规范不一致，全局聚合查询结果不准确
