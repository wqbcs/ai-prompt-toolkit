# 系统可观测性设计场景模板

> 覆盖: 三大支柱整合 / 可观测性成熟度模型 / SLO / SLI / 错误预算

---

## 1. 陷阱（5项）

### 1.1 三支柱各自为政导致排障效率低下
- 追踪（Trace）、指标（Metric）、日志（Log）三套系统独立建设，缺乏关联机制，排障需在三个工具间反复切换
- TraceID未注入日志、日志未关联指标、指标未关联Trace Exemplar，三大支柱成为信息孤岛
- 三套系统使用不同的服务命名/标签规范，同一服务在不同系统中名称不一致，无法快速关联
- 告警触发后无法一键跳转到关联日志和链路，排障人员需要手动搜索和拼凑信息
- 华为云APM/CloudEye/LTS虽可集成但需手动配置关联规则，配置遗漏导致断链

### 1.2 SLO定义模糊导致可观测性失效
- SLO定义过于笼统（如"系统可用性>99.9%"），未明确具体指标、计算方式、时间窗口和排除条件
- SLI（服务级别指标）选择不当：使用avg延迟代替P99延迟、使用服务端成功率代替客户端成功率
- SLO时间窗口选择不当：使用年度SLO掩盖了短期严重故障，月度SLO波动过大
- 缺乏SLO的分级体系：所有服务同一SLO标准，核心服务与辅助服务无差异化
- SLO未与业务影响关联，技术指标正常但业务体验差（如搜索结果质量下降）未纳入SLO

### 1.3 错误预算超支无动作导致系统退化
- 错误预算耗尽后缺乏明确的响应流程，团队继续发布新功能而非停止变更修复可靠性问题
- 错误预算消耗速率未监控，预算在月初就耗尽但未触发任何告警
- 错误预算的消耗归因不清，无法区分是哪个服务/变更导致的预算消耗加速
- 缺乏错误预算的政策定义：预算耗尽后是否冻结发布？是否强制进入可靠性改进阶段？
- 华为云CloudEye的SLO功能缺乏错误预算可视化，团队对预算消耗无感知

### 1.4 可观测性成熟度停滞导致能力瓶颈
- 可观测性停留在L1（被动监控）阶段：仅有基础指标和告警，缺乏主动发现和预测能力
- 团队依赖仪表盘巡检发现问题，缺乏异常自动检测和智能告警
- 可观测性工具持续增加但成熟度未提升：工具碎片化、数据孤岛、排障效率无改善
- 缺乏可观测性成熟度评估模型，无法量化当前水平和改进方向
- 华为云APM提供了L2/L3能力但团队仅使用L1功能，高级特性（拓扑分析、智能告警）未被采纳

### 1.5 工具碎片化导致可观测性成本失控
- 追踪用Jaeger、日志用ELK、指标用Prometheus、告警用PagerDuty、面板用Grafana，5+工具的许可、运维、学习成本叠加
- 不同工具的数据格式和API不兼容，数据互操作需要大量集成开发
- 工具碎片化导致告警来源分散，缺乏统一告警管理，团队需要同时关注多个告警渠道
- 华为云APM+CloudEye+LTS三件套可替代部分碎片化工具，但迁移成本阻碍整合
- 工具选型缺乏整体规划，各团队独立选型导致工具重复和生态割裂

## 2. 性能（5项）

### 2.1 SLO/SLI指标体系设计
- 采用分层SLO设计：L0全局SLO（用户可访问性）> L1服务SLO（核心接口可用性+延迟）> L2依赖SLO（数据库/缓存/消息队列）
- SLI选择遵循用户感知优先原则：客户端延迟 > 服务端延迟、端到端成功率 > 单服务成功率
- 使用多维度SLI：可用性（成功率）、延迟（P50/P90/P99/P999）、吞吐量（QPS）、耐久性（数据不丢失）
- SLO时间窗口采用滚动窗口（28天）替代日历月，避免月初集中出错和月末过度紧张
- 华为云CloudEye配置SLO仪表盘，实时展示SLI趋势和错误预算消耗情况

### 2.2 错误预算策略优化
- 错误预算 = (1 - SLO) × 时间窗口总请求量，按服务重要性和流量分配差异化预算
- 错误预算分三级策略：绿色（预算消耗<50%）正常发布、黄色（50%-80%）只允许可靠性改进、红色（>80%）冻结发布
- 错误预算消耗速率监控：按天/周计算消耗速率，预测预算耗尽时间，提前预警
- 错误预算归因分析：按服务、变更、依赖故障维度拆分预算消耗，识别最大消耗来源
- 华为云CloudEye配置错误预算告警：预算消耗达50%/80%/100%分别触发P2/P1/P0告警

### 2.3 可观测性平台集成优化
- 采用OpenTelemetry作为统一采集层，SDK一次埋点同时产出Trace/Metric/Log三信号数据
- 使用Grafana作为统一可视化层，集成Prometheus（指标）、Loki（日志）、Tempo（追踪）三数据源
- 告警统一收敛到Alertmanager或华为云CloudEye，统一路由、去重、静默、升级策略
- 统一标签/维度规范：service、environment、version、region作为所有信号的标准标签
- 华为云APM+CloudEye+LTS三件套配置关联规则，实现链路-指标-日志一键关联

### 2.4 告警收敛与降噪
- 告警分级：P0（5分钟响应/15分钟升级）、P1（15分钟响应/1小时升级）、P2（1小时响应/次日升级）、P3（次日处理）
- 告警收敛策略：同一服务同一告警5分钟内去重、同一故障域告警按拓扑关系聚合
- 告警降噪规则：维护窗口静默、已知问题关联工单静默、重复告警自动降级
- 智能告警：使用异常检测替代静态阈值，减少因业务波动导致的误报
- 华为云CloudEye配置告警策略组，按业务域和服务组统一管理告警规则

### 2.5 可观测性成本优化
- 可观测性成本分摊到各业务团队，按使用量（指标基数、日志量、Span量）计费
- 数据分层存储：热数据（7天/SSD）> 温数据（30天/HDD）> 冷数据（>30天/对象存储）
- 定期审计可观测性数据使用率：删除无人查询的指标/面板、降低低价值日志的采集频率
- 采样策略优化：正常流量低采样、异常流量高采样、核心服务高采样、辅助服务低采样
- 华为云APM/CloudEye/LTS使用包年包月替代按量计费，长期使用成本更低

## 3. 安全（3项）

### 3.1 可观测性数据合规
- 可观测性数据（Trace/Metric/Log）可能包含个人信息（IP地址、用户行为、地理位置），属于GDPR/个保法管辖范围
- 数据跨境传输合规：华为云APM/CloudEye/LTS数据存储在指定Region，跨境需满足数据本地化要求
- 数据保留期限合规：等保要求日志保留≥180天、GDPR要求不得超出必要期限、行业监管可能有特殊要求
- 可观测性数据的处理需要明确法律依据（合同履行/合法利益/同意），并记录数据处理活动
- 华为云APM/CloudEye/LTS需配置数据保留策略和自动清理规则，确保合规

### 3.2 跨团队数据访问控制
- 可观测性平台的多租户访问控制：团队A只能查看团队A的服务指标/日志/链路
- 敏感服务（支付/用户/认证）的日志和链路数据需要额外审批才能访问
- Grafana的RBAC配置：Viewer/Editor/Admin角色按团队分配，敏感Dashboard设置组织级别权限
- 华为云IAM配置精细化权限：只读权限/操作权限/管理权限按角色分离
- 定期审计可观测性平台的访问日志，发现异常访问行为

### 3.3 监控盲区
- 缺乏对第三方依赖（SaaS服务/外部API）的可观测性，外部故障无法及时发现
- 后台任务（定时任务/数据同步/消息消费）缺乏监控，延迟和失败无法及时发现
- 数据层面的可观测性不足：数据一致性、数据延迟、数据质量缺乏监控
- 前端/RUM可观测性缺失：客户端错误、页面性能、用户体验缺乏监控
- 华为云APM对非HTTP/gRPC协议（如TCP自定义协议、消息队列）的追踪覆盖不足

## 4. 故障排查（5项）

### 4.1 SLO频繁违反排查
- **现象**: SLO违反次数持续增加，错误预算消耗加速，团队疲于应对
- **排查步骤**:
  1. 分析SLO违反的时间分布：集中时段/均匀分布/突发尖刺
  2. 按服务/接口/依赖拆分SLO违反来源，识别最大贡献者
  3. 关联变更时间线：SLO违反是否与部署/配置变更相关
  4. 分析错误类型分布：超时/5xx/4xx/降级，定位根因类别
  5. 华为云APM分析链路数据，识别延迟尖刺和错误集中的服务节点
- **根因模式**: 新变更引入缺陷 > 依赖服务降级 > 资源不足 > 配置错误 > 流量模式变化

### 4.2 错误预算耗尽排查
- **现象**: 错误预算在时间窗口早期就耗尽，团队被迫冻结发布
- **排查步骤**:
  1. 识别错误预算消耗的峰值时段和对应事件
  2. 按故障类型分类：计划内维护/计划外故障/变更引发/依赖故障
  3. 评估预算分配是否合理：高流量服务与低流量服务使用相同SLO标准是否合适
  4. 分析预算消耗趋势：是否逐月加速，系统可靠性是否在退化
  5. 华为云CloudEye查看SLO趋势图和错误预算消耗曲线
- **根因模式**: 重大故障消耗大量预算 > 频繁小故障累积 > SLO标准过高 > 预算分配不合理

### 4.3 告警风暴排查
- **现象**: 短时间内收到数十甚至数百条告警，团队无法有效响应
- **排查步骤**:
  1. 确认告警的根因：单一故障引发级联告警 vs 多个独立故障同时发生
  2. 分析告警的拓扑关系：下游服务告警是否由上游服务故障触发
  3. 检查告警规则是否存在重复：同一指标配置了多条阈值不同的告警规则
  4. 评估告警收敛策略是否生效：去重/聚合/静默规则是否正确配置
  5. 华为云CloudEye查看告警历史和关联分析
- **根因模式**: 级联故障 > 告警规则重复 > 收敛策略失效 > 阈值过于敏感 > 维护窗口未静默

### 4.4 可观测性平台故障排查
- **现象**: 可观测性平台自身不可用（Grafana无法访问、Prometheus宕机、华为云APM数据缺失）
- **排查步骤**:
  1. 确认可观测性平台的基础设施状态（K8s Pod/CPU/内存/磁盘）
  2. 检查数据采集链路：Agent→Collector→Storage各环节是否正常
  3. 确认网络连通性：各组件间的网络策略和防火墙规则
  4. 华为云控制台查看APM/CloudEye/LTS服务状态和配额
  5. 启用备用可观测性方案：直接访问服务/metrics端点、查看服务本地日志
- **根因模式**: 基础设施故障 > 采集链路中断 > 网络策略变更 > 配额超限 > 版本升级兼容性问题

### 4.5 数据一致性问题排查
- **现象**: 指标、日志、追踪三方数据不一致（如指标显示成功但日志记录错误、链路显示完整但日志缺失）
- **排查步骤**:
  1. 对比三方数据的时间戳和计数，确认不一致的范围和程度
  2. 检查数据采集链路的时间差：指标实时采集、日志可能延迟、追踪可能采样
  3. 确认标签/维度/TraceID是否一致：同一服务在不同系统中的标识是否匹配
  4. 检查采样和聚合策略：追踪采样可能导致链路数据与日志/指标不对应
  5. 华为云APM/CloudEye/LTS关联配置检查：确保三系统使用统一的服务标识和时间基准
- **根因模式**: 采样偏差 > 采集延迟差 > 标签不匹配 > 聚合口径不一致 > 关联配置错误

## 5. 替代方案（3项）

### 对比表格

| 维度 | 自建可观测性平台 | SaaS可观测性 | 华为云APM全栈 |
|------|-----------------|-------------|--------------|
| **架构模式** | OpenTelemetry+Prometheus+Loki+Tempo+Grafana | Datadog/NewRelic/Dynatrace | APM+CloudEye+LTS |
| **部署复杂度** | 极高（5+组件自建运维） | 低（Agent安装即用） | 低（Agent安装即用） |
| **数据主权** | 完全自主（数据在自有基础设施） | 数据在SaaS厂商（海外为主） | 数据在华为云（指定Region） |
| **三支柱整合** | 需手动配置关联（Grafana统一可视化） | 原生一体化 | 原生一体化（需配置关联规则） |
| **定制能力** | 极强（完全可控） | 有限（受限于SaaS功能） | 中等（API+自定义指标） |
| **AIOps能力** | 需第三方或自建 | 内置异常检测/根因分析 | 趋势告警/智能分析 |
| **成本模型** | 基础设施+人力成本（固定+弹性） | 按Host/按量计费（弹性） | 按量/包年包月（弹性+固定） |
| **运维人力** | 需要1-3人专职运维可观测性平台 | 几乎无需运维 | 几乎无需运维 |
| **适用场景** | 大规模/合规严格/需要深度定制 | 全球化/快速接入/无专职团队 | 华为云深度用户/合规要求 |

### 5.1 自建可观测性平台 — 完全自主的深度定制方案
- 优势：数据完全自主、定制能力极强、无厂商锁定、成本在大规模场景下可控
- 劣势：部署运维复杂度极高、需要专职团队、功能迭代依赖社区/自研、学习曲线陡峭
- 推荐场景：大规模系统（>1000服务）、合规严格（数据不出境）、有专职可观测性团队

### 5.2 SaaS可观测性 — 开箱即用的全栈方案
- 优势：开箱即用、AIOps内置（异常检测/根因分析）、多语言Agent、全球基础设施
- 劣势：成本高（按Host计费+数据量计费）、数据在海外（合规风险）、定制能力有限
- 推荐场景：中小规模系统、全球化业务、无专职可观测性团队、快速接入需求

### 5.3 华为云APM全栈 — 华为云生态的一体化方案
- 优势：APM+CloudEye+LTS一体化、华为云服务原生集成、数据在国内（合规友好）、技术支持
- 劣势：功能深度不如自建和SaaS、部分语言支持有限、定制能力中等、华为云生态锁定
- 推荐场景：华为云深度用户、合规要求（数据不出境）、中等规模系统、快速接入需求

## 6. 已知限制（≥3项）

### 6.1 可观测性成熟度提升的组织阻力
- L1→L2提升需要文化和流程变革（从被动响应到主动发现），阻力来自习惯和考核机制
- L2→L3提升需要SRE实践（SLO/错误预算/故障复盘），需要组织层面的支持和投入
- 可观测性工具的升级不等于成熟度的提升，工具先进但使用方式落后是常见问题
- 华为云APM的L3功能（智能根因分析/容量规划）需要足够的训练数据和正确的使用方式

### 6.2 SLO的设定困境
- SLO设定过高（如99.99%）导致错误预算极小，任何小故障都触发红色告警，团队疲于应对
- SLO设定过低（如99.5%）无法驱动可靠性改进，系统退化无感知
- SLO的SLI选择偏差：技术指标（服务端延迟）与用户感知（客户端延迟）存在差距
- 多维度SLO的聚合计算复杂：可用性SLO和延迟SLO如何综合评估？

### 6.3 三支柱关联的实现复杂度
- TraceID注入日志需要应用框架支持（MDC/Context），遗留系统改造成本高
- 指标与追踪的关联（Exemplar）在Prometheus中仅支持Histogram和Counter，覆盖不全
- 日志与指标的关联需要在日志查询时实时计算指标，性能开销大
- 华为云APM/CloudEye/LTS的关联需要统一服务标识和配置映射关系，配置遗漏导致断链

### 6.4 可观测性平台的自身可靠性问题
- 可观测性平台自身故障（Grafana宕机、Prometheus OOM）导致排障时"灯下黑"
- 可观测性数据丢失（采集链路中断、存储故障）导致关键时段无数据可查
- 自建可观测性平台需要独立的监控方案（谁监控监控者？），增加额外复杂度
- 华为云APM/CloudEye/LTS作为SaaS服务可用性高，但仍需考虑华为云Region级故障的应急预案

### 6.5 错误预算的政策落地困难
- 错误预算耗尽后冻结发布的政策在业务压力下难以执行（"这个功能必须上线"）
- 错误预算的分配在多团队共享服务场景下难以公平划分
