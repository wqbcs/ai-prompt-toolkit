# Kimi长上下文适配策略

> **版本**：v1.0.0
> **日期**：2026-05-29
> **迭代**：C10-迭代49
> **适用场景**：02_架构设计(长文档分析)

---

## 一、适配原理

Kimi核心优势在于200K超长上下文窗口(国内最长)和联网搜索增强。长文档分析策略充分利用>128K上下文能力，将完整项目文档/架构设计书一次性注入，避免分段导致的信息丢失，同时结合联网搜索获取最新技术信息。

---

## 二、02_架构设计场景长文档分析策略

### 2.1 >128K上下文利用策略

```markdown
<!-- Kimi 长上下文适配指令 -->
【Kimi长文档深度分析策略】

**上下文利用模式**：一次性注入全量文档（充分利用200K窗口）

**分析流程**：

**Phase 1: 全局理解（一次性注入）**
将以下文档一次性全部注入：
- 架构设计文档（完整版本）
- 系统依赖关系图
- 接口定义文档
- 部署架构文档
- 历史架构决策记录(ADR)
- 性能基线数据

**Phase 2: 深度分析（200K窗口内跨文档关联）**
请执行以下跨文档关联分析：

1. 【跨模块依赖分析】
   - 构建模块依赖图：识别循环依赖/单点依赖/过深依赖链
   - 依赖热力图：标注高频调用路径和瓶颈模块
   - 版本兼容性：跨模块API版本一致性检查

2. 【架构一致性验证】
   - 设计文档 vs 实现代码一致性
   - 接口定义 vs 实际实现一致性
   - 部署配置 vs 架构设计一致性
   - 识别文档-代码漂移(drift)

3. 【非功能需求覆盖度分析】
   - 性能：所有关键路径是否有性能预算？
   - 安全：所有外部入口是否有安全设计？
   - 可用性：所有关键服务是否有容错设计？
   - 可扩展性：所有预期增长点是否有扩展设计？

4. 【技术债全景扫描】
   - 架构债：过时模式/硬编码配置/缺失抽象
   - 代码债：TODO/FIXME/HACK标记统计+分类
   - 文档债：过期文档/缺失文档/不一致文档
   - 测试债：缺失测试/过期测试/低覆盖率模块

**Phase 3: 联网搜索增强（获取最新技术信息）**
当分析涉及以下内容时，使用联网搜索：
- 框架/库的最新版本和安全漏洞
- 新的架构模式和最佳实践
- 竞品的架构方案对比
- 最新的性能优化技术

标注信息来源：[联网搜索:查询词|来源URL|获取时间]

**Phase 4: 综合评审报告**
```json
{
  "architecture_review": {
    "overall_score": 0,
    "module_count": 0,
    "dependency_issues": [],
    "consistency_gaps": [],
    "nfr_coverage": {"performance": 0, "security": 0, "availability": 0, "scalability": 0},
    "tech_debt_summary": {"architecture": 0, "code": 0, "documentation": 0, "test": 0},
    "improvement_priorities": []
  },
  "cross_document_findings": [],
  "web_enhanced_insights": [],
  "recommendation": ""
}
```
```

### 2.2 长文档注入规范

```markdown
【Kimi长文档注入规范】

1. 文档预处理：
   - 移除无关内容(页眉页脚/目录导航/广告)
   - 保留结构标记(标题/列表/代码块/表格)
   - 标注文档版本和日期

2. 注入策略：
   - 单次注入最大200K tokens
   - 如超200K，按文档优先级分批注入
   - 优先级：架构核心文档 > 接口定义 > 依赖配置 > 测试文档 > 历史文档

3. 输出控制：
   - 先输出200字全局概要
   - 再逐模块详细分析
   - 最后综合结论和优先改进建议
   - 分段输出，每段不超过3000字
```
